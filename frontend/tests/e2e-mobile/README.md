# Мобильный UI/UX-набор

Проверяет, что платформой удобно пользоваться с телефона — и посетителю сайта,
и сотруднику в рабочих разделах. Это не скриншотные тесты: они бы требовали
перегенерации эталонов при каждой правке вёрстки и всё равно не отвечали на
вопрос «попадает ли сюда палец». Здесь измеряются свойства, которые можно
проверить объективно.

## Запуск

```bash
# весь набор (два размера экрана: 360 и 390 CSS-px)
npm run test:mobile

# один размер
npx playwright test --config=playwright.mobile.config.ts --project=android-360

# сводка нарушений по всем экранам, ничего не утверждает — печатает картину
# целиком и готовые строки для baseline.ts
npm run test:mobile:probe
```

Vite поднимается автоматически (`webServer` в `playwright.mobile.config.ts`,
`reuseExistingServer: true`). Нужен работающий backend: логин идёт через
`/api/users/v1/token/` учёткой `admin` / `admin12345` — переопределяется
переменными `E2E_ADMIN_LOGIN`, `E2E_ADMIN_PASSWORD`, `E2E_MOBILE_BASE_URL`.
Браузер — `msedge`: бинарника chromium на машинах разработки нет, движок тот же.

## Что проверяется

| Правило | Что ловит | Порог |
|---|---|---|
| `horizontal-overflow` | Контент шире экрана: обрезанные заголовки, уехавшие за край кнопки и картинки | строго 0 |
| `input-zoom` | Поля ввода мельче 16px — Safari на iOS зумит вёрстку при фокусе и обратно не отматывает | строго 0 |
| `touch-target` | Интерактивные элементы меньше 44×44px (рекомендация Apple HIG) | храповик, см. `baseline.ts` |

Плюс поведенческие проверки в `03_interactions.spec.ts`: мобильное меню
(открытие, блокировка прокрутки, закрытие по фону), нижняя навигация (ведёт по
своим разделам и ничего не прячет под собой в самом низу страницы), карусели на
главной листаются, модальное окно помещается в экран и закрывается.

### Почему `horizontal-overflow` смотрит на элементы, а не на `scrollWidth`

В `index.css` у `body` стоит `overflow-x: hidden`. Он не даёт странице ездить
вбок, но и **прячет симптом**: при реальном переполнении `scrollWidth` документа
остаётся равен ширине экрана, а контент просто обрезается. Поэтому проверяется
геометрия каждого элемента.

Самая частая причина такого переполнения в этом проекте — grid-элемент без
`min-w-0`: у него `min-width: auto`, он отказывается сжиматься уже своего
`max-content` и растягивает всю сетку. Так уезжали за экран секции «О нас»,
«Миссия», «Контакты» и карточки должностей.

### Почему нет проверки «элемент перекрыт»

Она была и дважды дала ложные срабатывания. Сам факт «элемент сейчас под
панелью» дефектом не является — пользователь его прокрутит. Отличить это от
настоящего «прокруткой уже не достать» одним замером геометрии не выходит:
у верхнего и нижнего края правило зеркальное, а липкая шапка ещё и анимирует
высоту 500мс. Вместо ненадёжной эвристики на 35 экранов оставлен один точный
тест в `03_interactions.spec.ts` — страница прокручивается до упора вниз, и там
проверяется, что нижняя навигация ничего под собой не прячет.

## Файлы

- `mobileAudit.ts` — движок: правила, `settlePage` (дожидается монтирования
  всех `LazySection`), форматирование отчёта.
- `pages.ts` — каталоги экранов посетителя и сотрудника, плюс точечные
  исключения (бегущая строка партнёров, холст react-flow).
- `baseline.ts` — храповик остаточного долга по тач-целям.
- `fixtures.ts` — логин через API, токены в `localStorage` до загрузки SPA.

## Как добавить экран

Допишите строку в нужный массив `pages.ts`. Порог по умолчанию — 0, то есть
новый экран обязан быть чистым. Если он таким пока быть не может, добавьте
запись в `baseline.ts` с числом из `npm run test:mobile:probe` и комментарием,
почему.

## Как расширить зону нажатия, не меняя вид

Мелкий по виду контрол (переключатель) можно оставить как есть, а зону нажатия
растянуть невидимым `::after` — так сделано в `ui/switch.tsx`. Элемент при этом
помечается `data-touch-expanded`, и аудит досчитывает вылет псевдоэлемента.
Маркеру он не верит: если расширение не дотянуло до 44px, нарушение засчитается.
