# Слой данных

Postgres, миграции и тестовая база. Много места занимает объяснение того,
чего в коде **больше нет** — потому что следы этого «нет» разбросаны по
репозиторию и сбивают с толку.

---

## 1. Django ходит в Postgres напрямую

`backend/htqweb/settings/base.py`, секция `DATABASES`:

| Параметр | Значение | Комментарий |
|---|---|---|
| `ENGINE` | `django.db.backends.postgresql` | psycopg, синхронный |
| `HOST` / `PORT` | из окружения; в контейнерах `db:5432` | дефолт `localhost:6432` — для хостовых утилит |
| `CONN_MAX_AGE` | `0` | соединение не переиспользуется между запросами |
| `DISABLE_SERVER_SIDE_CURSORS` | `True` | наследие пулера, см. ниже |

Пул соединений — на уровне приложения, отдельного внешнего пулера в пути
запроса нет.

---

## 2. PgBouncer: что это и почему его можно игнорировать

PgBouncer (`:6432`) остался в compose-файлах, но **в пути живого запроса его
нет**. Он нужен для хостовых утилит и ручного `psql`.

Знать про него надо ради двух вещей:

**Дефолт порта.** `manage.py` по умолчанию целится в `localhost:6432`, то есть
в пулер, чьи учётные данные с хоста не проходят SASL. Симптом — необъяснимая
ошибка аутентификации при запуске управляющих команд с хоста. Лечение —
явно указать беспуловый порт (см. раздел 5).

**`DISABLE_SERVER_SIDE_CURSORS = True`.** Это не оптимизация, а требование
пулера в transaction-режиме: серверный курсор живёт дольше транзакции, а пулер
между транзакциями отдаёт соединение другому клиенту. Настройка осталась с тех
времён.

---

## 3. Чего в схеме больше нет (историческая справка)

FastAPI-поколение держало все девять сервисов за PgBouncer в
transaction-режиме. Пулер в этом режиме **молча теряет `search_path`**, из-за
чего все сервисы фактически жили в схеме `public` и различались префиксами
таблиц: `hr_*`, `task_*`, `request_*`, `cms_*`, `email_*`. Alembic'у ради
переживания пулера требовался отдельный поток на каждую миграцию.

**К нынешнему коду ничего из этого не относится.** Сейчас: одна схема
`public`, натуральные имена таблиц `<аппка>_<модель>`, `managed=True`, обычные
`makemigrations` / `migrate`.

Абзац существует затем, чтобы, наткнувшись на префиксы в старых миграциях или
на упоминания Alembic в документах, вы не приняли их за действующее правило.

## 4. Расширения Postgres

`infra/db/init-ltree.sql` выполняется при первом создании базы:

- **`ltree`** — иерархические пути. Используется деревом отделов
  (`backend/apps/hr/models.py`, `backend/apps/hr/services/department_service.py`)
  и в `backend/apps/messenger/models.py`.
- **`pgcrypto`**.

Важно: расширения ставятся **при инициализации тома**. Если база создана без
них, миграции упадут, и повторный запуск контейнера не поможет — скрипт
инициализации на существующем томе не выполняется.

## 5. Тестовая база: почему отдельный порт

`pytest-django` создаёт и удаляет базу `test_htqweb` через `CREATE DATABASE` /
`DROP DATABASE`. Через transaction-пул PgBouncer такие команды не проходят.
Плюс на хосте порт `:5432` обычно занят нативным Windows-Postgres.

Отсюда третий адрес — прямой, беспуловый, на отдельном хостовом порту.
Поднимается только БД:

```bash
docker compose -f docker-compose.test-local.yml up -d db
```

Запуск сюиты из `backend/`:

```bash
./.venv/Scripts/python.exe -m pytest -q
```

`DJANGO_SETTINGS_MODULE` и `JWT_SECRET` заданы в `backend/pytest.ini` и
`backend/htqweb/settings/test.py` — руками ничего экспортировать не нужно.
Полная сюита — около 3900 тестов, порядка 13 минут.

Подробности — [backend/README-tests.md](../../backend/README-tests.md).

### Интерпретатор

Виртуальных окружения два, и это ловушка: в корневом `.venv` **нет
`pytest-django`**. Запуск им даёт лавину ошибок
`ImproperlyConfigured: Requested setting INSTALLED_APPS` — выглядит как
поломка импортов по всему проекту, хотя дело только в интерпретаторе.

Правильный — `backend/.venv/Scripts/python.exe`.

### `max_connections`

В compose тестовой БД поднят до 300 (`docker-compose.test-local.yml`).
Длинная сюита с тестами `transaction=True` под дефолтными сотней упирается в
лимит к концу прогона и сыплет ошибками в хвосте.

## 6. Две засады с портом тестовой БД

Обе выглядят одинаково — «pytest завис» — и имеют разные причины.

**Первая: `docker restart` контейнера БД.** Плоский `docker restart`
пересоздаёт контейнер **без публикации порта**, потому что не применяет
конфигурацию compose. Дальше каждое соединение ждёт таймаута, и это читается
как «медленная миграция», хотя pytest вообще не подключился.

Поднимать только через compose, не через `docker restart`.

**Вторая: порт забрал Windows.** WinNAT после перезапуска резервирует куски
динамического диапазона, и порт тестовой БД может оказаться внутри. Симптом
при старте контейнера:

```
Error response from daemon: ports are not available ...
bind: An attempt was made to access a socket in a way forbidden by its access permissions
```

Проверить:

```powershell
netsh interface ipv4 show excludedportrange protocol=tcp
```

Обход без прав администратора — порт параметризован с обеих сторон:

```powershell
$env:DB_HOST_PORT='15432'   # compose: "${DB_HOST_PORT:-55432}:5432"
docker compose -f docker-compose.test-local.yml up -d db
$env:TEST_DB_PORT='15432'   # settings/test.py читает TEST_DB_PORT
```

Диагностика: `docker port <контейнер-БД>` должен показать проброс на хост.
Если показывает только `5432/tcp` — порт не опубликован, и это первая или
вторая засада.

## 7. Миграции

Обычные Django-миграции. После правки моделей:

```bash
../.venv/Scripts/python.exe manage.py makemigrations <аппка>
../.venv/Scripts/python.exe manage.py migrate
```

Два правила, специфичных для платформы:

1. **Миграции накатывает только `backend-web`**, под флагом `RUN_MIGRATIONS`
   (см. [00-overview.md](00-overview.md)). На боевой базе флаг бывает выключен —
   тогда миграции применяются вручную.
2. **Междоменных внешних ключей не бывает.** Связь между доменами — через
   `interface.py`, не через FK (см. [01-conventions.md](01-conventions.md),
   раздел 4). Миграция, заводящая FK в чужую аппку, нарушает изоляцию.

## 8. Доступ к базе с хоста

Дефолтный `manage.py` целится в пулер, чьи учётные данные с хоста не работают.
Для управляющих команд указывайте беспуловый порт и настройки явно:

```bash
cd backend
DJANGO_SETTINGS_MODULE=htqweb.settings.dev DB_HOST=localhost DB_PORT=55432 \
  DB_NAME=htqweb DB_USER=htqweb DB_PASSWORD=change-me JWT_SECRET=dev \
  PYTHONIOENCODING=utf-8 \
  ../.venv/Scripts/python.exe manage.py <команда>
```

`PYTHONIOENCODING=utf-8` обязателен: без него русский вывод в консоли Windows
превращается в мусор.

## Чек-лист

- Тесты не идут — проверьте интерпретатор (`backend/.venv`) и публикацию порта.
- Контейнер БД не поднимается по порту — смотрите резервации WinNAT.
- Перезапуск БД — только через compose, не `docker restart`.
- Новый FK — убедитесь, что он не ведёт в чужой домен.
