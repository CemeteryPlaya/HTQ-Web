# Мультикомпанейность — что осталось незакрытым

**Дата:** 2026-08-28
**Ветка:** `structure-refactoring`
**Спека:** [multi-company-tenancy-design.md](multi-company-tenancy-design.md)
**План (выполнен):** [../docs/plans/2026-08-27-multi-company-tenancy-core.md](plans/2026-08-27-multi-company-tenancy-core.md)

Подпроект 1 «Ядро тенантности» выполнен: 18 задач, 4545 тестов проходят, регрессий
относительно состояния до работ нет. Итоговое ревью ветки нашло три Critical — все
три оказались **дырами между задачами**, которых не видела ни одна задачная
проверка. Две из них закрыты; остальное собрано здесь.

Документ существует потому, что часть найденного требует **решений**, а не правок,
и потому что часть пунктов делает платформу неработоспособной после переноса
боевых данных. Читать до запуска `tenancy_bootstrap` на бою.

## Блокирует запуск на бою

### 1. Задачи Celery не переведены на контекст компании — ЗАКРЫТО

См. `.superpowers/sdd/2026-08-27-multi-company-tenancy-core/followup-a-report.md`.
Все три носителя переведены на шаблон «диспетчер + веер»: `sync_identity`,
`task_deadline_reminder`, `calendar_event_reminder` помечены `@company_task`,
рядом заведены диспетчеры (`sync_identity_dispatch`,
`task_deadline_reminder_dispatch`, `calendar_event_reminder_dispatch`), beat
переключён на них миграциями `hr/0020_sync_identity_dispatch_periodic_task` и
`tasks/0019_tasks_periodic_tasks_use_dispatchers` (обе — в
`SHARED_EFFECT_MIGRATIONS`). Мета-тест
`apps/core/tests/test_invariants.py::test_tenant_app_tasks_use_company_task_or_are_marked_dispatchers`
падает в CI на любой tenant-задаче без `@company_task`/`@company_dispatch_task`.
Ниже — исходная постановка, оставлена для истории.

`grep` по `htqweb.tenancy` в `apps/{hr,tasks,contracts,signoff}` даёт ноль
совпадений. После `tenancy_bootstrap` тенантных таблиц в `public` нет, а у задач
Celery нет HTTP-запроса, значит контекст компании пуст и `search_path = public`.

Ломается:

| Задача | Расписание | Последствие |
|---|---|---|
| `apps/hr/tasks.py::sync_identity` | ночью | `ProgrammingError` на `hr_employee` |
| `apps/tasks/tasks.py::task_deadline_reminder` | ежечасно | напоминания о сроках прекращаются для всей платформы |
| `apps/tasks/tasks.py::calendar_event_reminder` | каждые 5 минут | напоминания о встречах прекращаются |

При этом механизм построен (`htqweb/tenancy/celery.py::company_task`), а
`backend/README.md` правило 12 уже требует его применять — но ни один носитель на
него не переведён.

**Шаблон решения — «диспетчер + веер»:** beat планирует диспетчерскую задачу без
компании; она читает `active_company_slugs()` и ставит по одной реальной задаче на
компанию, передавая `company_slug` **именованным** аргументом; реальная задача
помечена `@company_task`. Сбой на одной компании не отменяет остальные.

Плюс расширить мета-тест в `apps/core/tests/` — сегодня он проверяет только
`require_service` первой строкой. Задача tenant-аппки без `@company_task` обязана
падать в CI, а не на бою.

### 2. Обновление токена игнорирует компанию запроса — ЗАКРЫТО

См. `.superpowers/sdd/2026-08-27-multi-company-tenancy-core/followup-b-report.md`.
`issue_token_pair` принимает необязательный `company_slug`; `refresh_token` берёт
`request.company`, проверяет членство через новый предикат
`apps.companies.interface.user_may_enter_company(user_id, slug)` и **отказывает
403 `{"detail": "Forbidden"}`**, если пользователь в компании не состоит, — вместо
молчаливого отката на компанию по умолчанию. Заголовка нет — поведение прежнее
(компания по умолчанию).

Ту же дыру нашли и во второй двери: `obtain_token` (вход по паролю) звал
`issue_token_pair(user)` без компании, и пользователь на поддомене, отличном от
его компании по умолчанию, не мог войти вообще — 403 на первый же запрос, без
спасительного обмена по refresh (тот срабатывает только на 401). Общая для обеих
вьюх логика вынесена в `apps.users.views._company_slug_for_token(request,
user_id)`. Ниже — исходная постановка первой находки, оставлена для истории.

`apps/users/views.py::refresh_token` зовёт `issue_token_pair(user)`, который берёт
`default_company_slug(user.id)`. Заголовок `X-HTQ-Company` до вьюхи доходит (nginx
ставит его и на `/token/refresh`), но на выдаваемый claim не влияет.

Последствие: пользователь с членством в `kz` (по умолчанию) и `uz` переходит на
`uz.` — фронт меняет refresh-cookie на access и получает токен с `company: "kz"`,
затем 403 от `htqweb/http.py`. Одна повторная попытка даёт то же. **Пользователь
заперт в компании по умолчанию.**

Это ровно тот сценарий, ради которого §9 спеки вводила cookie на родительском
домене: механизм переноса cookie сделан верно, второй конец обмена — нет.

Решение: при выпуске токена учитывать компанию запроса, **если пользователь в ней
состоит**. Проверка членства обязательна — без неё это дыра.

## Требует проектного решения

### 3. Бизнес-метрики tenant-аппок после переноса данных

`apps/tasks/metrics.py::collect()` вызывается из `apps/core/metrics.py` в
Celery-задаче без контекста компании. После переноса данных упадёт, сборщик поймает
падение через `fallback`, в проде режим `log` — и метрики домена **тихо исчезнут с
дашборда навсегда**, оставив только строку `FALLBACK` в Loki раз в минуту.

Развилка: агрегировать по группе или лейблировать по компании. Второе информативнее,
но меняет форму метрик и дашборды. Правкой не закрывается — нужно решение.

### 4. Архивная компания: 404 против «только чтение»

Спека противоречит сама себе, и код следует одной из версий:

- §6: «архивный slug → 404 до всякой аутентификации» — так и сделано
  (`company_context.py`);
- требование заказчика: архив это **только чтение**, данные остаются доступны.

Реализовано «недоступна вовсе». Кроме того, пересборка сводных представлений при
архивации не вызывается (кода архивации нет вовсе, `status` правится через админку),
поэтому строки архивированной компании **остаются в сводках холдинга** до
следующего `migrate_companies`.

Относится к подпроекту 4 (жизненный цикл), но решить надо раньше: подпроект 4 будет
строиться на этой предпосылке.

## Известные ограничения, названные явно

### 5. Пост-bootstrap рантайм не исполнялся нигде

Все 4545 тестов идут на раскладке **до** переноса данных: тенантные таблицы в
`public`. Ни один разработчик и ни один тестовый стек не может пройти путь
«поддомен → заголовок → схема» целиком, потому что прокси Vite не ставит
`X-HTQ-Company`, а сервиса `nginx` в тестовых compose-файлах нет вовсе — он только
в `docker-compose.yml` под профилем `production`.

Следствие: поведение платформы после `tenancy_bootstrap` выведено по коду, а не
наблюдением. Перед боевым запуском стоит собрать стенд, где этот путь проходится.

### 6. `companySwitch` на фронте не подключён

`frontend/src/lib/auth/companySwitch.ts` экспортирует `companyFromHost` и
`switchCompany`; за пределами собственных тестов их никто не вызывает. Переключателя
компании в интерфейсе нет — по плану это подпроект 2.

Значит регулярка, существующая ради согласования с nginx, сегодня не участвует ни в
одном пути выполнения, и расхождение с шлюзом не обнаружится на живом трафике.

### 7. Схема `holding` собирается, но не читается

`use_holding()` не вызывается нигде, кроме тестов; `managed=False`-моделей поверх
представлений в ветке нет — читатели это подпроекты 2-3. Цена уже платится
(представления блокируют contract-миграции, пересборка идёт на каждом
`migrate_companies`), выгоды пока нет.

## Рантбук первого запуска на бою

Порядок, выведенный из кода. Шаги 4-5 сегодня **не работают** без закрытия
пунктов 1-2 выше.

1. Выставить `RUN_MIGRATIONS=0` **явно**. `docker-compose.yml` даёт дефолт `1`
   (`${RUN_MIGRATIONS:-1}`), и ни один `.env` в репозитории его не переопределяет.
2. `manage.py tenancy_bootstrap --slug <slug> --name "..." --kind holding --dry-run`
   — проверяет наличие таблиц в `public`, свободу схемы и валидность слага, ничего
   не меняет.
3. Боевой прогон той же команды без `--dry-run`. Одна транзакция, `ALTER TABLE ...
   SET SCHEMA` — правка каталога, данные не копируются; простой равен длительности
   блокировки `ACCESS EXCLUSIVE`, то есть секундам. `--grant-all` включён по
   умолчанию и заводит членство всем активным пользователям.
4. Перезапуск контейнеров. `docker-entrypoint.sh` зовёт `migrate_shared`, тенантные
   таблицы в `public` не воскресают.
5. Перевод пользователей на поддомены. **Требует HTTPS** — refresh-cookie объявлена
   `Secure`. `infra/nginx/tls.conf.example` теперь несёт маршрутизацию по компании,
   но wildcard-сертификат нужен через **DNS-01**: HTTP-01, на который настроен
   certbot, wildcard не выдаёт.

### Аварийная ситуация, которую надо знать

Если `company.delete()` в откате `company_create` упадёт после успешного
`drop_schema`, останется активная строка реестра **без физической схемы**. После
этого `rebuild_holding_views` падает на `CREATE VIEW ... FROM co_x.hr_employee`, и
сводки холдинга не восстановить, пока строку не удалить руками.

Лечение: удалить строку `Company`, повторить `manage.py migrate_companies`.

## Двадцать отложенных мелких находок

Все двадцать разобраны итоговым ревью и признаны не блокирующими слияние. Две из
них взяты в волну правок (`--plan` лгал про обратное направление, `--dry-run`
ничего не проверял). Остальные — в истории ревью; ни одна не меняет поведения,
которое кто-то мог бы принять за правильное.
