# Подпроект 2 — Доступ и роли

Дизайн второй стадии мультикомпанейности. Опирается на
[multi-company-tenancy-design.md](multi-company-tenancy-design.md) (подпроект 1,
выполнен) и заменяет одно из зафиксированных там решений — см. §1.

---

## 1. Что меняется относительно подпроекта 1

Подпроект 1 зафиксировал решение **«Роль = должность из HR»**. Заказчик его
отменил: роль становится **самостоятельной сущностью** с собственным весом и
иерархией подчинения, редактируемой через диаграмму.

Это не косметическая правка. Следствия:

- должность (`hr.Position`) перестаёт быть носителем прав и остаётся тем, чем
  является в кадровом учёте — записью штатного расписания;
- появляется связь «сотрудник → роль», независимая от должности;
- существующий механизм уровней HR (`LevelThreshold`, ручка
  `hr/v1/employees/hr-level/`, флаги `can_*`) становится частным случаем нового
  и **обязан быть на него переведён**. Оставить оба — значит получить тот самый
  параллельный RBAC, который дизайн подпроекта 1 прямо запрещает.

§3 исходного документа правится соответствующей строкой; здесь это отмечено,
чтобы расхождение не всплыло позже как «в дизайне написано иначе».

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Носитель прав | Отдельная сущность `Role` с весом и иерархией подчинения |
| Редактирование иерархии | Диаграмма в стиле оргструктуры: переподчинение и обмен местами |
| Гранулярность прав | Грубые уровни на модуль: `none` / `read` / `write` / `admin` |
| Не-сотрудники | Грант на компанию поверх `CompanyMembership` |
| Область видимости | Компания / отдел / объект |

## 3. Что уже написано и переиспользуется

Две вещи не надо строить заново — это определяет объём работ сильнее всего
остального.

**Диаграмма.** `frontend/src/components/hr/OrgChart/` построена на
`@xyflow/react` + `@dagrejs/dagre` и уже умеет ровно то, что просит заказчик:
перетаскивание связей через `Handle` с диалогом подтверждения
(`ConnectDialog`), панель редактирования (`OrgEditPanel`), перенос подчинённых
(`TransferSubordinatesDialog`), раскладку (`useOrgLayout`), мутации
(`useOrgEditMutations`), экспорт в SVG. Редактор ролей — второй экземпляр этого
семейства с другим источником данных, а не новая диаграмма.

**Модель уровней.** `hr-level` уже отдаёт уровень, область (`scope_department_id`)
и набор возможностей. Формат обкатан, фронт умеет его потреблять
(`useHRLevel`). Новая модель обобщает его, а не заменяет чужой конструкцией.

## 4. Мёртвый код, который стадия удаляет

`frontend/src/lib/auth/roles.ts` объявляет словарь ролей — `hr_manager`,
`senior_hr`, `junior_hr`, `senior_manager`, `junior_manager`, `editors`,
`employee`. **Бэкенд не выдаёт ни одну из этих строк никогда:**
`apps/users/services/profile_service.py::roles_for` возвращает ровно
`admin` (superuser), `staff` (is_staff) или `user`.

То есть все ветки, опирающиеся на богатый словарь, недостижимы, а фактический
доступ сегодня определяется двумя булевыми флагами Django плюс проверкой
«у пользователя есть отдел и должность». Стадия 2 удаляет словарь целиком —
это не рефакторинг ради чистоты, а устранение источника ложной уверенности:
код выглядит так, будто ролевая модель есть.

## 5. Модель данных

### 5.1 Где живут роли

Новая аппка **`apps.access`**, добавляется в `settings.TENANT_APPS`. Роли
принадлежат компании, поэтому лежат в `co_<slug>` и, как все тенантные модели,
**не содержат столбца компании** — изоляцию обеспечивает `search_path`.

Обязательства тенантной аппки из подпроекта 1 действуют полностью:
`apps/access/holding.py` с `HOLDING_MODELS`, участие в `migrate_companies`,
expand/contract при любом изменении схемы.

### 5.2 Сущности

```
Role                      (co_<slug>.access_role)
  code            slug, уникален в компании   — на него ссылаются гранты
  title           отображаемое имя
  weight          int, вес в иерархии
  parent          self-FK, null у корня
  is_system       защита от удаления служебных ролей

RoleModulePermission      (co_<slug>.access_rolemodulepermission)
  role            FK Role
  module          строка из реестра модулей
  level           none | read | write | admin
  уникальность    (role, module)

RoleAssignment            (co_<slug>.access_roleassignment)
  employee_id     int, «мягкая» ссылка в apps.hr — без FK, по правилу
                  «никаких междоменных FK»
  role            FK Role
  scope_kind      company | department | site
  scope_id        int | null   (null только при scope_kind=company)
```

`CompanyMembership` (`public`, `apps.companies`) получает три необязательных
поля: `role_code`, `scope_kind`, `scope_id`.

**Ссылка по коду, а не по FK — вынужденно и намеренно.** `CompanyMembership`
живёт в `public`, `Role` — в схеме компании; внешний ключ поперёк схем
невозможен. Разрешение гранта означает «войти в контекст компании и найти роль
по коду». Это тот же приём, что уже применяется для междоменных ссылок.

### 5.3 Реестр модулей

`level` выдаётся на модуль; список модулей — существующий `KNOWN_SERVICES`
из `apps/core/services.py`. Отдельного справочника не заводим: разъехавшиеся
списки модулей — предсказуемый источник расхождений.

## 6. Иерархия: что она задаёт, а что нет

**Иерархия ролей определяет область подчинения, а не наследование прав.**

Родительская роль **не получает** автоматически права дочерних. Права каждой
роли заданы явно в `RoleModulePermission`.

Причина. Наследование выглядит естественно («начальник может всё, что
подчинённый»), но на трёхуровневой структуре холдинга оно немедленно ломается:
директор регионального общества оказывается родителем ролей сервисных компаний
и молча получает кадровый администраторский доступ в КУП, СЭС и СТЗЭР. Права,
приезжающие в роль сами собой, невозможно ни увидеть на диаграмме, ни
проверить глазами.

Иерархия используется для:
- **области видимости**: `scope_kind=department` плюс подчинённые роли дают
  ответ на вопрос «чьи данные мне видны»;
- **отображения** на диаграмме;
- **сортировки** по весу.

Это самое вероятное место расхождения ожиданий с заказчиком, поэтому в
интерфейсе редактора рядом с деревом должна стоять явная подпись: связь — это
подчинение, а не передача прав.

## 7. Операции над иерархией

**Переподчинение** (`PATCH role/<id>` с новым `parent`) обязано отвергать циклы.
Проверка на стороне сервиса и ограничением в БД, не в интерфейсе: диаграмма —
не единственный вход, есть ещё API и админка.

**Обмен местами** — **одна атомарная операция** `POST roles/swap`, а не два
последовательных редактирования. Два отдельных `PATCH` проходят через состояние,
где обе роли имеют одного родителя либо образуют цикл; при обрыве между ними
дерево остаётся сломанным. Ровно та же логика, по которой `migrate_companies`
сносит и пересобирает представления одной командой.

**Удаление роли** с подчинёнными — по образцу `TransferSubordinatesDialog`:
либо перенос подчинённых на родителя, либо явный отказ. Молчаливое осиротение
ветки недопустимо.

## 8. Разрешение прав

```
permission_level(user, module, company) -> none | read | write | admin
```

Порядок:

1. `is_superuser` — `admin` на всё. Платформенный оператор; нужен для поддержки.
2. Нет контекста компании → только платформенные флаги. Прикладные права
   вычислить нельзя, и подставлять «по умолчанию» их запрещено — это ровно тот
   молчаливый откат, против которого написан `htqweb/fallback.py`.
3. Есть `Employee` в этой компании → объединение уровней его `RoleAssignment`
   (максимум по каждому модулю).
4. Нет `Employee`, но есть `CompanyMembership.role_code` → уровни этой роли.
5. Иначе — `none`.

Вход — `apps.access.interface.permission_level()`; прямые импорты моделей из
других аппок запрещены, как и везде.

**Гейт в `api_view`.** Декоратор получает `module=` и `level=`; резолвинг —
через интерфейс, ленивым импортом внутри функции, иначе `apps.access`, чьи
вьюхи сами декорированы `api_view`, даст циклический импорт на старте.

**`is_staff` меняет смысл.** Сегодня он через `roles_for` попадает в
`ELEVATED_ROLES` и `HR_ROLES` фронта, то есть даёт прикладной доступ. После
стадии 2 он означает только «платформенный админ» для `api_view(admin=True)`.
Изменение поведения заметное, его надо проговорить с заказчиком до выкатки.

## 9. Область видимости

`scope_kind` ∈ `company | department | site`.

- `company` — вся компания;
- `department` — свой отдел (уже реализовано в HR как `scope_department_id`);
- `site` — стройплощадка/объект из `apps.tasks`.

Область **сужает** данные, но не расширяет права: `write` на `department`
означает запись только в своём отделе.

⚠️ **Объектная область — самая дорогая часть стадии.** Фильтр по объекту
придётся протащить через весь домен задач: задачи, роудмапы, ежедневные отчёты,
отчёты по персоналу, потребности в ресурсах, технику. Если объём стадии
окажется велик, разумная точка разреза — выпустить `company`/`department`
первыми, `site` — вторым шагом; модель это допускает, `scope_kind` расширяемо.

## 10. Перевод существующего HR

Четыре уровня HR ложатся на новую модель без потери различий:

| Уровень | Модуль `hr` | Область | Покрывает флаги |
|---|---|---|---|
| junior | `read` | department | чтение своего отдела |
| middle | `write` | department | `+ can_write_basic` |
| senior | `write` | company | `+ can_read_all`, `can_create_employee`, `can_transfer_employee` |
| lead | `admin` | company | `+ can_delete_employee`, управление учётками |

Это проверялось отдельно: опасение, что грубые уровни не выразят нынешние
`can_*`, не подтвердилось — различия сводятся к паре «уровень × область».
Разрушающие операции ложатся на `admin`, создание и перевод — на `write`
с областью компании.

`hr-level` остаётся тонким адаптером над новой моделью на время перехода и
**удаляется в этой же стадии**. Адаптер, переживший свою стадию, и есть тот
второй RBAC, которого нельзя допустить.

## 11. Фронтенд

1. **Удалить** словарь ролей из `roles.ts` вместе со всеми функциями, которые
   на нём построены.
2. **`RequireAuth`** переходит с `requiredRole: string` на пару «модуль +
   уровень». 45 маршрутов в `routeDefinitions.ts` перекладываются:
   `hr` → `hr:read`, `editor` → `cms:write`, `admin` → `<модуль>:admin`
   по принадлежности маршрута.
3. **Профиль** отдаёт карту «модуль → уровень» и область; `useHRLevel`
   заменяется общим `usePermissions`.
4. **Навигация** скрывает пункты по уровню `none`. Скрытие в меню — удобство,
   а не защита: гейт остаётся на бэкенде.
5. **Редактор ролей** — новая страница на компонентах `OrgChart`:
   дерево ролей, перетаскивание для переподчинения, обмен местами, панель
   выставления уровней по модулям.

## 12. Тестирование

- изоляция аппок (`test_app_isolation`) — `apps.access` не импортируется
  напрямую ниоткуда, кроме своего интерфейса;
- наличие `apps/access/holding.py` с `HOLDING_MODELS`;
- отказ на цикле при переподчинении, включая попытку через API в обход UI;
- атомарность обмена местами: прерывание в середине не оставляет сломанного дерева;
- матрица `permission_level` по всем пяти веткам §8, включая «нет контекста компании»;
- сужение выборок областью: сотрудник с `department`-областью не видит чужой отдел;
- грант не-сотруднику: пользователь без `Employee` в компании получает права из членства;
- **тест-сторож**: ни один маршрут во фронте не ссылается на строку роли,
  которой бэкенд не выдаёт. Именно отсутствие такой проверки позволило
  словарю из §4 годами выглядеть работающим.

## 13. Риски

1. **Отмена решения подпроекта 1** — правка §3 исходного дизайна обязательна,
   иначе документы противоречат друг другу.
2. **Два механизма во время перехода.** HR-уровни и роли сосуществуют внутри
   стадии. Снимается только удалением адаптера до её завершения.
3. **Смена смысла `is_staff`** (§8) — поведенческое изменение для действующих
   учёток, требует согласования.
4. **Объектная область** (§9) — основной кандидат на выход за оценку.
5. **Ожидание наследования прав по иерархии** (§6) — расхождение с заказчиком
   вероятнее прочих; закрывается подписью в интерфейсе и явной проверкой на
   демонстрации.

## 14. Чего стадия не делает

- `CompanyModule` и гейты модулей на компанию — подпроект 3;
- жизненный цикл компании, банкротство, преемник — подпроект 4;
- «архив — только чтение» — подпроект 4;
- третий режим для `media_files` и `mail` (общая таблица, обязательный
  столбец-владелец, принудительный фильтр) — упомянут в подпроекте 1 как
  относящийся сюда, но требует модели доступа как предусловия;
  выносится в конец стадии отдельным шагом и первым идёт под нож при нехватке
  объёма.
