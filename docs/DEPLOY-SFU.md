# Деплой видеоконференции (SFU) в продакшен

Пошаговый чеклист с проверкой после каждого шага. Порядок не случайный:
каждый следующий пункт бессмысленно проверять, пока не сделан предыдущий.

Симптомы в правой колонке — то, что вы увидите, если пункт пропустить. Все
они выглядят одинаково («не работает видео») и различаются только деталями,
поэтому проверяйте по порядку, а не по догадке.

| # | Шаг | Если пропустить |
|---|---|---|
| 1 | `WEBRTC_ANNOUNCED_IP` = публичный IP | контейнер `sfu` не стартует вовсе |
| 2 | Порт `44444` UDP **и** TCP открыт | участники видят друг друга в списке, но экран чёрный |
| 3 | HTTPS с валидным сертификатом | камера не включается ни у кого: браузер не даёт `getUserMedia` |
| 4 | TURN-сервер | внутри одной сети работает, между разными — нет |

---

## 1. Публичный адрес медиа-сервера

```bash
# в корневом .env
WEBRTC_ANNOUNCED_IP=<публичный IP сервера>
WEBRTC_SERVER_PORT=44444
```

Это адрес, который SFU кладёт в ICE-кандидаты — «подключайтесь ко мне сюда».
Должен быть тем, по которому сервер виден клиентам. Не доменом, а именно IP.

При пустом значении контейнер падает на старте **намеренно**: с wildcard
`listenIp` и пустым announced клиенты получили бы `0.0.0.0` и вечный чёрный
экран, который отлаживают часами. Явный отказ при старте дешевле.

**Проверка:**
```bash
docker compose --profile production up -d sfu
docker compose logs sfu | grep "announced as"
# ждём: WebRtcServer bound on 0.0.0.0:44444 (UDP+TCP) announced as <ваш IP>
```

## 2. Firewall

```bash
# порт медиа — ОБА протокола
sudo ufw allow 44444/udp
sudo ufw allow 44444/tcp
sudo ufw allow 443/tcp
sudo ufw allow 80/tcp     # нужен certbot для выпуска сертификата
```

UDP и TCP оба: mediasoup пробует UDP, при блокировке откатывается на TCP.
Открытый только один из них даёт «у части участников не работает» —
у тех, чья сеть режет оставшийся.

**Проверка снаружи сервера:**
```bash
nc -vzu <публичный IP> 44444    # UDP
nc -vz  <публичный IP> 44444    # TCP
```

## 3. HTTPS

Без него видеоконференции не будет: браузеры дают доступ к камере и микрофону
только в защищённом контексте, и `http://` (кроме `localhost`) не подходит.

```bash
# 1) домен направлен на сервер, в .env:
SERVER_DOMAIN=conf.example.com

# 2) поднять стек — nginx уже отдаёт /.well-known/acme-challenge/
docker compose --profile production up -d

# 3) выпустить сертификат
docker compose exec certbot certbot certonly --webroot \
  -w /var/www/certbot -d conf.example.com --email you@example.com --agree-tos

# 4) включить TLS-конфиг (пошагово — в шапке файла)
cp infra/nginx/tls.conf.example infra/nginx/tls.conf
sed -i 's/ВАШ_ДОМЕН/conf.example.com/g' infra/nginx/tls.conf
# примонтировать его в nginx (docker-compose.yml, рядом с default.conf):
#   - ./infra/nginx/tls.conf:/etc/nginx/conf.d/tls.conf:ro
docker compose restart nginx
```

Основной `default.conf` слушает только `:80` — блок 443 вынесен отдельно,
потому что без сертификата nginx с ним не стартует.

**Проверка:**
```bash
curl -sI https://conf.example.com/ | head -1        # ждём 200
curl -s https://conf.example.com/api/core/v1/services/ | grep -o '"conference": [a-z]*'
```

## 4. TURN

STUN (два публичных Google зашиты в настройках) лишь сообщает клиенту его
внешний адрес. Когда обе стороны за **симметричным NAT** — мобильный
интернет, корпоративные сети со строгим firewall — прямой путь для медиа не
находится. Внутри одной сети всё работает, между разными — нет. Это и есть
«у части участников чёрный экран».

Свой coturn или платный сервис (Twilio, Metered, Xirsys):

```bash
# в .env
TURN_URLS=turn:turn.example.com:3478?transport=udp,turns:turn.example.com:5349
TURN_USERNAME=<логин>
TURN_CREDENTIAL=<пароль>
docker compose restart backend-web
```

**Проверка — TURN доехал до фронта:**
```bash
TOKEN=<access-токен любого пользователя>
curl -s https://conf.example.com/api/cms/v1/conference/config \
  -H "Authorization: Bearer $TOKEN" | python -m json.tool
# в ice_servers должна появиться запись с turn: и username
```

**Проверка, что TURN реально ретранслирует** — https://icetest.info или
Trickle ICE от Google: вставьте свой TURN, нажмите Gather candidates. Должны
появиться кандидаты типа `relay`. Нет `relay` — TURN не работает, и между
сетями связи не будет, сколько бы ни было `srflx`.

## Итоговая проверка

Два участника **из разных сетей** (например, один по Wi-Fi офиса, второй с
мобильного интернета — не с того же Wi-Fi). Проверка с двух вкладок одного
компьютера ничего не доказывает: там медиа идёт по localhost и работает даже
при полностью сломанном NAT-обходе.

Что смотреть, если не видно картинки:
```bash
docker compose logs -f sfu     # подключился ли участник вообще
```
`Client connected: … user=<логин>` есть, а видео нет → медиа-путь (пункты 1, 2, 4).
Записи нет вовсе → сигналинг (пункты 3 и JWT: `JWT_SECRET` у SFU обязан
совпадать с Django, иначе 401 на WS-upgrade).

В браузере: `chrome://webrtc-internals` → вкладка со встречей → смотрите
выбранную пару кандидатов. `relay` означает, что работает TURN; отсутствие
любой выбранной пары — медиа не прошло.

## Чего в этом контуре пока нет

- **Своего TURN в compose.** Пункт 4 предполагает внешний сервер. Поднять
  coturn рядом — отдельная задача (свой порт, свои креды, свой сертификат).
- **Записи встреч и шеринга экрана в проде** — не проверялись под нагрузкой.
- **Масштабирования.** `MEDIASOUP_WORKERS=1` — один воркер на все комнаты.
  Ориентир mediasoup — ~500 потоков на воркер, но реальный потолок зависит от
  битрейта; при росте нагрузки поднимайте по числу ядер.
