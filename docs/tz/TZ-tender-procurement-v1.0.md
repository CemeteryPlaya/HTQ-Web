# HTQ-Web: тендерный модуль закупок (аппка tender) — требования и план

Oct 6, 2026 · @Sanzhar

## Свод и принятые решения

Тендерный модуль закупок — новая отдельная аппка `tender`, не часть БЗО. Закупщик создаёт в ней заявку на закуп (проект и статья указываются сразу), рассылает её поставщикам по персональным ссылкам, сравнивает предложения с учётом доставки и СМР, ТД (или другое уполномоченное лицо) проверяет качество, ФД утверждает выбор. Дальше закупка передаётся в БЗО на договор и оплату, а тендерный модуль ведёт доставку, приёмку и закрытие.

Что было надиктовано:

- Заявка на закуп со списком позиций; несколько текущих контрагентов с почтами; каждому — письмо с индивидуальной ссылкой.
- На странице по ссылке поставщик предлагает цену, срок поставки и доп. условия, на все позиции или только часть.
- Ссылка именная и после первого открытия привязана к устройству; телефон или компьютер — без разницы.
- Известных поставщиков мало, потенциально заинтересованных больше — нужно расширять круг участников.
- Выбранное уходит в модуль договоров, согласований и оплат (БЗО): договор с поставщиком, затем оплата бухгалтером после всех согласований.
- После оплаты — «В доставке»; получив товар, закупщик закрывает заявку закрывающими документами.
- Режим работы — тендерная система.

**Решения 06.10 по вопросам первой редакции:**

| № | Вопрос | Решение |
| --- | --- | --- |
| 1 | Откуда берётся заявка | Создаётся в тендерном модуле; запрос цен — только после утверждения заявки (умолчание) |

| 3 | Обязательно ли самый дешёвый | Нет; выбор не минимальной цены — с комментарием. Сравнение по полной стоимости: товар + доставка + СМР, если они есть |
| 4 | Проект и статья | 1 заявка = 1 проект. Статья указывается закупщиком при создании; обычно одна, допускаются разные по позициям |

## Место в архитектуре

`apps.tender` — новая тенантная аппка со своим сервисом `tender` в `KNOWN_SERVICES`, API `/api/tender/v1/`, своими узлами прав и разделом `/tender` во фронте. С БЗО она общается только через `apps.bpp.interface`, в одну сторону: tender знает про bpp, bpp про tender не знает.

| Аппка | Что tender берёт | Через что |
| --- | --- | --- |
| `project` | Проект заявки, участники, руководитель | `project.interface.project_brief`, `search_projects`, `is_member` |
| `refdata` | Статьи, ед. изм., валюты, курсы НБРК, ставка НДС, МРП | `refdata.interface` (`article_brief`, `uom_brief`, `exchange_rate`, `vat_rate`, `mrp`) |
| `bpp` | Реестр контрагентов, остаток бюджета статьи, передача закупки, статусы договоров и счетов | `bpp.interface`: существующие `counterparty_brief`, `search_counterparties` + новые функции (ниже) |
| `signoff` | Маршруты «Заявка на закуп» и «Выбор поставщика» | `register_subject`, `start_process`, флаги маршрутов БЗО |
| `hr` | Кто проверяет качество: ТД или уполномоченное лицо по должности | `hr.interface.resolve_position_users` |
| `notifications` | Колокольчик, e-mail, Telegram внутренним пользователям | `notify`, `register_digest_source` |
| `files` | ТЗ и чертежи заявки, КП поставщиков, накладные, акты приёмки | `files.interface.register_owner` + ClamAV |
| `mail` | Исходящие письма поставщикам с `tender@htq.group` | SMTP mailcow (`apps.mail.services.sender`) |

**Ключевой стык с БЗО.** В main строки договора (`AgreementItem`) и счёта (`InvoiceLine`) ссылаются на `PurchaseRequestItem` через `PROTECT`, а «задействовано» по бюджету (CALC-002) считается от позиций заявок `bpp`. Поэтому передать в БЗО «голую» закупку нельзя — нужна заявка `bpp` под ней. Два варианта:

- **Вариант A (принят 06.10).** Заявку закупщик создаёт и ведёт в интерфейсе тендерного модуля. При «Отправить на согласование» tender через `bpp.interface` создаёт под ней заявку ЗЗ (проект, статья, позиции, плановые цены, `source="tender"`, номер тендера) и запускает её штатный маршрут ТД → ОД. Согласование одно, проверка и резерв бюджета штатные (BR-011, CALC-002), статус заявки в tender повторяет статус ЗЗ. После выбора поставщика договоры и счета создаются из позиций этой ЗЗ через мастер F-03 с ценами победителя; превышение над планом проверяется штатно (BR-043, BR-034). БЗО меняется минимально: несколько функций интерфейса и поле источника, без правок расчётов.
- **Вариант A′.** Создавать ЗЗ только после выбора победителя, уже утверждённой (`preapproved`). Минус: между утверждением заявки и выбором бюджет не зарезервирован — две закупки могут занять один остаток.
- **Вариант B.** Разрешить строки договора и счёта без позиции заявки. Это переписывает CALC-002, план закупок и сверку — зона Руслана и утверждённые Алгазы правила. Не рекомендуется.

Для варианта A в `bpp.interface` добавляются: `submit_request_from_tender(...)` — создать и отправить ЗЗ; `request_status(ids)`; `create_documents_from_tender(...)` — черновики договоров и счетов из позиций ЗЗ; `documents_status(request_ids)` — статусы договоров, счетов, оплат и закрывающих; `budget_available(project_id, article_id)` — подсказка об остатке ещё в черновике; budget\_articles(project\_id) — статьи бюджета проекта для выбора, в том числе для доставки и СМР; `create_counterparty_from_prospect(...)` — новый поставщик становится контрагентом. Позиции ЗЗ из тендера скрываются из обычного Плана закупок, чтобы СН не оформил их мимо тендера. Контрагенты в БЗО — зона исполнителя A (Санжар); изменения заявки и мастера F-03 — согласовать с Русланом.

В идеале стык между аппками — внутренний HTTP API (DRF); при нынешней структуре (вызовы `interface.py` в одном процессе) это откладывается. Чтобы потом перейти механически, новые функции `bpp.interface` сразу принимают и возвращают Pydantic-схемы (`apps/bpp/schemas/tender.py`) — без моделей Django и QuerySet, только идентификаторы и простые типы.

Другие правила кодовой базы — как в БЗО: UUID-ключи, деньги `Decimal(18,2)`, ошибки `{"detail","code","fields"}`, `version` и 409, аудит append-only, своя нумерация тендера `ТН-ГГГГ-NNNNNN` (сервис нумерации и аудита из `bpp/services/core` выносится в `apps.core` или копируется — решить в этапе 0).

Закупка живёт в тендерном модуле от заявки до закрытия; в БЗО уходят только согласование заявки с резервом бюджета, договоры, счета и оплаты.

## Функциональные требования

Приоритет: **\[П\]** — пилот, **\[Л\]** — желательно в пилоте, **\[У\]** — после пилота. Роли: Закупщик (СН или ПМ), Проверяющий качество (ТД или уполномоченное лицо), ФД, ГД, Поставщик.

### Заявка на закуп

- **TND-001 \[П\]** Закупщик создаёт заявку в `/tender`: проект (один), статья по умолчанию для всех позиций, позиции (наименование, характеристики, ед. изм., количество, плановая цена, дата потребности, статья — если отличается), адрес поставки, файлы ТЗ и чертежей.
- **TND-002 \[П\]** Признаки заявки: «нужна доставка до объекта», «нужны СМР / монтаж» (с описанием объёма работ); для доставки и для СМР закупщик выбирает отдельные статьи расходов из статей бюджета проекта в БЗО, «аналоги разрешены», «частичные предложения разрешены».
- **TND-003 \[П\]** Подсказка об остатке статьи ещё в черновике; «Отправить на согласование» создаёт ЗЗ в БЗО и запускает маршрут ТД → ОД (вариант A). Отказ, возврат, отмена — как у ЗЗ.
- **TND-004 \[П\]** Если позиции заявки относятся к разным статьям, в БЗО создаётся по одной ЗЗ на статью: в main у ЗЗ одна статья. Доставка и СМР всегда уходят отдельными ЗЗ на свои статьи, СМР — с видом «Работы и услуги».

### Запрос предложений (тендер)

- **TND-010 \[П\]** На утверждённой заявке — «Запросить предложения»: тендер ТН-ГГГГ-NNNNNN с крайним сроком, валютой предложения, желаемой схемой оплаты (раздел «Оплата и доставка»), условиями поставки. Плановые цены поставщикам не показываются.
- **TND-011 \[П\]** Участники: контрагенты БЗО со статусом «Активен» и их контакты (несколько адресов на компанию); потенциальные поставщики по названию и e-mail без БИН \[Л\].
- **TND-012 \[П\]** «Опубликовать» — каждому участнику отдельная ссылка и письмо, статус доставки по каждому. До срока: продлить, добавить участника, отозвать приглашение, отменить тендер с причиной (письма всем).
- **TND-013 \[П\]** Предложения видны только после срока или досрочного закрытия приёма; до этого — счётчики «отправлено / открыто / подано».

### Сравнение и выбор

- **TND-020 \[П\]** Таблица сравнения: позиции строками, поставщики колонками. Отдельными строками — доставка и СМР. Итог по поставщику = товар + доставка + СМР, в KZT с НДС по курсу НБРК на дату вскрытия. Плановая цена и экономия видны.
- **TND-021 \[П\]** Если поставщик предложил не все позиции, итоги сравниваются по общему набору позиций, а покрытие показывается («7 из 10 позиций»). Доставку и СМР частичного предложения нельзя делить пропорционально — она берётся целиком.
- **TND-022 \[П\]** Выбор победителя по каждой позиции; разные поставщики на разные позиции допустимы. Не самый дешёвый по полной стоимости — обязательный комментарий.
- **TND-023 \[П\]** Маршрут `tender.award`: этап «Проверка качества» (ТД или назначенное уполномоченное лицо — по умолчанию ТД по должности, закупщик может заменить на пользователя с ролью tender-quality) → ФД. Этап ГД с порогом суммы в пилоте не ставится — добавляется настройкой маршрута после утверждения с руководством. Проверяющий видит характеристики, аналоги, файлы КП, может вернуть с комментарием.
- **TND-024 \[П\]** После утверждения — письма победителям и тем, кто не выбран; создание черновиков договоров и счетов в БЗО: по одному на поставщика (и на ЗЗ), договор, если сумма > 1000 МРП. Доставка и СМР оформляются отдельными документами по своим ЗЗ и статьям.
- **TND-025 \[Л\]** Переторжка: второй раунд для выбранных участников. Экспорт сравнения в xlsx.

### Поставщик на внешней странице

- **TND-030 \[П\]** Страница по ссылке без входа: заказчик, позиции, условия, схема оплаты, срок, файлы ТЗ.
- **TND-031 \[П\]** По каждой позиции: участвую или нет, цена за ед., количество (не больше запрошенного), срок поставки, комментарий, аналог с описанием (если разрешены).
- **TND-032 \[П\]** Отдельно: стоимость доставки (или «включена в цену»), стоимость СМР (если запрошены) с кратким составом работ, ставка НДС, валюта, срок действия предложения, предлагаемая схема оплаты, доп. условия, файл КП.
- **TND-033 \[П\]** Реквизиты: название, страна, БИН/ИИН, НДС, контакт; для известного контрагента — только чтение. Согласие на обработку персональных данных перед первой отправкой.
- **TND-034 \[П\]** Черновик, отправка, правка и отзыв до срока; каждая отправка — новая версия с историей. Отказ от участия с причиной.
- **TND-035 \[П\]** После срока — только чтение и итог: «Ожидается решение», «Выбрано по позициям …», «Не выбрано», «Отменено».
- **TND-036 \[Л\]** Вопрос заказчику; ответ уходит всем участникам без раскрытия автора.

### Доставка, приёмка, закрытие

- **TND-040 \[П\]** Карточка тендера показывает по каждому поставщику стадию оплаты и доставки (раздел «Оплата и доставка»), данные — из БЗО через `documents_status`.
- **TND-041 \[П\]** «Отметить получение»: дата, количество по позициям (частичная приёмка допустима), сканы накладной, СФ или акта, фото; отметка «Оригиналы переданы в бухгалтерию» (дата, кому). СМР — «Работы приняты» с актом.
- **TND-042 \[П\]** Тендер «Закрыт», когда всё получено и все счета в БЗО «Закрыт». Закрывающие документы, загруженные в tender, автоматически прикладываются к счёту БЗО (типы `waybill`, `act`, `vat_invoice`).

### Расширение круга поставщиков

- **TND-050 \[Л\]** Открытый тендер: публичная страница без цен, где новая компания подаёт заявку на участие; закупщик одобряет — она получает персональную ссылку.
- **TND-051 \[У\]** Категории товаров у поставщиков для подбора участников; рейтинг: доля ответов, выигрышей, срывов сроков.

## Оплата и доставка

Предлагается не один фиксированный момент «В доставке», а схема оплаты у каждого выбранного предложения: доставка разрешена, когда оплачена доля «до отгрузки» из этой схемы. Закупщик задаёт желаемую схему в тендере, поставщик может предложить свою, при выборе фиксируется схема победителя и переносится в договор и счета БЗО.

| Схема | Когда «В доставке» | Счета в БЗО | Закрывающие документы |
| --- | --- | --- | --- |
| 1. Предоплата 100% | После «Оплачено» по счёту | Один счёт с признаком «аванс» | После поставки; в БЗО — штатно, т.к. счёт уже оплачен |
| 2. Аванс X% + остаток после поставки | После оплаты аванса | Счёт-аванс X% и счёт на остаток после приёмки (или один счёт с частичными отметками оплаты) | Накладная после приёмки, до оплаты остатка — см. ниже |
| 3. Постоплата 100%, отсрочка N дней | Сразу после согласования документа (договор «Действует» или счёт «К оплате») | Один счёт, оплата после приёмки, срок = дата приёмки + N дней | Накладная после приёмки, до оплаты — см. ниже |
| 4. Поэтапная (EPC) | После оплаты всех этапов «до отгрузки» | Счёт на каждый этап: аванс, по отгрузке, после СМР, гарантийное удержание | Акты по этапам |

В пилоте — схемы 1–3 готовыми шаблонами; схема 4 (этапы с процентами и событиями «до отгрузки», «по приёмке», «после СМР», «по окончании гарантии») — после пилота, модель данных закладывается сразу.

**Стадии поставки у поставщика в тендере:** Ожидает документов (договор или счёт на согласовании) → Ожидает оплаты для отгрузки → В доставке → Получено частично → Получено → Ожидает окончательной оплаты (если остаток не оплачен) → Закрыто. Условие «В доставке» = оплачено по отметкам БУХ ≥ сумма этапов «до отгрузки»; для схемы 3 эта сумма 0. Поставщик может сам отметить «Отгружено» с датой через свою ссылку \[Л\] — это даёт закупщику ожидаемую дату прибытия.

**Закрывающие документы — после фактической приёмки (трактовка D-13 от 06.10).** Закупщик получает товар вместе с физическими документами (накладная, СФ, акт СМР), отмечает приёмку в тендере, прикладывает сканы и передаёт оригиналы в бухгалтерию. Закрывающие документы появляются после приёмки, независимо от того, когда оплачен счёт.

- **Предоплата 100%.** Приёмка идёт после оплаты — код БЗО уже так работает («Оплачено» → «Ждёт закрывающих»): сканы из тендера сразу уходят на счёт.
- **Аванс и постоплата.** Приёмка раньше полной оплаты. В main проверка прав на файлы счёта (`can_modify_type`) принимает закрывающие только после «Оплачено», поэтому нужна точечная правка БЗО: разрешить типы `waybill`, `act`, `vat_invoice` на счёте, если по нему есть приёмка в тендере (`bpp.interface` получает признак от tender). В пилоте правку не делаем и ждём решения в БЗО: тендер хранит сканы у себя и прикладывает их к счёту автоматически, когда он станет «Оплачено».
- **Основание оплаты остатка.** Бухгалтер видит в карточке счёта отметку «Товар принят <дата>, оригиналы переданы <дата>» — по ней оплачивается остаток при постоплате и при схеме «аванс + остаток».

## Персональная ссылка и привязка к устройству

MAC-адрес из браузера получить нельзя: ни JavaScript, ни HTTP его не передают, а до сервера он не доходит в принципе — меняется на каждом маршрутизаторе. Привязка делается секретом устройства в cookie плюс одноразовым кодом на почту для перепривязки.

1. Ссылка `https://<компания>.htq.group/supplier/<token>`; токен — `secrets.token_urlsafe(32)`, в БД только SHA-256 (как `hr` share-links).
2. GET отдаёт промежуточную страницу с кнопкой «Открыть предложение»: почтовые сканеры (Outlook Safe Links, антиспам) сами открывают ссылки из писем и иначе «съели» бы привязку.
3. По кнопке (POST) сервер выдаёт секрет устройства в cookie `HttpOnly; Secure; SameSite=Strict; Path=/supplier/` на срок тендера + 30 дней; у приглашения хранится только хэш секрета, User-Agent, IP, время.
4. Каждый запрос портала проверяет пару «токен + cookie». Чужое устройство видит «Ссылка уже открыта на другом устройстве» и кнопку «Привязать это устройство».
5. Перепривязка: 6-значный код на e-mail приглашения (10 минут, 5 попыток, 3 отправки в час); старое устройство теряет доступ, событие видно закупщику.
6. Закупщик может сбросить привязку или перевыпустить ссылку (старый токен отзывается).

Отпечаток браузера (fingerprint) замком не делаем: он меняется после обновлений, совпадает у одинаковых телефонов и подделывается — пишем его только в журнал. Ссылка многоразовая по открытиям (поставщик возвращается править предложение до срока); одноразовой является привязка. Устройств на ссылку — 1, настройка до 2. Инкогнито или очистка cookie = новое устройство, лечится кодом.

### Статусы

| Объект | Жизненный цикл |
| --- | --- |
| Заявка | Черновик → На согласовании → Утверждена / На доработке / Отклонена → В тендере → Передана в БЗО → Закрыта; Отменена. «На согласовании» и решения — зеркало ЗЗ в БЗО |
| Тендер | Черновик → Приём предложений → Вскрыт → Проверка качества → Утверждение ФД (и ГД) → Выбор утверждён → Документы в БЗО → Поставка → Закрыт; Отменён, Не состоялся (нет предложений), Возвращён на доработку |
| Приглашение | Создано → Отправлено / Ошибка доставки → Открыто → Подано / Отказ → Выбрано / Не выбрано; Отозвано, Истекло |
| Предложение | Черновик → Подано → Заменено новой версией; Отозвано; после вскрытия — Выбрано полностью / частично / Не выбрано |
| Поставка (по поставщику) | Стадии из раздела «Оплата и доставка» |

Тендер «Не состоялся» или «Отменён» возвращает заявку в «Утверждена»: можно объявить новый тендер или отдать позиции СН в обычный План закупок БЗО.

## API, права, передача в БЗО, безопасность

Два контура: внутренний `/api/tender/v1/` за JWT и узлами `tender.*`, и публичный портал `/api/tender/v1/supplier/<token>/` с `auth=None`, где доступ даёт пара «токен + cookie устройства».

### Внутренний API

| Метод и путь | Назначение |
| --- | --- |
| `GET/POST requests`, `GET/PATCH/DELETE requests/<id>` | Заявки, черновик |
| `POST requests/<id>/submit`, `withdraw`, `cancel` | Отправка (создаёт ЗЗ в БЗО), отзыв, отмена |
| `GET/POST tenders`, `GET/PATCH tenders/<id>` | Тендеры по заявке |
| `POST tenders/<id>/publish`, `extend`, `close-intake`, `cancel`, `new-round` | Жизненный цикл |
| `GET/POST tenders/<id>/invitations`, `…/<inv>/revoke`, `reissue`, `reset-device` | Участники и ссылки |
| `GET tenders/<id>/comparison`, `export` | Сравнение (после вскрытия), xlsx |
| `PUT tenders/<id>/award`, `POST …/award/submit` | Выбор по позициям, старт `tender.award` |
| `POST tenders/<id>/handover` | Черновики договоров и счетов в БЗО |
| `GET tenders/<id>/delivery`, `POST …/receipts` | Стадии поставки, приёмка |
| `GET/POST contacts`, `prospects` | Контакты и потенциальные поставщики |

**Публичный портал:** `GET` (карточка без плановых цен), `POST bind`, `otp/send`, `otp/verify`, `GET/PUT offer`, `POST offer/submit`, `offer/withdraw`, `decline`, `shipped` \[Л\], файлы `offer/files`. Вьюхи — `apps/tender/views_supplier.py`, фронт — `pages/public/SupplierTender.tsx` по образцу `PublicOrgView.tsx`, без общего layout.

### Права и роли

Узлы `apps/tender/access_functions.py`: `tender.requests` (свои — фильтр в сервисе), `tender.tenders`, `tender.tenders.all` (просмотр всех, ФД), `tender.award.quality`, `tender.award.approve`, `tender.prospects`, `tender.receipts`, `tender.settings`. Под-узлы из трёх сегментов получают явные строки у каждой роли (предупреждение CLAUDE.md). Системные роли новой миграции `access`: `tender-buyer` (СН, ПМ), `tender-quality` (ТД; выдаётся и уполномоченным лицам), `tender-fd`, `tender-gd`, `tender-viewer` (БУХ, ОД — просмотр), `tender-adm`. Выдача должностям холдинга — по образцу `bpp_assign_roles`.

### Передача в БЗО

- **Отправка заявки** → `bpp.interface.submit_request_from_tender`: ЗЗ по каждой статье, маршрут ТД → ОД, резерв бюджета. Решения по ЗЗ возвращаются в tender через опрос `request_status` (или слушатель `register_request_listener`, если нужны мгновенные уведомления).
- **Передача выбора** → `create_documents_from_tender`: по поставщику × ЗЗ — договор (если сумма > 1000 МРП или выбран закупщиком) или счёт без договора; цены победителя, схема оплаты, файл КП; доставка и СМР — отдельными позициями.
- **Статусы** → `documents_status`: договор, счета, отметки оплаты БУХ, закрывающие; по ним считаются стадии поставки.
- **Новый поставщик** → `create_counterparty_from_prospect` с реквизитами, которые он ввёл в портале; метка «Проверенный» — по правилам БЗО (D-20).
- **Альтернативы БЗО** к документам из тендера разрешены (решение 8); если документ заменён альтернативой, тендер показывает это у поставщика.

### Безопасность

- Тенант — по поддомену (`X-HTQ-Company`), как сейчас; на поддомене архива портал закрыт через `anonymous_blocked`.
- Rate limit на портал по токену и IP (`htqweb/ratelimit.py`); ClamAV для файлов портала включён обязательно; 20 МБ на файл, 10 файлов на предложение, без xml и исполняемых.
- Портал не раскрывает плановые цены, других участников, их число и цены. Правка после `deadline_at` — 409 по времени сервера.
- POST портала — только `application/json`, проверка `Origin`, cookie `SameSite=Strict`.
- Почта `tender@htq.group`: SPF, DKIM, DMARC обязательны, иначе приглашения уйдут в спам — главная эксплуатационная угроза функции. Outbox + Celery с повторами, учёт bounce.
- Celery beat: закрытие приёма по сроку, напоминание участникам за 24 ч, напоминание закупщику о просроченной поставке, чистка OTP.

## План реализации

Семь этапов; этапы 0–5 дают пилот на холдинге — от заявки в tender до закрытой закупки, этап 6 — расширение круга поставщиков. Пошаговый план с кодом пишется к старту каждого этапа в `docs/plans/`; `STRUCTURE.md`, `CLAUDE.md`, `API.md` обновляются в той же задаче.

1. **Этап 0. Каркас аппки и решения.**
   - `apps.tender`: `apps.py`, `interface.py`, `access_functions.py`, `KNOWN_SERVICES`, `TENANT_APPS`, префикс `/api/tender/v1/`, раздел `/tender` во фронте.
   - Нумерация и аудит: вынести общий код из `bpp/services/core` в `apps.core` или скопировать.
   - Узлы и роли `tender-*`, миграция `access`; закрыть вопросы раздела «Что осталось решить».
   - Приёмка: рубильник выключает аппку (503), `test_app_isolation.py` и `test_gate.py` зелёные.
2. **Этап 1. Заявка и стык с БЗО.**
   - Модели заявки, форма, подсказка остатка; в `bpp.interface` — `submit_request_from_tender`, `request_status`, `budget_available`, поле `source` у ЗЗ, скрытие позиций из Плана закупок.
   - Приёмка: заявка с двумя статьями даёт две ЗЗ; отказ ТД в БЗО виден в tender; остаток бюджета резервируется.
3. **Этап 2. Тендер и участники.**
   - Тендер, схемы оплаты 1–3, `SupplierContact`, `SupplierProspect`, приглашения, публикация без писем (ссылки видны закупщику).
   - Приёмка: заблокированный контрагент не выбирается; одна заявка — один активный тендер.
4. **Этап 3. Портал поставщика.**
   - Токены, привязка устройства, OTP, rate limit, журнал; форма предложения с частичными позициями, доставкой, СМР, версиями; файлы + ClamAV; мобильная вёрстка.
   - Приёмка (pytest + Playwright): второе устройство — отказ; OTP перепривязывает; GET не привязывает; правка после срока — 409; плановая цена не уходит в ответ.
5. **Этап 4. Письма.**
   - `tender@htq.group` в mailcow, SPF / DKIM / DMARC, outbox + Celery, bounce; письма: приглашение, продление, напоминание, отмена, итог.
   - Приёмка: письмо в Gmail, Mail.ru, Yandex не в спам; ошибка доставки видна у приглашения.
6. **Этап 5. Сравнение, выбор, передача, поставка.**
   - Вскрытие по сроку, сравнение по полной стоимости, выбор по позициям, маршрут «Проверка качества → ФД».
   - `create_documents_from_tender`, `documents_status`, `create_counterparty_from_prospect`; стадии поставки, приёмка, передача оригиналов в бухгалтерию, закрывающие на счёт БЗО.
   - Приёмка, сквозной сценарий: заявка → тендер → 2 поставщика по разным позициям, один с доставкой и СМР → проверка ТД → ФД → договор + счёт без договора → аванс 30% → «В доставке» → приёмка → оплата остатка → закрыт.
7. **Этап 6. После пилота.**
   - Открытый тендер и заявки на участие, переторжка, вопросы-ответы, отгрузка от поставщика, схема 4 (этапы EPC), категории и рейтинг поставщиков, английский язык.

Выкатка — по образцу `docs/deploy/bpp-rollout-runbook.md`: репетиция на дампе прода, `migrate_companies`, включение сервиса `tender` только у холдинга. Зависимость: этапы 1 и 5 требуют уже выкаченного БЗО.
