# Выкатка модуля «Бюджет, закупки и оплаты» на все компании группы — ранбук (A6.3)

Модуль выкатывается **всем действующим компаниям сразу, в одном окне** (D-S6-7, D-S6-9) с откатом из бэкапа. Отдельного пилотного этапа нет: в окне каждая компания проходит одни и те же шаги; управляющая компания (`hi-tech-group`) идёт первой как контрольная — на ней же сначала прогоняются дымовые SC-001…SC-006, затем остальные.

**Почему не только управляющей.** После `migrate_companies` (шаг 4) связка «доска задач ↔ „Проект“» (`tasks/0023`–`0024`, `project_link.py`) и «партнёр задач ↔ контрагент модуля» (`tasks/0025`) действует в схеме КАЖДОЙ компании, а экран «Проектов», контрагентов и права на них (роли `bpp-*`) есть только в модуле `bpp`. Компания без модуля не может завести доску задач (доска создаётся выбором «Проекта»), поменять название и сроки доски (409: правятся только в «Проектах») и привязать контрагента к партнёру или договор к привлечению (I-1 итогового ревью). Решение пользователя 02.10.2026: модуль получают все компании, а не только пилот. Включать `bpp` «только пилоту» после этого шага нельзя — см. раздел 3 («Если одна компания упала»).

**Что идёт по компаниям, что один раз.** Один раз на всю платформу: шаги 1–3, 4–5 (команды без `--company` либо с обходом всех), 13 (шаблон закупа снимается во всех схемах сразу), воркеры (шаги 1 и 15). По компании, в порядке «управляющая — первой»: шаги 6–12, 14 (SQL уже по всем схемам), `CompanyModule` шага 15, 16. Сводная таблица — «Чеклист компания × шаг» ниже. Платформенная часть окна (поддомены, гейты) — [subdomains-runbook.md](subdomains-runbook.md); перенос данных «Договоров» — [bpp-migrate-contracts-runbook.md](bpp-migrate-contracts-runbook.md) (здесь на него ссылка, не копия). Решения — [docs/plans/2026-10-01-bpp-stage6-executor-a.md](../plans/2026-10-01-bpp-stage6-executor-a.md), D-S6-4, D-S6-7, D-S6-8.

Условные обозначения:
- `<slug>` — slug компании, по которой идёт шаг (цикл по списку компаний, управляющая первой); `<АДМ>` — `user_id` администратора модуля (у каждой компании свой: пользователь с членством в ней).
- `manage` — `docker compose exec backend-web python manage.py` для прода; для тестового стека — `docker compose -f docker-compose.test-local.yml exec -T backend-web python manage.py` (`-T` — без псевдотерминала: без него вывод в скрипте и `<<heredoc` не работают). Файлы compose самостоятельные, цепочка `-f a -f b` не используется. Все команды `docker compose …` ниже даны для прода; на тестовом стеке — те же, с `-f docker-compose.test-local.yml` после `docker compose`.
- Файлы переноса (карты, отчёты, книга) команды читают и пишут **внутри контейнера** `backend-web`: на проде — путь на хосте, смонтированный в контейнер, либо `/tmp/…` и `docker compose cp` в обе стороны. Пути `maps/…` в примерах ниже — относительные к рабочему каталогу контейнера (`/app`; на тестовом стеке это смонтированный `backend/` — артефакты переноса в репозиторий не класть, использовать `/tmp/…`).
- Схема компании — `co_<slug>` (дефис в slug заменяется на `_`).

## 1. Предусловия

Отметить до начала окна. Нет любого пункта — окно не открывается.

  pg_dump -Fc -h <прод> -U htqweb htqweb > prod-pre-bpp-$(date +%F-%H%M).dump

### Шаг 1. Остановить воркеры

```bash
docker compose stop backend-worker backend-beat
```

**Ожидается:** два контейнера `Stopped` (в `docker-compose.yml` процессы Celery — `backend-worker` и `backend-beat`; `flower` — только наблюдение). **Проверка:** `docker compose ps` — их нет среди `running`; в Flower нет активных задач. Зачем: перенос и заморозка не должны гоняться с периодикой и напоминаниями; задачи, поставленные во время окна, подхватятся шагом 15.

### Шаг 2. Обновить код и поднять `backend-web`/`backend-asgi`

```bash
docker compose up -d --build backend-web backend-asgi
docker compose logs backend-web | grep entrypoint
```

**Ожидается** в логе: `[entrypoint] migrate (только общие аппки) ...` (внутри — `manage.py migrate_shared`) и отсутствие `migrate ПРОПУЩЕН`, если `RUN_MIGRATIONS=1`; дальше `collectstatic`, `бакеты хранилища`, `админ готов`. **Проверка:** `GET /health/` → 200. На тестовом стеке `backend-web` — `runserver`, а не gunicorn: порт `:8000` начинает отвечать через 1–1,5 минуты после `up` (контейнер из `health: starting` переходит в `healthy` тогда же) — повторять `curl http://localhost:8000/health/` до 200, а не считать это сбоем.

### Шаг 3. `migrate_shared` (общие аппки и периодические задачи)

Если на шаге 2 `RUN_MIGRATIONS=0` — вручную:

```bash
manage migrate_shared
```

**Ожидается** (на уже актуальной базе — `No migrations to apply`, в конце `Смигрировано общих аппок: N. Тенантные (…) пропущены`, `Периодические задачи тенантных аппок: заведено 0 … уже были 6`): применены миграции общих аппок (в т.ч. `access` до `0021_bpp_all_nodes`, `files` до `0005_bpp_alternative_offer_type`, `notifications` до `0002_digest_periodic_task`, `refdata` до `0003_nbrk_periodic_task`), в конце — заведены недостающие периодические задачи (`ensure_periodic_tasks`; вручную — `manage ensure_periodic_tasks`: только недостающие строки, операторские `enabled`/расписание не трогаются). **Проверка:** `manage showmigrations access files notifications refdata | grep "\[ \]"` — пусто; в django-admin → «Periodic tasks» есть задачи `signoff.retry_no_executor` и сводки.

### Шаг 4. `migrate_companies` — все компании

```bash
manage migrate_companies --plan                    # сухой прогон по всем компаниям
manage migrate_companies --company <slug> --plan   # то же, одна компания
manage migrate_companies --company hi-tech-group   # управляющая первой (контрольная)
manage migrate_companies                           # затем остальные (доводит отставших, собирает сводки холдинга)
```

Шаг идёт по ВСЕМ компаниям. Причина: код (шаг 2) уже новый у всех, и пока схема компании отстаёт, её задачи и партнёры отвечают 500 (см. «Окно» в предусловиях); к тому же сводки холдинга собираются, только когда все действующие компании на одной версии. Прогон одной компании — вариант для стенда с одной компанией. Настройка модуля у компании (роли, маршруты, перенос) делается на шагах 6–16; до них модуль у неё не настроен.

**Что это меняет у каждой компании.** Миграция `tasks/0023_link_boards_to_projects` в КАЖДОЙ компании заводит «Проекты» `TP-<id>` к её доскам задач (одна доска — один «Проект»; название, статус, сроки и владелец доски дальше правятся только в «Проектах»; уже связанная доска приводится к своему «Проекту», «Проекты» миграция не меняет), `tasks/0024` ставит «одна доска на проект», а `tasks/0025` вводит связь партнёра с контрагентом `bpp` вместо прежней связи с «Договорами». Поэтому модуль `bpp` (экран «Проектов», контрагенты) нужен КАЖДОЙ компании: решение «выкатываем всем» (D-S6-9, 02.10.2026; I-1 итогового ревью) закрывает вопрос, что делать с компаниями без модуля, — таких не остаётся, рубильник `bpp` не выключается ни у кого.

Пока схема компании отстаёт от кода, **воркеры должны быть остановлены** (шаг 1): сборщик бизнес-метрик (`collect_business_metrics`, раз в минуту) падает на компании без таблиц `bpp_*` (`core.metrics.tenant_collect_failed`: в `strict` — исключение задачи, в `log` — строка в логе). Сводки холдинга на время команды сняты, а собрать их можно, только когда все действующие компании на одной версии: при `--company` у одной из нескольких отставших команда завершится `CommandError: Схемы мигрированы, но сводки холдинга собрать нельзя` — доведите остальные компании командой `manage migrate_companies` без фильтров. Аргумент `--app` принимает любую тенантную аппку (`hr/tasks/contracts/signoff/bpp/project`), подсказка в `--help` называет только первые четыре.

**Ожидается:** для `--plan` — строка `<slug>: <миграция>, …` по каждой компании (у компании, на которой модуля ещё не было, — весь перечень от `bpp.0001_core` до `bpp.0017_merge_stage5_a_b`, затем `contracts.0028_freeze_state`, `project.0001_initial`, `tasks.0023_link_boards_to_projects`, `tasks.0024_project_ref_unique`, `tasks.0025_contractor_bpp_counterparty`; у отставшей — только хвост); после применения последними стоят `bpp/0017_merge_stage5_a_b`, `tasks/0025_contractor_bpp_counterparty`, `contracts/0028_freeze_state` (таблица заморозки), `project/0001_initial`, `hr`/`signoff` без изменений относительно кода; затем применение (`<slug>: bpp=0017…, contracts=0028…, hr=…, project=0001…, signoff=…, tasks=0025…` и `Сводки холдинга собраны: N шт.`; ~15 с на компанию с небольшими данными). Голый `migrate` не запускать: он пересоздал бы тенантные таблицы в `public`. Представления `holding.*` на время команды сносятся и пересобираются автоматически. **Проверка:** `manage migrate_companies --plan` — «нечего применять» у всех, `CompanySchemaVersion` каждой компании (django-admin, только чтение) соответствует `bpp/0017`, `tasks/0025`, `contracts/0028`; ручки сводки холдинга отвечают 200, а не 503 «сводки пересобираются».

### Шаг 4а. Производственный календарь: `refdata_import_production_days` (один раз на платформу)

Календарь РК стал общим справочником группы (`refdata.ProductionDay`, A7.1, D-S7-1): читают все сотрудники, правят ОД (`bpp-od`) и HR (`hr-senior`, `hr-lead`) управляющей компании. Ручные правки дней, которые компании успели сделать в своих схемах (`tasks_productionday`), переносит команда — НЕ миграция (исключение в миграции уронило бы старт `backend-web`).

```bash
manage refdata_import_production_days --dry-run     # на репетиции на дампе после `migrate_shared` (нужны новый код и refdata/0004), перед боевым прогоном: строки и конфликты
manage refdata_import_production_days               # после шага 4 (`migrate_companies`)
manage refdata_import_production_days               # повтор: «добавлено: 0»
```

**Ожидается:** по каждой компании строка `[<slug>] строк календаря: N`; итог `добавлено: …, без изменений: …, конфликтов: …`. Совпадающие строки компаний сливаются в одну; **конфликт** (разный тип дня одной даты у двух компаний или у компании и в `refdata`) — дата пропускается и печатается `КОНФЛИКТ <дата>: …` — решают ОД/HR вручную через экран календаря. Содержимое таблиц на бою неизвестно — `--dry-run` прогоняют на репетиции на дампе (после `migrate_shared`/на шаге 4а), а не «до выкатки»: ему нужен новый код. Переносятся только действующие компании со схемой — правки архивных компаний не переносятся. Проверка: `GET /api/refdata/v1/production-calendar/?date__gte=…&date__lte=…` отвечает 200 любому сотруднику; PATCH от ОД дочерней компании — 403; старый путь `/api/tasks/v1/production-calendar/` отвечает через `rewrite` nginx (на один релиз). До выкатки проверить, что холдинг в группе один (правка — только в управляющей компании). Таблица `tasks_productionday` остаётся до этапа 8 (expand).

### Шаг 14. Права на `bpp_auditlog` (запрос — по всем схемам сразу)

Журнал изменений неизменяем триггером на `UPDATE`/`DELETE`; от `TRUNCATE` его защищают права, а не триггер. Роль приложения не должна владеть таблицей `bpp_auditlog` и иметь на неё `TRUNCATE` — в схеме **каждой** компании:

```sql
SELECT n.nspname, c.relowner::regrole AS owner,
       has_table_privilege(current_user, format('%I.%I', n.nspname, c.relname), 'TRUNCATE') AS can_truncate
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relname = 'bpp_auditlog' AND n.nspname LIKE 'co\_%';
```

(выполнять **под ролью приложения, не суперпользователем**: у суперпользователя `has_table_privilege` всегда `t`, и проверка ничего не скажет; в `psql` — в Bash, а не в PowerShell, из-за кавычек; запрос читает только каталог, транзакция не нужна). **Ожидается:** `owner` — не роль приложения, `can_truncate = f`. Иначе администратор БД: `ALTER TABLE co_<slug>.bpp_auditlog OWNER TO <владелец схемы>; REVOKE TRUNCATE ON co_<slug>.bpp_auditlog FROM <роль приложения>;` и повторить проверку. На тестовых стеках роль приложения владеет всем — там пункт неприменим, в протоколе «н/п». Этот пункт выкатки закрывает требование этапа 8 мастер-плана.

### Шаг после окна. Включение блокировки входа (A7.2, D-S7-3)

Блокировка выкатывается **выключенной**: во всех трёх compose `AUTH_LOCKOUT_THRESHOLD` по умолчанию `0`, и в окне вход ведёт себя как раньше. Включают отдельно, после того как окно закрыто и пользователи вошли без сюрпризов — одним изменением окружения, без миграций.

1. **Предусловия.** Окно закрыто; Redis (кэш `/8`) доступен — счётчики живут в нём, а при его падении блокировка сама не действует (вход работает, в логе `FALLBACK site=htqweb.ratelimit.store_unavailable`, срабатывает алерт); в `infra/nginx/default.conf` выкачан `limit_req_status 429` у `location` токена; дежурному выдан доступ к `manage.py` на `backend-web`.
2. **Включить.** В боевом окружении (`.env` на хосте, правит администратор инфраструктуры) задать `AUTH_LOCKOUT_THRESHOLD=5` и `AUTH_LOCKOUT_SECONDS=900` и перезапустить `backend-web`: `docker compose up -d backend-web` (настройки читаются на старте процесса).
3. **Проверить.** На тестовой учётке (не рабочей): 5 неверных паролей подряд **с паузой не меньше 12 с между попытками** (зона nginx `api_auth` — 5 запросов в минуту, burst 2: быстрые попытки упираются в её собственный 429 уже на четвёртой и до блокировки не доходят) → шестой вход, даже с верным паролем, отвечает 429 с `code` = `E-AUTH-LOCKED` и заголовком `Retry-After` (сверять именно `code`: 429 без него — лимит nginx по IP, а не блокировка); ответы «неизвестный логин», «неверный пароль» и «неактивированная учётка с неверным паролем» одинаковы (401 «Invalid credentials»); `POST token/refresh/` у уже вошедших работает. В Grafana — панель «Блокировки входа» (дашборд `htqweb-business`) и правило «Всплеск блокировок входа» активны.
4. **Дежурному — как снять блокировку** (сотрудник написал, что его не пускает):
   ```bash
   docker compose exec backend-web python manage.py auth_unlock <логин или e-mail>
   ```
   Команда сбрасывает счётчик и блокировку по обоим логинам учётки (имя и e-mail). Блокировку снимает и смена пароля — самим пользователем или администратором (`admin/users/<id>/set-password`). Блокировка сама проходит через 15 минут.
5. **Откат.** `AUTH_LOCKOUT_THRESHOLD=0` и перезапуск `backend-web` — блокировка перестаёт действовать сразу; счётчики в Redis доживают свои 15 минут и ни на что не влияют.

Лимит 300 запросов в минуту на пользователя в этот шаг не входит (D-S7-4, позже).

## 3. Откат

**Кто решает.** Тимлид модуля по согласованию с ФД; администратор инфраструктуры исполняет. Решение и время — в протокол.

**Критерии «откатываем»** (любой из):
- шаги 3–4 не завершились (миграция упала, схема компании в неконсистентном состоянии) и исправление нельзя сделать за остаток окна;
- шаг 9: сальдо не сходится (`diff` ≠ 0) и ФД не принимает расхождение;
- потеря или искажение данных (`tenancy_status` показывает уменьшение числа строк);
- после шагов 12–15 не проходит любой из SC-001…SC-006 из-за дефекта, не лечащегося конфигурацией (роли, маршруты, рубильники) за остаток окна;
- не закрыто предусловие, обнаруженное уже в окне (нет бэкапа и т.п.) — тогда шаги не стартуют.

**Если одна компания упала посреди окна** (шаги 6–12 или 16 у компании N, остальные уже пройдены или ещё нет). Допустимы два исхода:
- **Продолжение окна** после исправления причины у этой же компании (исправили карту, должность, маршрут; шаг повторяется — команды идемпотентны). Остальные компании ждут своей очереди, окно продлевается.
- **Откат всего окна из бэкапа** — если дефект не лечится конфигурацией за остаток окна. Откатываются ВСЕ компании, не только упавшая: миграции схем и перенос откатываются только восстановлением.

**«Закончить окно без упавшей компании» недопустимо.** После шага 4 связка задач (`tasks/0023`–`0025`) уже действует в её схеме: без модуля `bpp` она не может завести доску задач, поменять название и сроки доски (409) и привязать контрагента к партнёру (I-1). Оставить компанию «на потом» или выключить ей `bpp` значит сломать задачи этой компании. Отдельной версии кода «без связки» нет, поэтому исключить одну компанию можно только откатом всего релиза.

Не сбой, а штатный пропуск: у компании нет данных «Договоров» — шаги 9–12 у неё «н/п», модуль настроен шагами 6–8 и 15.

**Что откатывается без восстановления** (если дефект локальный):
- заморозка — `contracts_freeze --undo`;
- рубильники — `manage service bpp --off` (для всех сразу; точечное выключение `CompanyModule` у одной компании не лечит, см. выше);
- перенос — **только восстановлением из бэкапа** (одной транзакцией отката нет: команда пишет в боевые таблицы и коммитится целиком).

**Восстановление из бэкапа:**
1. Остановить `backend-web`, `backend-asgi`, воркеры; включить страницу обслуживания.
2. Восстановить БД из дампа «Предусловий» (`pg_restore --clean --if-exists …` в ту же БД либо в новую и переключение `DB_HOST`/`DB_NAME`); файлы S3, загруженные после начала окна (`file_object/…`), не откатываются и остаются сиротами — безопасно.
3. Вернуть предыдущий образ и коммит; `RUN_MIGRATIONS=0` до выяснения причины, чтобы старый образ не гонял миграции поверх восстановленной схемы.
4. Снять слепок `tenancy_status --json` и сравнить с `tenancy-before.json`: совпадение.
5. Запустить воркеры, проверить вход, «Договоры» (запись открыта), мессенджер.
6. Сообщить пользователям; разбор причин — отдельным документом, повторное окно назначается заново.

Дамп, снятый перед окном, нельзя удалять до закрытия окна и подтверждения ФД.

**Оценка длительности окна (D-S6-9).** Замер выше — для ОДНОЙ компании с небольшими данными. Шаги 1–3, 5, 13 и миграции шага 4 (~15 с на компанию) растут слабо; шаги 6–12 и 16 повторяются по каждой компании, и к ним добавляется разбор отчётов переноса ФД каждой компании.
