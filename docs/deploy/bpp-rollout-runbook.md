# Выкатка модуля «Бюджет, закупки и оплаты» на пилотную компанию — ранбук (A6.3)

Пилот — управляющая компания. Выкатка идёт **одним окном** (D-S6-7) с откатом из бэкапа. Платформенная часть окна (поддомены, гейты) — [subdomains-runbook.md](subdomains-runbook.md); перенос данных «Договоров» — [bpp-migrate-contracts-runbook.md](bpp-migrate-contracts-runbook.md) (здесь на него ссылка, не копия). Решения — [docs/plans/2026-10-01-bpp-stage6-executor-a.md](../plans/2026-10-01-bpp-stage6-executor-a.md), D-S6-4, D-S6-7, D-S6-8.

Условные обозначения:
- `<slug>` — slug пилотной компании; `<АДМ>` — `user_id` администратора модуля.
- `manage` — `docker compose exec backend-web python manage.py` для прода; для тестового стека — `docker compose -f docker-compose.test-local.yml exec backend-web python manage.py`. Файлы compose самостоятельные, цепочка `-f a -f b` не используется.
- Схема компании — `co_<slug>` (дефис в slug заменяется на `_`).

## 1. Предусловия

Отметить до начала окна. Нет любого пункта — окно не открывается.

- [ ] **Бэкап.** Полный дамп БД и снимок бакетов S3/MinIO сняты **непосредственно перед окном**, дамп проверен восстановлением в отдельную копию (`pg_restore --list` без ошибок как минимум):
  ```bash
  pg_dump -Fc -h <прод> -U htqweb htqweb > prod-pre-bpp-$(date +%F-%H%M).dump
  ```
  Файл лежит вне хоста БД; имя и время записаны в протокол.
- [ ] **Окно.** Время начала и конца согласовано; пользователей предупредили (на время шагов 1–15 раздел «Договоры» и «Закупки и оплаты» недоступны для работы). Порядок и состав окна — вместе с блоком поддоменов ([subdomains-runbook.md](subdomains-runbook.md)), если выкатываются в одном окне.
- [ ] **Кто на связи** (имена и контакты записаны в протокол):
  - ФД (Алгазы) — решает по сальдо и по откату в части финансов;
  - тимлид модуля — решает «откатываем / идём дальше»;
  - разработчики A и B — запуск шагов, разбор ошибок;
  - администратор инфраструктуры — доступ к хосту, БД и бэкапам.
- [ ] **Флаги заданы явно** в боевом `.env`, а не наследуются умолчанием: `RUN_MIGRATIONS` по умолчанию `1` (`${RUN_MIGRATIONS:-1}` в `docker-compose.yml`), `RUN_BOOTSTRAP` по умолчанию равен `RUN_MIGRATIONS`. Значения на окно:
  - `RUN_MIGRATIONS=1` — только у `backend-web`; при старте он выполнит `migrate_shared` (не голый `migrate`); схемы компаний этот флаг не трогает, их доводит шаг 4;
  - `RUN_BOOTSTRAP=0`, если сид `admin`/`admin12345`, collectstatic и бакеты на бою уже сделаны, иначе `1` осознанно;
  - у `backend-worker` и `backend-beat` миграций нет.
- [ ] **Образ на Python 3.14.** Проверка перед сборкой и после:
  ```bash
  docker compose exec backend-web python -c "import sys, django; print(sys.version, django.get_version())"
  ```
  Ожидается `3.14…` и `5.2.7`. Образы всех backend-процессов собраны из одного коммита. Если медиа-воркер конференций (`backend/Dockerfile.media`) запускается отдельно от этого compose-файла, его образ пересобран тоже: в `docker-compose.yml` сервиса `backend-media-worker` нет.
- [ ] **Компания и её схема существуют** (`tenancy_status`, шаг 5 — снять слепок «до»); в окружении заданы `DB_HOST` и `JWT_SECRET`; режим `HTQ_ENV=production` (fallback-режим `log`).
- [ ] **Карты переноса `maps/projects.csv` и `maps/articles.csv`** заполнены ФД, статьи заведены в справочнике (по ранбуку B, п. «Сначала — репетиция»).
- [ ] **Репетиция на дампе пройдена** (D-S6-8) и протокол заполнен — раздел 5. В этапе 6 ранбук проверен прогоном на тестовом стеке (раздел 4).
- [ ] **Маршруты `contracts.*` выписаны** и сверены с маршрутами модуля (ранбук B, раздел «Маршруты согласования»).

## 2. Шаги

Каждый шаг: команда, ожидаемый вывод, проверка. Время начала и результат — в протокол (раздел 4/5). Не удался шаг — стоп, решение по разделу 3.

### Шаг 1. Остановить воркеры

```bash
docker compose stop backend-worker backend-beat
```

**Ожидается:** два контейнера `Stopped` (в `docker-compose.yml` процессы Celery — `backend-worker` и `backend-beat`; `flower` — только наблюдение). **Проверка:** `docker compose ps` — их нет среди `running`; в Flower нет активных задач. Зачем: перенос и заморозка не должны гоняться с периодикой и напоминаниями; задачи, поставленные во время окна, подхватятся шагом 15.

### Шаг 2. Обновить код и поднять `backend-web`/`backend-asgi`

```bash
docker compose up -d --build backend-web backend-asgi
docker compose logs backend-web | grep entrypoint
```

**Ожидается** в логе: `[entrypoint] …migrate_shared…` и отсутствие `migrate ПРОПУЩЕН`, если `RUN_MIGRATIONS=1`. **Проверка:** `GET /health/` → 200.

### Шаг 3. `migrate_shared` (общие аппки и периодические задачи)

Если на шаге 2 `RUN_MIGRATIONS=0` — вручную:

```bash

```

**Ожидается:** применены миграции общих аппок (в т.ч. `access` до `0018_bpp_all_nodes`, `files` до `0005_bpp_alternative_offer_type`, `notifications` до `0002_digest_periodic_task`, `refdata` до `0003_nbrk_periodic_task`), в конце — заведены недостающие периодические задачи (`ensure_periodic_tasks`; вручную — `manage ensure_periodic_tasks`: только недостающие строки, операторские `enabled`/расписание не трогаются). **Проверка:** `manage showmigrations access files notifications refdata | grep "\[ \]"` — пусто; в django-admin → «Periodic tasks» есть задачи `signoff.retry_no_executor` и сводки.

### Шаг 4. `migrate_companies` — пилот

```bash
manage migrate_companies --company <slug> --plan   # сухой прогон
manage migrate_companies --company <slug>
```

**Ожидается:** для `--plan` — список миграций тенантных аппок; после применения последними стоят `bpp/0017_merge_stage5_a_b`, `tasks/0025_project_ref_unique`, `contracts/0028_freeze_state` (таблица заморозки), `project/0001_initial`, `hr`/`signoff` без изменений относительно кода; затем применение. Голый `migrate` не запускать: он пересоздал бы тенантные таблицы в `public`. Представления `holding.*` на время команды сносятся и пересобираются автоматически. **Проверка:** `manage migrate_companies --company <slug> --plan` — «нечего применять», `CompanySchemaVersion` пилота (django-admin, только чтение) соответствует `bpp/0017`, `tasks/0025`, `contracts/0028`; ручки сводки холдинга отвечают 200, а не 503 «сводки пересобираются».

### Шаг 5. `tenancy_status`

```bash
manage tenancy_status --json > tenancy-after.json
```

Слепок «до» снимается так же до шага 3 (`tenancy-before.json`). **Ожидается:** у пилота все тенантные таблицы в `co_<slug>`, включая новые таблицы `bpp_*` и `project_*`. **Проверка:** различия до/после — только новые таблицы; число строк существующих таблиц не уменьшилось (`--exact` для точного `count(*)`).

### Шаг 6. Роли модуля: `bpp_assign_roles`

```bash
manage bpp_assign_roles --company <slug> --dry-run
manage bpp_assign_roles --company <slug>
```

**Ожидается** (dry-run): строки `выдать <роль> → <должность> (#id)`, при пропавшей должности — `нет должности: <название>`; настоящий запуск — `выдано: …` / `уже есть: …`. Повтор идемпотентен. **Проверка:** в редакторе должностей у ФД/ТД/ОД/ГД/БУХ/СН/ПМ видны роли `bpp-*`; `bpp-adm` в команду не входит и выдаётся лично (редактор ролей / `access_grant`).

**Кастомные роли.** Узлы «все документы» (`bpp.requests.all`, `bpp.invoices.all`, `bpp.agreements.all`, `bpp.accountable.all`, `bpp.plan.reassign`) у предка глубину не наследуют (`access/0017`, `0018`) и несут явную строку только у восьми системных ролей. Кастомным ролям и `platform-admin`, которым нужны все заявки, счета, договоры или подотчёт, выдать нужный узел **явной строкой в редакторе ролей** — иначе держатель увидит только свои документы. Узел `project.all` («все проекты») у ПМ намеренно отсутствует. **Проверка:** под каждой кастомной ролью открыть реестр заявок/счетов — видны чужие документы.

### Шаг 7. Маршруты согласования: `bpp_configure_routes`

```bash
manage bpp_configure_routes --company <slug> --dry-run
manage bpp_configure_routes --company <slug>
```

Должности ищутся по названию; при неоднозначности — `--td ID --od ID --gd ID --fd ID` (id должностей HR). **Ожидается:** `завести маршрут <что>: <цепочка>, флаги …` (dry-run) и `заведён маршрут <что> #id`; у существующих — `уже есть: активный маршрут … не менялся`; пропавшая должность — `нет должности «…»`, маршрут не заводится. **Проверка:** в редакторе маршрутов: заявка «ТД → ОД», договор «ФД → ТД → ОД → ГД», допсоглашение «ФД при росте суммы», счёт, подотчёт и авансовый отчёт — «ФД»; расхождения с выписанными маршрутами `contracts.*` внесены вручную (ранбук B).

### Шаг 12. Заморозка «Договоров»: `contracts_freeze`

Только когда ФД сверил сальдо по листу «Сверка» (шаг 9). До этого старый раздел остаётся живым.

```bash

```

**Ожидается:** `<slug>: раздел «Договоры» заморожен (<когда>)`. ### Шаг 13. Снять шаблон «Заявка на закуп»: `retire_purchase_request_template`

```bash
manage retire_purchase_request_template --dry-run
manage retire_purchase_request_template
```

Команда общая, а не по компании: идущие согласования заявок шаблона отзываются в `public` и в схеме **каждой** действующей компании. `--slug` по умолчанию `zayavka-na-zakup`. **Ожидается:** `шаблон [<id>] «<название>»: статус <статус>, заявок N, таблиц данных M`; `--dry-run` на этом останавливается; настоящий запуск печатает `снят: отозвано согласований X, удалено заявок N, таблица данных и справочники сохранены`. Шаблон получает статус «удалён» и перестаёт подаваться, его заявки удаляются, таблица данных и `RequestReferenceSource` остаются. Нет шаблона с таким slug — `шаблона со slug «…» нет — снимать нечего`; повторный запуск — `уже снят — без изменений`. **Проверка:** «Запросы» → «Создать запрос» — шаблона закупа нет; в очередях «Ждёт меня» нет согласований по заявкам закупа. Заявки удаляются безвозвратно (Q-A04: тестовые заявки пилота), поэтому перед запуском тимлид подтверждает в протоколе, что боевых заявок закупа нет; откат шага — только из бэкапа.

### Шаг 14. Права на `bpp_auditlog`

Журнал изменений неизменяем триггером на `UPDATE`/`DELETE`; от `TRUNCATE` его защищают права, а не триггер. Роль приложения не должна владеть таблицей `bpp_auditlog` и иметь на неё `TRUNCATE` — в схеме **каждой** компании:

```sql
SELECT n.nspname, c.relowner::regrole AS owner,
       has_table_privilege(current_user, format('%I.%I', n.nspname, c.relname), 'TRUNCATE') AS can_truncate
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relname = 'bpp_auditlog' AND n.nspname LIKE 'co\_%';
```

(выполнять под ролью приложения; в `psql` — в Bash, а не в PowerShell, из-за кавычек). **Ожидается:** `owner` — не роль приложения, `can_truncate = f`. Иначе администратор БД: `ALTER TABLE co_<slug>.bpp_auditlog OWNER TO <владелец схемы>; REVOKE TRUNCATE ON co_<slug>.bpp_auditlog FROM <роль приложения>;` и повторить проверку. На тестовых стеках роль приложения владеет всем — там пункт неприменим, в протоколе «н/п». Этот пункт выкатки закрывает требование этапа 8 мастер-плана.

### Шаг 15. Рубильники `bpp_*` у пилота и запуск воркеров

Модуль включается **у пилота**, у остальных компаний остаётся выключенным. Слои:
- глобальный — `ServiceStatus`: `manage service bpp --on` и подмодули `bpp_budget`, `bpp_requests`, `bpp_agreements`, `bpp_invoices`, `bpp_bank`, `bpp_alternatives`, `bpp_accountable` (`manage service <имя> --on`). Подмодуль гаснет вместе с родителем `bpp`;
- по компании — `CompanyModule` (нет строки = включено; отдельной management-команды нет). Два способа, платформенный администратор (суперпользователь): `PATCH /api/companies/v1/companies/<slug>/modules/<app_label>` с телом `{"enabled": false, "message": "…"}` (допустимы `bpp` и подмодули `bpp_*`; ядро — 409, неизвестное имя — 422; список состояний — `GET /api/companies/v1/companies/<slug>/modules`) либо django-admin → «Company modules» (поля компания, `app_label`, `enabled`). Для пилота — включены `bpp` и все `bpp_*`; у остальных компаний `bpp` выключается явно (`enabled=false`), иначе модуль у них включён по умолчанию.

Затем:

```bash
docker compose up -d backend-worker backend-beat
```

**Ожидается:** `manage service bpp --on` → «Сервис 'bpp' включён». **Проверка:** на поддомене пилота `GET /api/bpp/v1/...` → 200, у компании с выключенным `bpp` → 503 `service_disabled`; воркеры `running`, задачи `bpp.*` и `signoff.retry_no_executor` видны во Flower, очереди не растут.

### Шаг 16. Дымовые проверки SC-001…SC-006 (короткий ручной вид)

Сценарии — ТЗ §28.2 «Пользовательские сценарии». Выполняет тимлид или разработчик под пользователями с нужными ролями на поддомене пилота; каждый — один проход, результат в протокол. Для тестовых данных — проект с утверждённым бюджетом (SC-001 даёт его для остальных).

- **SC-001. Утверждение бюджета.** ФД: «Бюджеты» → «Создать бюджет», проект, строки статей и лимиты, итоги пересчитались, «Утвердить». Ожидается: версия 1, статьи доступны для заявок (BR-001, BR-002).
- **SC-002. Создание и согласование заявки.** СН: «Заявки» → «Создать заявку», проект (подгружаются статьи группы «Снабжение»), статья (виден остаток), позиции, «Отправить». Ожидается: остаток проверен и зарезервирован, созданы этапы ТД и ОД; после их согласования статус «Утверждена», позиции в Плане закупок СН.
- **SC-003. Договор из Плана закупок.** ПМ: отметить позиции одного проекта и статьи, «Оформить договор»; контрагент (подставляются БИН, страна, ставка НДС), номер, дата, наименование, тип, сумма, файл, «Отправить». Ожидается: ФД, ТД, ОД согласуют, затем ГД; договор «Действует», виден в реестре договоров.
- **SC-004. Счёт без договора.** СН: отметить позиции, «Оформить счёт», основание «Без договора», контрагент, номер, дата, сумма, файл. Ожидается: сумма > 4 325 000 тг (1000 МРП при МРП 4 325) — отправка заблокирована, предложен договор (E-INV-01); сумма ≤ порога — уходит ФД, присвоен номер `СЧ-ГГГГ-NNNNNN`.
- **SC-005. Решение ФД и оплата.** ФД: «На решение ФД», отметить счета, «Оплатить». Ожидается: счета у БУХ во вкладке «К оплате»; БУХ по услуге ставит «АВР» и «Запросить документы», автор вкладывает АВР, БУХ принимает и нажимает «Оплачено» (до принятия АВР — E-INV-04).
- **SC-006. Сверка оплат.** ФД: «Оплаты факт», банк, формат, период, файл выписки. Ожидается: загрузка «Сверена»; «Требуют проверки» и «Не сопоставлены» разбираются вручную; в реестре счетов виден статус сверки, дашборд «Оплаты» показывает итоги.

Дополнительно (не из §28.2):
- **Альтернативы и KPI.** СН подаёт АП к счёту «На рассмотрении ФД», ФД выбирает вариант. Ожидается: АП «Выбрано», KPI «Предварительный».
- **Подотчёт.** Авансовый отчёт проходит ФД.
- **Перенос.** Перенесённый договор виден с пометкой «перенесён»; остаток статьи равен листу «Сверка»; запись в «Договоры» — 403 `contracts_frozen`.
- В логах нет `FALLBACK … expected=false`; бизнес-метрики `htqweb_*` экспортируются (через минуту после старта beat); колокольчик и ежедневная сводка (09:00 Пн–Пт) приходят авторам из листа «Переотправить».

**Окно закрывается**, когда все шаги отмечены, SC-001…SC-006 пройдены, ФД подтвердил сальдо. Бэкап шага «Предусловия» не удаляется до подтверждения ФД и закрытия окна.

## 3. Откат

**Кто решает.** Тимлид модуля по согласованию с ФД; администратор инфраструктуры исполняет. Решение и время — в протокол.

**Критерии «откатываем»** (любой из):
- шаги 3–4 не завершились (миграция упала, схема компании в неконсистентном состоянии) и исправление нельзя сделать за остаток окна;
- шаг 9: сальдо не сходится (`diff` ≠ 0) и ФД не принимает расхождение;
- потеря или искажение данных (`tenancy_status` показывает уменьшение числа строк);
- после шагов 12–15 не проходит любой из SC-001…SC-006 из-за дефекта, не лечащегося конфигурацией (роли, маршруты, рубильники) за остаток окна;
- не закрыто предусловие, обнаруженное уже в окне (нет бэкапа и т.п.) — тогда шаги не стартуют.

**Что откатывается без восстановления** (если дефект локальный):
- заморозка — `contracts_freeze --undo`;
- рубильники — `manage service bpp --off` и строки `CompanyModule`;
- перенос — **только восстановлением из бэкапа** (одной транзакцией отката нет: команда пишет в боевые таблицы и коммитится целиком).

**Восстановление из бэкапа:**
1. Остановить `backend-web`, `backend-asgi`, воркеры; включить страницу обслуживания.
2. Восстановить БД из дампа «Предусловий» (`pg_restore --clean --if-exists …` в ту же БД либо в новую и переключение `DB_HOST`/`DB_NAME`); файлы S3, загруженные после начала окна (`file_object/…`), не откатываются и остаются сиротами — безопасно.
3. Вернуть предыдущий образ и коммит; `RUN_MIGRATIONS=0` до выяснения причины, чтобы старый образ не гонял миграции поверх восстановленной схемы.
4. Снять слепок `tenancy_status --json` и сравнить с `tenancy-before.json`: совпадение.
5. Запустить воркеры, проверить вход, «Договоры» (запись открыта), мессенджер.
6. Сообщить пользователям; разбор причин — отдельным документом, повторное окно назначается заново.

Дамп, снятый перед окном, нельзя удалять до закрытия окна и подтверждения ФД.
