# Файловая подсистема по ТЗ §21 — этап 1 (подсистема + заявка)

> **Поправки 26.09.2026 — подгонка под мастер-план БЗО** ([2026-09-26-bpp-master-plan.md](2026-09-26-bpp-master-plan.md)). Ниже — исходная спека; действует она с этими изменениями:
> - **Владельцы «заявка» (`approvals.request`) и «договор» (`contracts.agreement`) сняты** (D-01: документы договоров и заявок живут в `apps.bpp`, `contracts` и шаблон закупа не развиваются). Подсистема осталась без владельцев и ждёт документы модуля БЗО; тесты — на пробных владельцах `apps/files/tests/testapp`. Этап 2 (договор) и команда `migrate_agreement_files` не делаются.
> - **Ключ владельца — строка** (`owner_id`, документы БЗО — UUID, D-05): `register_owner(model=…)`, колбэки получают ключ в типе модели.
> - **Формат ошибок** — `{detail, code, fields, details}` (D-28) вместо `{code, message, fields, details}`; тексты формата и размера — одна фраза ТЗ §13.2.
> - **Антивирус по умолчанию выключен** (D-31), ClamAV — под профилем compose `antivirus`.
> - **Гейт** (глобальное ограничение плана): правка справочника — `files:write`, остальные ручки — `scoped`/`open` в `access/self_service.py`.
> - Сиды справочника для заявки/договора/КП удалены; миграции подсистемы — одна `0001_initial`.


Источник требований: ТЗ «Бюджет, закупки и оплаты» v1.0 — §21 «Файлы и
вложения» (стр. 65), объект «Файл» (стр. 9), справочник «Типы файлов»
(стр. 61), API `UploadFile/DownloadFile` (стр. 68), таблица `file_object`
(стр. 70), REQ-024 (стр. 79), формат ошибок и каталог сообщений (стр. 68, §26).

## Решения (приняты с заказчиком разработки)

| Вопрос | Решение |
|---|---|
| Объём | Этап 1 — подсистема + заявка на ней. Этап 2 — договор. Альтернативные предложения (§12) — отдельной задачей в конце. Счёт/АВР/накладная — ждут. Доп. соглашение (новая версия договора) — не трогаем. Выписка — позже. |
| Версии | **Как в ТЗ.** Номер версии присваивается один раз и не меняется никогда. Новая версия грузится поверх конкретной действующей; если её уже заменили — 409 `E-CON-01`. Повтор запроса с тем же `Idempotency-Key` возвращает результат первого. Перенумерации по времени нет. |
| Формат ошибок | **Как в ТЗ:** `{code, message, fields: [{field, message}], details}`, `message` — готовый текст для человека (§26: что произошло, почему, что делать). Поля `detail` в новом API нет — фронт учится читать `message`. |
| Антивирус [Л] | Сделан после этапа 2: ClamAV-контейнером, проверка в пайплайне media по флагу scope, fail-closed (см. раздел «Антивирус» ниже). |
| Роли ФД/БУХ/… | Для заявки и договора не нужны (доступ = «все с правом просмотра объекта»). |
| Файлы после отправки | **Только чтение.** Менять (новый документ, новая версия, удаление) можно лишь в статусах владельца «Черновик» и «На доработке» — у заявки только автору. Согласующие видят и скачивают. |
| Журнал скачиваний | ТЗ §25.2 («загрузка / замена / скачивание файлов», IP, user-agent). Готовых подписанных ссылок в ответах нет вовсе: ссылка выдаётся на каждое скачивание (`link`), и каждая выдача пишется в журнал владельца. Заранее подписанная ссылка была бы скачиванием мимо журнала. |

## Архитектура

### Аппка `apps.files` (public)

Новая аппка, `API_PREFIX = "api/files/v1/"`, сервис `files`. Общая (не в
`TENANT_APPS`): владельцы бывают и public (заявка), и tenant (договор).

Подключение новой аппки (всё обязательно, большая часть ловится тестами):

  бы отправку заявок/договоров; `PREFIX_TO_SERVICE["/api/files/"]`
  (`htqweb/middleware/service_gate.py`, тестом НЕ ловится — не забыть).

  (`access/tests/test_bootstrap.py` сверяет узлы с `KNOWN_SERVICES`);
  `apps/files/access_functions.py`.

- nginx: локация загрузки (см. ниже).

### Модели

**`FileType`** — справочник «Типы файлов» (стр. 61). Строки фиксированы
(заводятся миграцией `RunPython update_or_create` по `code`),
администратор меняет **только** `max_mb`.

| Поле | Тип | Смысл |
|---|---|---|
| `code` | `CharField(64)`, PK | `request.kp`, `request.tz`, `request.spec`, `request.other` (этап 2: `agreement.main`, `agreement.attachment`) |
| `owner_type` | `CharField(64)` | `approvals.request` (этап 2: `contracts.agreement`) |
| `name` | `CharField(200)` | «КП», «ТЗ», «Спецификация», «Прочее» |
| `formats` | `JSONField` | список расширений: `[".pdf", ".docx", ".xlsx", ".jpg", ".jpeg", ".png"]` |
| `max_mb` | `PositiveIntegerField` | 20; правка ≤ `FILES_UPLOAD_CEILING_MB` (= 20, совпадает с nginx) |
| `sort_order`, `updated_at`, `updated_by_id` | | |

Правила количества — в коде владельца (`FileTypeSpec`, см. реестр), не в
справочнике: в ТЗ у справочника только код, наименование, форматы, размер,
объект-владелец.

**`FileObject`** — таблица `file_object` из ТЗ (стр. 70).

| Поле | Тип | Смысл |
|---|---|---|
| `company_slug` | `CharField(64)`, `""` по умолчанию | компания владельца. Для tenant-владельцев — часть ключа (id договоров повторяются в разных схемах); `""` = режим до `tenancy_bootstrap`. Для public-владельцев — просто факт «из какой компании загрузили», фильтром не служит |
| `owner_type`, `owner_id` | `CharField(64)`, `IntegerField` | владелец (ТЗ: `owner_type, owner_id`) |
| `file_type` | FK → `FileType` (`PROTECT`) | ТЗ: `file_type` |
| `document_id` | `UUIDField` | линия версий одного документа |
| `version_no` | `PositiveIntegerField` | ТЗ: `version_no`, **неизменен** |
| `is_replaced`, `replaced_by` | bool, FK self `SET_NULL` | «Заменён», ТЗ: `replaced_by_id` |
| `name`, `mime`, `size`, `sha256` | | метаданные ТЗ |
| `storage_key` | `CharField(1024)`, **unique** | ТЗ: уникальность по `storage_key` |
| `media_file_id` | `CharField(64)`, unique | id `FileMetadata` в `media_files` (строкой — межаппный FK запрещён) |
| `uploaded_by_id`, `uploaded_by_name`, `uploaded_by_department_id`, `uploaded_by_department_name` | | «кто загрузил» + снимок ФИО и отдела на момент загрузки |
| `uploaded_at` | `DateTimeField(auto_now_add, db_default=Now())` | «когда загрузил» |
| `idempotency_key` | `CharField(64)`, `""` | ключ повтора |
| `deleted_at`, `deleted_by_id` | | удаление после отправки — только пометка |

Ограничения: `UniqueConstraint(document_id, version_no)`;
`UniqueConstraint(company_slug, owner_type, owner_id, idempotency_key)` с
условием `idempotency_key <> ''`; индекс `(owner_type, owner_id, company_slug)`.

### Реестр владельцев

Приём тот же, что у signoff (`signoff/services/registry.py`): владелец
регистрируется из своего `AppConfig.ready()` через `apps.files.interface`,
подсистема зовёт его колбэки и не импортирует его модели.

```python
register_owner(
    owner_type="approvals.request", label="Заявка", service="approvals",
    tenant=False, folder="request",
    file_types=(FileTypeSpec("request.kp", quota_group="request"), ...),
    quotas={"request": 20},             # «до 20» — на документы, версии не считаются
    can_view=...,     # (owner_id, token) -> bool; False → 404 E-FIL-05 (не раскрываем существование)
    can_modify=...,   # (owner_id, token) -> None; raise FilesForbidden(msg) → 403 E-ACC-01,
                      #                          raise FilesLocked(msg)    → 409 E-FIL-06
    was_sent=...,     # (owner_id) -> bool; False → удаление физическое
    lock=...,         # (owner_id) -> None; SELECT … FOR UPDATE строки владельца (зовётся внутри atomic)
    on_event=None,    # (owner_id, event, actor_id, payload) -> None; журнал владельца, в той же транзакции
)
```
`FileTypeSpec(code, cardinality="multi"|"single", quota_group=None,
max_documents=None, required=False)`. `single` = «1 действующий + версии»
(этап 2, основной файл договора): второй документ того же типа — 409
`E-FIL-03`, менять — только новой версией.

Порядок проверок перед любым вызовом колбэка: `require_service(entry.service)`;
для tenant-владельца — компания из `current_company_or_none()` (`""` до
bootstrap), все запросы к `FileObject` фильтруются по ней.

### API (`/api/files/v1/`)

| Метод и путь | ТЗ | Что делает |
|---|---|---|
| `GET <owner_type>/<owner_id>/files/` | — | Папка владельца: `can_modify`, `modify_reason` (только когда мешает состояние владельца; отказ по правам не объясняется), `delete_is_physical`, `storage_prefix`, типы (`code, name, formats, max_mb, cardinality, required, can_add, reason`), квоты (`group, max, used`), документы: `{document_id, file_type, file_type_name, deleted_at, current, versions[]}` (версии от новой к старой; удалённые документы — в конце). Ссылок на файлы нет |
| `POST <owner_type>/<owner_id>/files/` | `UploadFile` | multipart `file`, `file_type`; заголовок `Idempotency-Key` → 201 версия 1 нового документа |
| `POST <owner_type>/<owner_id>/files/<document_id>/versions/` | `UploadFile` | multipart `file`, `base_file_id` (действующая версия, поверх которой грузят); `Idempotency-Key` → 201 новая версия |
| `DELETE <owner_type>/<owner_id>/files/<document_id>/` | — | 204. Документ ни разу не отправленного владельца — физически (строки + `media.delete_file` после коммита, `robust`), повтор — 404 `E-FIL-05`; иначе — `deleted_at` у всех версий, повтор — 204 |
| `GET <owner_type>/<owner_id>/files/<document_id>/versions/<file_id>/link` | `DownloadFile` | `{url, expires_at}` — временная подписанная ссылка после проверки прав, на каждое скачивание; событие `file_downloaded` (IP, user-agent) в журнал владельца |
| `GET types/?owner_type=` | — | справочник (нужен странице создания заявки, где владельца ещё нет) |
| `PATCH types/<code>/` | — | `admin=True`, тело `{max_mb}`, только размер |

Все пути — в обоих написаниях (со слэшем и без, `APPEND_SLASH=False`).
Версия в ответе (`FileVersion`): `id, document_id, file_type, version_no,
is_replaced, replaced_by_id, name, mime, size, sha256, storage_key,
uploaded_by_id, uploaded_by_name, uploaded_by_department_id,
uploaded_by_department_name, uploaded_at, deleted_at` — без `url` (см.
«Журнал скачиваний»). Неподдерживаемый метод — 405 в формате ТЗ
(`E-FIL-07`), битый multipart — 422 `E-FIL-07`, а не 500.

Порядок проверок загрузки: видимость (404) → право менять (403/409) → тип
файла у этого владельца (422) → расширение ∈ `formats` (415) → размер ≤
`max_mb` (413) → квота/`single` (409) → для версии: `base_file_id` — всё ещё
действующая (409 `E-CON-01`) → повтор по `Idempotency-Key` (вернуть первую
запись). Затем запись в хранилище **вне** транзакции, затем транзакция:
`lock` владельца → повторная проверка права, квоты, `base_file_id`, ключа →
вставка (номер = max+1 по документу) → у прежней действующей `is_replaced`
и `replaced_by` → `on_event`. Отказ после записи в хранилище — файл
возвращается в media, только если строка так и не появилась.

Последний рубеж — уникальные индексы (`(document_id, version_no)` и ключ
повтора). Вставка идёт в точке сохранения, и отказ индекса разбирается, а не
отдаётся 500: успел повтор с тем же ключом — вернуть его запись (свой файл —
в media), успела чужая версия — `E-CON-01`. Для заявки до этого не доходит
(её `lock` — `FOR UPDATE`), но владелец со слабой блокировкой не должен
получать 500. Ключ повтора ставится на одно действие: тот же ключ для
другого файла или места — 422 `E-FIL-07`, а не молчаливая чужая запись.

Компания тенантного владельца обязательна: когда компании заведены, запрос
без контекста компании — `NoCompanyContext` (500 наружу), а не молчаливое
`""` («ничья» куча файлов). `""` честно только до `tenancy_bootstrap`, пока
компаний нет вовсе.

### Ошибки (формат ТЗ)

`{"code", "message", "fields": [{"field", "message"}], "details": {...}}`.
Каталог §26.1 кодов для файлов не содержит — заводим `E-FIL-*`, общие берём
из ТЗ:

| Код | HTTP | Ситуация | Пример `message` |
|---|---|---|---|
| `E-FIL-01` | 415 | недопустимый формат / содержимое не совпадает с типом | «Файл schet.exe не загружен: допустимы PDF, DOCX, XLSX, JPG, PNG до 20 МБ.» (ТЗ §13.2) |
| `E-FIL-02` | 413 | превышен размер (в т.ч. nginx) | «Файл scan.pdf не загружен: размер 24,3 МБ больше допустимых 20 МБ.» |
| `E-FIL-03` | 409 | превышено количество / `single` уже приложен | «В заявке уже 20 документов — это предел. Удалите лишний или загрузите новую версию существующего.» |
| `E-FIL-04` | 422 | не приложен обязательный файл (отправка договора) | «Не удалось отправить договор на согласование: не приложен файл «Договор». Приложите его и повторите отправку.» |
| `E-FIL-05` | 404 | документ / владелец не найден или не виден | «Документ не найден. Возможно, он удалён или у вас нет к нему доступа.» |
| `E-FIL-06` | 409 | менять файлы в текущем статусе нельзя | «Файлы заявки меняются только в статусах «Черновик» и «На доработке».» |
| `E-FIL-07` | 422 | некорректный запрос (нет файла, неизвестный тип) | «Не выбран файл. Выберите файл и повторите загрузку.» |
| `E-CON-01` | 409 | версию уже заменил другой | «Документ изменён пользователем Иванов А. в 14:32. Ваши изменения не сохранены. Обновите страницу и внесите их повторно.» (ТЗ §26.1) |
| `E-ACC-01` | 403 | нет прав | «У вас нет прав на изменение файлов заявки REQ-…. Если это ошибка, обратитесь к администратору.» |

401/503 (нет токена, выключен сервис) остаются в общем формате платформы —
их отдаёт `api_view`, не подсистема. Фронт (`lib/apiError.ts`) читает
`message`, если нет `detail`.

### Хранилище (`media_files`)

- Scope `request_doc` → **`file_object`**: `folder_layout`, `keep_original`,
  MIME — объединение форматов всех типов (сейчас PDF/DOCX/XLSX/JPG/PNG),
  `max_mb` = потолок 20. Узкие правила типа проверяет `files` до записи.
- Новый флаг `ScopePolicy.owner_gated=True` у `file_object`: media НЕ отдаёт
  такие файлы загрузившему/администратору по JWT и не подписывает их через
  `POST files/<id>/sign` — только по ссылке, выданной подсистемой после
  проверки прав владельца (закрывает «вторую дверь»).
- Ключ: `file_object/<company или public>/<folder владельца>/<owner_id>/<uuid>/original<ext>`
  («1 объект = 1 папка»).
- Точка подключения антивируса: `files.services.scan(data, filename)` —
  сейчас ничего не делает.

### Заявка как первый владелец

`apps/approvals/file_hooks.py`, регистрация в `ApprovalsConfig.ready()`:
- `can_view` — `instance_service.can_view` (инициатор, наблюдатель, участник
  согласования, администратор);
- `can_modify` — только автор; замок согласования (`assert_editable`) и
  статус `draft`/`returned`;
- `was_sent` — `status != draft` или `submitted_at` задан или в журнале есть
  `submitted`;
- `lock` — `select_for_update` строки заявки;
- `on_event` — `RequestActivity` (`file_attached`, `file_version_attached`,
  `file_deleted`, `file_downloaded`; у всех — IP и user-agent);
- типы `request.kp/tz/spec/other`, общая квота 20.

### nginx

Локация `location /api/files/v1/`: `client_max_body_size 21M`; зоны
`files_upload` (ключ — `map` по методу: считает только POST, чтение папки и
выдача ссылок её не расходуют) и общая `api_general`; полный набор
`proxy_set_header` (включая `X-HTQ-Company`), буферизация запроса включена,
`error_page 413` → JSON `E-FIL-02` вместо HTML-страницы nginx. В
`/api/media/` повторены серверные `add_header` (свой `X-Cache-Status`
отменял их наследование), — оттуда отдаются документы по ссылкам.

### Фронт

- `api/files.ts` (`filesApi`): `list`, `upload`, `uploadVersion` (с
  `base_file_id`), `remove`, `link`, `types.list/update`; `Idempotency-Key` —
  UUID v4 (`crypto.randomUUID`, вне HTTPS — из `getRandomValues`).
- `hooks/useFiles.ts`: ключ живёт, пока не ясно, дошёл ли запрос (ТЗ §26.2):
  после обрыва или 5xx тот же файл в то же место уходит с тем же ключом,
  ответ по существу (2xx/4xx) ключ снимает. В отпечатке версии нет
  `base_file_id` — иначе повтор поверх уже перечитанной папки получил бы
  новый ключ и приложил файл дважды.
- Скачивание — клик просит `link`; PDF/картинки открываются во вкладке
  (открытой синхронно в обработчике клика — иначе её режет блокировщик
  окон), остальное скачивается, не уводя со страницы. Время — по Алматы
  (ТЗ стр. 11), как в текстах сервера.
- Общий `components/files/FilesPanel.tsx` (+ `FileUploadControls`) — из
  нынешнего `RequestFilesPanel`; типы — из ответа сервера, не из кода.
  409 `E-CON-01` — показать текст и перечитать папку.

## Этап 2 — договор (сделано)

ТЗ: §21 (стр. 65) «Договор: PDF, DOCX, JPG, PNG, 20 МБ, обязателен,
1 действующий + версии, замена новой версией до «Действует»; приложения,
доп. соглашения — то же, необязательны, до 30»; §9.1 «Редактирование —
Автор, «Черновик», «На доработке»»; §9.2 «Файл договора … после утверждения —
только новой версией через изменение договора».

| Вопрос | Решение |
|---|---|
| Типы | `agreement.main` «Договор» (`single`, обязателен) и `agreement.attachment` «Приложения, доп. соглашения» (до 30) — миграция `files/0004`. XLSX у договора нет — так в ТЗ. |
| Кто меняет | Автор договора, пока статус «Черновик» и согласование `draft`/`rework` (`assert_editable`). Администратор не исключение — по ТЗ правка у автора. |
| Заморозка | «Действует» = `approved` (решение заказчика). На согласовании и дальше (`approved`, `signed`, `executed`, `terminated`) — только чтение. «Изменения договора» (новая версия после утверждения) в системе нет — вместе с доп. соглашениями его не трогаем. |
| Отправка | Без действующего «Договора» — 422 `E-FIL-04` в формате ТЗ. Проверка последней из предметных, под блокировкой строки договора — той же, что берёт подсистема на загрузке/удалении. Общий админский `POST /api/signoff/v1/processes` её не делает, как не делает и остальных предметных проверок. |
| Кто видит | Все, кто видит договор (реестр читает любой сотрудник). |
| Журнал | `FileEvent` в `apps.files` — у каждого владельца (ТЗ §25.2); своей ленты у договора нет. |
| Удаление черновика | `files.owner_deleted` в транзакции удаления: ни разу не отправленный — файлы физически, отправлявшийся (возвращён на доработку) — `deleted_at`, строки остаются. |
| Старые сканы | `Agreement.file_id` больше не читается и не пишется (колонка остаётся — expand/contract). `manage.py migrate_agreement_files [--dry-run] [--company]` копирует скан в папку договора версией 1 «Договора» (автор и время — от оригинала), оригинал не трогает, повтор ничего не дублирует, договор с уже приложенным «Договором» пропускает. |
| Компания | Договор тенантный: `company_slug` — часть ключа. До первой компании — `""`; `tenancy_bootstrap` проставляет компанию файлам и журналу тенантных владельцев в той же транзакции, что переносит таблицы. Ключи в S3 не переносятся: файлы до bootstrap остаются под `file_object/public/agreement/<id>/`. |

Убрано: `POST agreements/<id>/file`, `GET agreements/<id>/file-url`,
`agreement_service.attach_file/file_url/file_info`, поле `file_id` в ответе
договора (вместо него `has_main_file`, одним запросом на список).

Фронт: карточка договора — «Файл договора» (встроенный просмотр действующей
версии по ссылке `DownloadFile`; просмотр тоже пишется в журнал) и панель
«Документы договора»; «На согласование» гаснет без файла и во время
загрузки. Форма создания — файл «Договор» уходит сразу после создания
черновика (`uploadDocument`, тот же ключ повтора), при отказе — переход в
карточку с причиной.

### Не сделано / следующее

- Договоры, заведённые сразу «Согласованными»/«Подписанными» (задним
  числом, импорт реестра), файл получить не могут — по ТЗ после «Действует»
  только через изменение договора. Если нужно — разрешить им прикладывать
  файлы, пока договор ни разу не уходил на согласование (одно условие в
  `file_hooks.can_modify`).
- Альтернативные предложения (§12), счёт/АВР/накладная, изменение договора.

## Антивирус (сделано)

ТЗ §21: «Антивирусная проверка при загрузке [Л]» — «реализуется, если
заказчик не возразит». Своего кода в каталоге §26.1 нет — заведён `E-FIL-08`;
для недоступного сканера — `E-SYS-01` «сервер недоступен» из ТЗ.

| Вопрос | Решение |
|---|---|
| Сканер | ClamAV, сервис `clamav` (`clamav/clamav:1.4`) во всех трёх compose-файлах: clamd :3310 только внутри сети, freshclam обновляет базы сам, базы в томе `clamav_db`. ~1,5 ГБ памяти. |
| Клиент | `htqweb/antivirus.py` — протокол INSTREAM по TCP (куски с 4-байтной длиной, нулевая — конец), без нового пакета. Ответ `ERROR` (размер, база) — не «чисто». |
| Где проверка | Пайплайн `apps.media_files` (`upload_file_bytes`) для scope с `ScopePolicy.antivirus`. После дешёвых проверок (размер, тип, сигнатура), до разбора картинки и записи; проверяются присланные байты. |
| Что проверяется | **Всегда, без отметок** (решение заказчика вместо галочки ФД на отдельных документах): `file_object` (файлы заявок и договоров, перенос старых сканов), `generic` (сканы счетов на оплату, актов, накладных, платёжных поручений, авансовых отчётов — и любой неизвестный scope), `signoff_doc` (PDF шагов согласования, в том числе «Счёт на оплату» закупщика). Не проверяются: аватарки, чат, новости, HR-документы, вложения задач. Отказы media — наследники `htqweb.http.ApiError`: и вьюхи договорного контура отдают их текстом, а не 500. |
| Угроза | 422 `E-FIL-08` «Файл X не загружен: антивирус обнаружил угрозу «…»», файл не сохраняется, `FileEvent` `file_rejected` (кто, IP, user-agent, сигнатура) — только в журнал, не в ленту владельца. |
| Сканер недоступен | **Fail-closed**: 503 `E-SYS-01`, файл не принимается. Молча пропустить непроверенный файл значило бы, что проверка есть только на бумаге. Это отказ, а не подмена, — через `htqweb.fallback` не идёт. Клиент повторяет с тем же `Idempotency-Key` (5xx). |
| Выключатель | `ANTIVIRUS_CLAMD_HOST`: `clamav` по умолчанию во всех трёх стеках; пустое значение в окружении выключает; тесты — пусто явно (`settings/test.py`). Предел потока clamd — `CLAMD_CONF_StreamMaxLength: 100M` (потолок шлюза для `/api/media/`). |
| Перенос сканов | Заражённый — в отчёт «пропущено», недоступный сканер — ошибка прогона (повтор безопасен). |

Проверено вживую против настоящего ClamAV: EICAR внутри DOCX — 422
`E-FIL-08`, чистый PDF — 201, остановленный clamav — 503 `E-SYS-01`.

Не сделано: проверка уже лежащих файлов (сканер видит только новые байты);
чат, HR-документы, вложения задач — включаются тем же флагом scope.
