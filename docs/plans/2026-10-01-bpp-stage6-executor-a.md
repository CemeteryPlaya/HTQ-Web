## Решения этого плана

**D-S6-1. Тесты — на Python 3.14.**
- Прод (`python:3.14-slim`) и CI (`backend-full`) работают на 3.14, локальный корневой `.venv` — на 3.13.
- 21 падение полного набора, найденное у Руслана, на 3.13 не воспроизводилось: Celery 5.6 по-разному читает сигнатуру задачи.
- С этого этапа контроллер гоняет pytest в окружении 3.14. Корневой `.venv` пересоздаётся на 3.14 (задача 1); CLAUDE.md и память правятся.

**D-S6-2. Партнёр → контрагент `bpp` — по связям переноса.**
- Новое поле `Contractor.bpp_counterparty_id` — строка UUID, уникальна среди непустых.
- Заполняет команда `tasks_link_counterparties --company <slug> [--dry-run]`. Она ставит партнёру того же контрагента, в которого B6.1 перенёс его контрагента `contracts`: `bpp.interface.migrated_targets("counterparty", ids)`.
- Партнёр без контрагента в `contracts` и непереносимые случаи — в отчёт команды, руками на экране партнёра.
- Старое `counterparty_id` после задачи 2 никто не читает (сторож — тест на `grep`).

**D-S6-3. Доска задач ↔ «Проект» — по решениям Руслана 29.09.**
- «Проект» главный: доска заводится только выбором существующего «Проекта», одна доска на проект.
- Название, статус, сроки и руководитель приходят из «Проекта» и на доске только для чтения.
- Существующие доски связываются миграцией: «Проект» `TP-<id доски>`, занятый код — `-2`, `-3`…
- Основа — отменённые коммиты B `321f402` (бэкенд) и `899aca3` (фронт). Переносятся заново, номера миграций — по текущему графу `tasks`.

**D-S6-4. Заморозка `contracts` — по компании, отдельным шагом ранбука.**
- Таблица `contracts.FreezeState` (одна строка в схеме компании: `frozen_at`, `frozen_by_id`, `comment`) и команда `contracts_freeze --company <slug> [--undo]`.
- Морозит человек после проверки переноса, а не сам перенос: пока ФД не сверил сальдо, старый раздел должен оставаться живым.
- Запись — middleware `apps/contracts/middleware.py` после `CompanyContextMiddleware`: любой метод, кроме `GET`/`HEAD`/`OPTIONS`, под `/api/contracts/` замороженной компании → 403 `{"detail": "Раздел перенесён в «Закупки и оплаты». Данные доступны только для чтения.", "code": "contracts_frozen"}`.
- Задачи Celery `contracts` у замороженной компании пропускаются, с записью в лог.
- `ServiceStatus` контрактов остаётся включённым — архив читается.

**D-S6-5. Совмещающий роли видит всё по узлам `.all`** (предложение B, сверка §19).
- Узлы `bpp.invoices.all`, `bpp.agreements.all`, `bpp.accountable.all` — «все документы, а не только свои», как `bpp.requests.all` (`access/0017`).
- Строки у каждой роли: просмотр — у тех, кто сегодня видит всё (ФД, ТД, ОД, ГД, БУХ — по матрице узла, АДМ — где у него V).
- Правило `sees_all` в сервисах B (`invoices`, `agreements`, `accountable`, правка в зоне B) и у альтернатив/KPI (A) — по узлу, а не «просмотр без права создавать». СН, совмещающий ФД, перестаёт видеть только свои счета.

**D-S6-6. Сценарии SC — на тестовом стеке, данные — через сервисы.**
- Пилотная компания стенда заводится командами: `seed_hr_demo`, `bpp_assign_roles`, `bpp_configure_routes`, `seed_bpp_demo`.
- Каждый сценарий входит под пользователем нужной роли.
- Банковская выписка SC-006 — файл 1С из фикстур тестов выписки.

**D-S6-7. Окно выкатки (Q-E18) — решает пользователь.** До ответа ранбук пишется для варианта (а) «одно окно с репетицией, чек-листом и откатом из бэкапа». Вариант (б) отличается только разбивкой шагов на два окна — раздел ранбука «Если два окна».

## Global Constraints

- **Окружение.**
  - pytest — только в окружении **Python 3.14** (после задачи 1 — корневой `.venv`), команды из `backend/`.
  - Один прогон за раз на машине. Прогон дольше 10 минут — отдельным `nohup`-скриптом, не фоновой командой инструмента: та обрывается через 10 минут, а Windows-процесс python остаётся жить и портит следующий прогон.
  - Перед новым прогоном убедиться, что прошлого python нет.
- **Ветки и коммиты.** Ветки не создавать. Коммитить только файлы своей задачи. Правка в зоне B — отдельным коммитом с пометкой «зона B».
- **Межаппный доступ** — только `apps.<x>.interface`:
  - `tasks` ↔ `bpp` / `project`;
  - `contracts` → `bpp` (`migrated_targets`).
- **Тенантные изменения схемы — expand.** Новые поля nullable или с умолчанием в БД. Удаление старых — этап 8.
- **Ручки** — `api_view(module=…, level=…)` с явным уровнем; сторож `test_gate.py`.
- **Фронт.**
  - Строки — `t('<ключ>', 'Русский текст')`, ошибки — `reportApiError`.
  - Полный `npx vitest run` — без новых падений, кроме 8 известных hr.
  - `tsc` — не выше 148; `eslint` — чисто.
- **Документация** — `API.md`, `STRUCTURE.md`, `CLAUDE.md` в той задаче, что меняет ручки или структуру.

## Review Focus

1. **Заморозка не ломает чтение и не пропускает запись.**
   - `GET` списков и карточек `contracts` замороженной компании — 200.
   - Любой `POST`/`PATCH`/`PUT`/`DELETE` под `/api/contracts/` — 403 с текстом.
   - Соседняя незамороженная компания пишет как раньше.
   - Повтор `contracts_freeze` идемпотентен; `--undo` возвращает запись.
   - Тест — задача 4.
2. **Партнёр без пары и два партнёра на одного контрагента.**
   - Команда связки идемпотентна.
   - Конфликт «два партнёра → один контрагент `bpp`» — в отчёт, а не `IntegrityError`.
   - Повтор после ручной правки её не затирает.
   - Тест — задача 2.
3. **«Проект» правит доску, а не наоборот.**
   - Правка названия или сроков «Проекта» сразу видна на доске.
   - Попытка править их на доске — 422.
   - Правка «Проекта», которую доска принять не может (название занято другой доской), отклоняется целиком.
   - Тест — задача 3.
4. **Совмещающий роли.**
   - СН + ФД видит все счета.
   - СН без ФД — только свои.
   - ПМ — только свои и по участию в проекте, как раньше.
   - Тест — задача 5.
5. **Ранбук проходит без ручных правок.**
   - Репетиция на копии дампа идёт строго по шагам, каждый шаг — с проверкой результата.
   - Любое отступление записывается в протокол и правит ранбук.
   - Задача 8.
