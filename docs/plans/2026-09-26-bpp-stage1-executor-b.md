## Task B1.1: `hr.ActingAssignment` — временный исполнитель должности

**Решение D-22.** Одна сущность «временный исполнитель должности на период». Её назначают АДМ и HR вручную, без матрицы `hr.Substitution`. Она закрывает оба случая:
- должность пуста;
- держатель отсутствует.

**Модель** `apps/hr/models.py::ActingAssignment(HrBase)`:

| Поле | Тип | Смысл |
|---|---|---|
| `position` | FK `Position`, `CASCADE` | чью должность исполняют |
| `employee` | FK `Employee`, `CASCADE` | кто исполняет |
| `date_from`, `date_to` | `DateField` | период, обе границы **включительно**, оба обязательны |
| `basis` | `CharField(255)` | основание — приказ, распоряжение |
| `assigned_by_id` | `IntegerField(null)` | кто назначил (user_id из токена) |

- `CheckConstraint`: `date_to >= date_from`.
- Пересечения периодов разрешены: двое временных исполнителей одной должности на одни даты получают этапы оба, кворум «достаточно одного» решает первым.
- Миграция `hr/0038_acting_assignment`.

**Сервис** `apps/hr/services/acting_service.py`:
- `list_assignments(position_id=None, employee_id=None, active_on=None)`;
- `create(…)`, `update(id, …)`, `delete(id)`;
- `active_user_ids(position_ids, on_date) -> dict[int, list[int]]`.

Отказы — `ActingError` со `status`/`detail`:
- 404 — должность или сотрудник не найдены;
- 422 — неактивная должность, уволенный или удалённый сотрудник, сотрудник без учётной записи;
- 422 — даты не по порядку.

**Интерфейс** `apps/hr/interface.py` (§2.6):
- `resolve_position_users(position_ids, *, on_date: date | None = None)`. К держателям добавляются временные исполнители, действующие на `on_date` (по умолчанию — сегодня по местному времени). Только активные учётные записи, без дублей. Сигнатура обратно совместима.
- `acting_holders(position_id, on_date) -> list[int]`.

**Ручки** — по образцу матрицы замещений:
- `GET/POST /api/hr/v1/acting-assignments[/]`;
- `PATCH/DELETE /api/hr/v1/acting-assignments/<id>[/]`.

Гейт: чтение — `module="hr", level="read"`, правка — `level="admin"`, как у замещений. Роль АДМ модуля БЗО появится в A1.4 — тогда её выдают тем же уровнем. Схемы — `ActingAssignmentCreate`/`Update`/`Out` в `apps/hr/schemas.py`. Django-admin — регистрация модели.

**Тесты** (`apps/hr/tests/test_acting_assignment.py`, `apps/signoff/tests/test_acting.py`):
- на период исполнитель попадает в `resolve_position_users`, вне периода — нет (границы включительно);
- неактивная учётная запись не попадает;
- `acting_holders` — то же для одной должности;
- должность без держателя, но с временным исполнителем: маршрут по этой должности запускается, задача — у исполнителя;
- назначение после запуска процесса не добавляет задач уже активному этапу — прошлые задачи не переписываются;
- ручки: создание, правка, удаление, 422 на даты и сотрудника без учётки, 403 без роли `hr:admin`.

## Task B1.2: Флаги маршрута `signoff`

**Флаги — столбцы `ApprovalRoute`** (миграция `signoff/0013_route_flags`). Все выключены по умолчанию. На запуске они снимком копируются в `ApprovalProcess.route_flags` (JSON), потому что по ТЗ §16.1 п.2 маршрут фиксируется при отправке: правка маршрута идущий процесс не меняет.

| Флаг | Тип | Правило ТЗ |
|---|---|---|
| `forbid_self_approval` | bool | BR-061: автор не согласует свой документ |
| `reject_comment_min` | smallint, 0 = не требуется | BR-060: отказ и возврат — комментарий ≥ N символов (у БЗО N = 10) |
| `lazy_resolution` | bool | §16.1 п.2: исполнитель этапа определяется при его АКТИВАЦИИ, а не на запуске |
| `no_executor_notify_position_ids` | JSON list[int] | §16.1 п.5: кого уведомить о «Нет исполнителя» (АДМ, ГД) |
| `escalation_position_id` | int или null | BR-061: к кому уходит этап при самосогласовании, если нет временного исполнителя (ГД) |
| `self_skip_notify_position_ids` | JSON list[int] | D-22: кого уведомить, когда автор — сам ГД и этап пропущен (ФД) |

**Почему должности, а не роли.** В мастер-плане флаг назван `no_executor_notify_roles`. В словаре `signoff` «роль» — это HR-должность (`ApprovalRouteStageRole.position_id`), а у `access.interface` нет функции «держатели роли». Поэтому получатели и эскалация заданы должностями, как все согласующие маршрута. Отступление — в файл сверки.

**Состояние этапа** `StageState.NO_EXECUTOR = "no_executor"` — «Нет исполнителя».

**Разрешение исполнителей — одна функция** `engine._materialize_stage(process, stage)`. Она создаёт задачи этапа по снимку этапа (`approver_kind`, `role_ids`, `user_ids`, `approver_key`) и применяет флаги.

- **Без `lazy_resolution`** — как сейчас: все отобранные этапы разворачиваются на запуске, при нехватке исполнителя — `RouteUnusable`. Самосогласование применяется и здесь.
- **С `lazy_resolution`:**
  - на запуске разворачивается только первая группа, следующие — в `_advance` при активации;
  - группа должности без исполнителей → этап `NO_EXECUTOR`, событие `no_executor`, уведомление держателей `no_executor_notify_position_ids`;
  - документ ждёт: `current_order` стоит на этой группе, остальные этапы группы активны как обычно.
- **Повторная попытка:**
  - `engine.retry_no_executor(process_id)` переразрешает этапы `NO_EXECUTOR` текущей группы; нашлись исполнители — этап `ACTIVE`, уведомление;
  - вызывается ручкой `POST /api/signoff/v1/processes/<id>/retry-executors` (администратор) и периодической задачей `signoff.retry_no_executor_dispatch` (диспетчер + веер по компаниям, раз в 15 минут; data-миграция `PeriodicTask`). До первой компании диспетчер работает в `public`.
- **Самосогласование** (`forbid_self_approval`), для каждой группы должности этапа:
  1. автор (`initiator_id`) исключается из исполнителей; временные исполнители (B1.1) уже в списке;
  2. никого не осталось → исполнители `escalation_position_id` без автора, задача с тем же `position_id` группы, чтобы кворум шёл по роли;
  3. эскалации нет или автор и есть ГД → группа пропускается: без задач, событие `self_approval_skipped`, уведомление `self_skip_notify_position_ids`.

  Этап, у которого не осталось ни одной группы, согласуется сразу (`APPROVED`, событие). Для видов `USERS`/`SUBJECT` — то же с группой `None`. Вид `INITIATOR` флагом не затрагивается: такой этап явно просит подпись автора.
- **Защита на решении.** При `forbid_self_approval` `act()` от автора процесса отвергается (`SelfApprovalForbidden`, 403, текст BR-061), даже если задача откуда-то взялась.
- **Комментарий.** `reject_comment_min > 0` и решение `reject`/`rework` с `len(comment.strip()) < N` → `CommentTooShort` (422): «Комментарий слишком короткий: при отказе и возврате на доработку нужно не меньше N символов. Опишите причину — её увидит автор документа.» База для 422 — `InvalidDecision(SignoffError)`; `OptionError` переходит под неё.
- **Ручки маршрута.** `RouteCreate`/`RouteUpdate`/`RouteRead` получают флаги, `route_service` проверяет, что должности существуют и активны (`hr.interface.get_positions_brief`).
- **Фронт.** Раздел «Правила маршрута» в `RouteEditorPanel`:
  - флажки;
  - число символов;
  - выбор должностей (`PositionPicker`).

  В ходе согласования — плашка «Нет исполнителя» и события `self_approval_skipped`/`no_executor`.
- **Отложено.** Кто вправе править маршруты БЗО (ФД и АДМ, В-09) — роли появятся в A1.4. До этого правка маршрутов остаётся за администратором, в сверку.

**Тесты** (`apps/signoff/tests/test_route_flags.py`), по тесту на сценарий:
- без флагов — прежнее поведение, весь старый набор зелёный;
- `reject_comment_min=10`: 9 символов → 422 с текстом, 10 → решение принято; `approve` без комментария — можно;
- `forbid_self_approval`:
  - автор — один из двух держателей → задача только у второго;
  - автор — единственный держатель, есть временный исполнитель → задача у исполнителя;
  - автор — единственный держатель без исполнителя → задача у держателя `escalation_position_id`;
  - автор — сам держатель эскалации → группа пропущена, событие, уведомление `self_skip_notify_position_ids`;
  - `act()` от автора → 403;
- `lazy_resolution`:
  - исполнитель второго этапа, назначенный ПОСЛЕ запуска, получает задачу при активации;
  - этап без исполнителя → `NO_EXECUTOR`, уведомлены держатели `no_executor_notify_position_ids`, процесс идёт;
  - после назначения `retry_no_executor` → `ACTIVE`, задача у нового исполнителя;
  - первый этап без исполнителя → процесс заводится в `NO_EXECUTOR`, а не `RouteUnusable`;
- снимок: правка флагов маршрута после запуска не меняет идущий процесс;
- ручки маршрута принимают и отдают флаги, несуществующая должность → 409.

## Task B1.3: API `signoff` для модуля

**`decide_many(*, actor_id, items)`** — `interface` и `services/batch.py`.
- Элемент — `{task_id, decision, comment, option_key?}`.
- Каждый элемент — свой вызов `engine.act`, то есть своя транзакция.
- Ответ — `[{task_id, ok, error?}]`.

Ручка `POST tasks/batch-decision` переходит на него. Прежнее тело `{task_ids, decision, comment}` принимается, новое `{items: [...]}` — тоже.

**`current_holders(subject_type, subject_ids) -> {sid: {stage, users: [{id, name}], position, since}}`** — «Сейчас у» для колонки реестров (A2.1).
- Ключ ответа — каноническая строка.
- `stage` — название активного этапа (через « / », если параллельных несколько).
- `users` — держатели открытых задач с ФИО.
- `position` — название должности первой открытой группы или `null`.
- `since` — когда этап стал активным. Для этого у `ApprovalProcessStage` появляется столбец `activated_at` (миграция `0013` той же задачи B1.2 или своя `0014`). Он ставится на запуске и в `_advance`, у старых строк — время создания процесса.
- Объекты без идущего процесса в ответ не попадают.
- Этап `NO_EXECUTOR` отдаёт `users: []` и `stage` с пометкой.

**`pending_for_user(user_id) -> [{task_id, subject_type, subject_id, title, url, since}]`** — для ежедневной сводки (A1.5), в контексте текущей компании. Та же выборка, что у «Ждёт меня» (`presentation.list_inbox`), без полей экрана.

**Предсогласованные этапы** — `start_process(…, preapproved=[{position_id, actor_id, label}])` (D-26).
- Группа должности из списка не получает задач и считается согласованной.
- Этап, у которого все группы предсогласованы, создаётся сразу `APPROVED` с событием `stage_preapproved` (`label`: «Согласовано при выборе альтернативы»).
- Процесс начинается с первой несогласованной группы; предсогласовано всё — процесс сразу согласован.
- Позиция, которой нет в маршруте, — 409: предметная аппка ошиблась, молча согласовать нельзя.

**Тесты** (`apps/signoff/tests/test_module_api.py`):
- массовое решение — один отказ не откатывает остальные, у каждого элемента свой комментарий и вариант;
- «Сейчас у» после решения показывает следующий этап;
- `since` = время активации;
- `pending_for_user` — только активные этапы;
- предсогласованный этап не создаёт задач, есть событие, процесс начинается со следующего;
- предсогласовано всё → процесс согласован, колбэк `on_approved` вызван;
- неизвестная должность в `preapproved` → 409.
