**Goal:** Договор и единый счёт по ТЗ §09–§10:
- договор из плана закупок с маршрутом ФД → ТД → ОД → ГД и допсоглашения;

## Task B3.1: Договор

**Решения:**
- **D-09.** Открытый договор сам бюджет не занимает — его занимают счета.
- **D-14.** Ставка НДС — поле договора. По умолчанию — из справочника «страна × дата договора»; нет ставки — 16% с предупреждением. Ставку правят и автор, и согласующие. Правка пишется в аудит и подсвечивается ФД. Это меняет BR-031 и AC-006: «изменить ставку вручную СН не может» больше не действует.
- **D-18.** Допсоглашение — договор с `parent_agreement`, форма та же, у него своя область маршрута `supplementary`.
- **D-19.** В договоре минимум одна позиция.
- **D-20.** Если контрагент не «Проверенный», автор подтверждает его в окне при отправке. Подтверждение пишется в аудит и метку не ставит.

**Модели** (`apps/bpp/models/agreements.py`):

| Модель | Поля | Ограничения |
|---|---|---|
| `Agreement` (`BppModel`, `signoff.Approvable`, `SIGNOFF_SUBJECT_TYPE = "bpp.agreement"`) | `number` («ДГ-ГГГГ-NNNNNN», при первом сохранении), `ext_number` (1–50), `ext_date`, `name` (3–500), `project_id`, `article_id`, `counterparty` (FK), `agreement_type` (`works`/`goods`), `is_open`, `amount` (null у открытого), `currency`, `with_vat`, `vat_rate`, `vat_rate_source` (`refdata`/`manual`), `vat_amount` (CALC-008), `valid_to`, `status` (`draft`/`on_review`/`active`/`rework`/`rejected`/`fulfilled`/`terminated`/`replaced`), `status_comment`, `author_id`, `parent_agreement` (FK на себя, null), `alt_limit` (лимит АП, 3 — поле для A5.1), `is_migrated` (B6.1) | `UNIQUE(number)`; `UNIQUE(counterparty, ext_number, ext_date)` частичный — кроме `rejected`/`replaced` (BR-032); `CHECK is_open OR amount > 0`; `CHECK valid_to ≥ ext_date` |
| `AgreementItem` (`BppModel`) | `agreement` (FK, CASCADE — только у черновика), `request_item` (FK на `PurchaseRequestItem`, PROTECT), `qty`, `amount` (null у открытого) | `UNIQUE(agreement, request_item)`; `CHECK qty > 0` |

Видимый статус — `status`, согласование ведёт `signoff` (Q-C08). Отозванный «На согласовании» возвращается в `draft`.

**Регистрация в `signoff`** (`approval_hooks.py`):
- `bpp.agreement`:
  - маршрут ФД → ТД → ОД → ГД с флагами БЗО;
  - `scope_of` — `""` у договора и `"supplementary"` у допсоглашения;
  - `facts`: сумма, прирост суммы допсоглашения (`amount_delta`), тип, открытый, группа статьи;
  - колбэки: `on_started` → `on_review`, резерв; `on_approved` → `active` (у допсоглашения: родитель остаётся действующим документом, суммы складываются); `on_rework` → `rework`, резерв снят; `on_rejected` → `rejected`, позиции освобождены; `on_cancelled` → `draft`;
  - варианты голоса (`options`/`on_option`) — не здесь, а в B5.1.
- **Допсоглашение без изменения суммы.** Стартовая настройка D-18: без этапов. Если по фактам маршрута не остаётся ни одного этапа, допсоглашение вступает в силу сразу, с событием в аудите. ✅ Сделано 27.09 флагом маршрута `skip_unmatched_groups` (`signoff/0016`), а не исключением `NoApplicableStages`: группа без сошедшегося условия и без «иначе» пропускается, а если этапов не осталось, движок заводит процесс и сразу закрывает его «согласовано» (события `started` + `no_applicable_stages`). `bpp` получает обычные `on_started` → `on_approved` и ничего не различает.
- `bpp_configure_routes` (из B2.2) получает `--fd`, `--gd` и заводит маршруты договора и допсоглашения. Этап ФД допсоглашения — с условием `amount_delta != 0`, маршрут допсоглашения — с флагом `skip_unmatched_groups`.

**Сервисы** (`apps/bpp/services/agreements/`):
- `agreements.py`:
  - `create_from_plan(item_ids, …)` — через `plan.validate_selection(target="agreement")`; проект, статья и тип — из заявки; сумма по умолчанию — Σ плановых сумм позиций;
  - `update_draft` — только `draft`/`rework`;
  - `submit`:

    - закрытый договор: Σ позиций = сумме — BR-033;
    - файл «Договор» приложен;

Отдельных `vat.py` у договора и счёта не будет: оба зовут `calc`.

- `execution.py` — блок «Исполнение»: счета по договору, оплачено факт, остаток по договору (CALC-009).

**Тесты** (`apps/bpp/tests/agreements/`):
- заблокированный контрагент → 422 E-CTR-01;
- непроверенный контрагент без подтверждения → 422, с подтверждением — запись в аудите;
- НДС по умолчанию из справочника на дату договора, изменённый — в аудите; нет ставки → E-VAT-01;

- позиция открытого договора не занимает бюджет, пока нет счёта (D-09).

## Task B3.2: Единый счёт

**Решения:**
- **D-11.** Одна модель `Invoice` с основанием «без договора» / «по договору». Аванс (предоплата) — признак. Частичная оплата и транши — несколько отметок БУХ по одному счёту (Q-B24).
- **D-12.** Решение ФД — одноэтапный маршрут `signoff`: `approve` = «Оплатить» с плановой датой, `reject` = «Не к оплате», `rework` = «Вернуть». Действия БУХ — доменные операции, не этапы.
- **D-13.** Закрывающие документы (АВР, накладная, счёт-фактура) — только **после** оплаты. Это меняет BR-051 и AC-009 и снимает E-INV-04.
- **D-15.** Курс — НБРК на дату счёта. Фактический курс редактируем у счёта и у отметки оплаты.
- **D-16.** Порог — сумма в KZT с НДС, МРП на дату счёта контрагента.
- **D-17.** Дробление — только значок для ФД, запрета нет.

**Статусы** (мастер-план §2.5):
- основная цепочка: Черновик → На рассмотрении ФД → К оплате / Не к оплате / Возвращён на доработку → Оплачено частично → Оплачено → Ждёт закрывающих → Документы предоставлены → Закрыт;
- финальные: «Отменён» и «Заменён альтернативой» (B5.1).

Статус сверки с банком — отдельное поле, основной статус он не блокирует.

**Модели** (`apps/bpp/models/invoices.py`):

| Модель | Поля | Ограничения |
|---|---|---|
| `Invoice` (`BppModel`, `signoff.Approvable`, `SIGNOFF_SUBJECT_TYPE = "bpp.invoice"`) | `number` («СЧ-ГГГГ-NNNNNN», BR-070), `basis` (`no_contract`/`contract`), `agreement` (FK, null), `project_id`, `article_id`, `counterparty` (FK), `ext_number`, `ext_date`, `amount`, `currency`, `rate`, `rate_source` (`nbrk`/`manual`), `amount_kzt` (CALC-012), `with_vat`, `vat_rate`, `vat_amount`, `purchase_type`, `is_advance`, `due_date` (по умолчанию дата + 5 раб. дней), `status`, `status_comment`, `fd_decided_at`, `planned_pay_date`, `docs_required` (json: `avr`, `waybill`, `vat_invoice`), `docs_requested_at`, `recon_status`, `paid_bank_amount` (пишет A4.2), `author_comment` (≤1000), `author_id`, `is_migrated` | `UNIQUE(number)`; `UNIQUE(counterparty, ext_number, ext_date)` частичный — кроме `cancelled`/`replaced` (BR-045); `CHECK amount > 0`; `CHECK basis = 'contract' ⇔ agreement IS NOT NULL` |
| `InvoiceLine` (`BppModel`) | `invoice` (FK, CASCADE — только у черновика), `request_item` (FK), `qty`, `amount` | `UNIQUE(invoice, request_item)`; `CHECK qty > 0, amount > 0` |
| `PaymentMark` (`BppModel`) | `invoice` (FK), `pay_date`, `amount`, `pp_number`, `rate` (фактический курс), `marked_by_id`, `cancelled_at`, `cancelled_by_id`, `cancel_comment` | Σ неотменённых ≤ `amount` (BR-052, сервис под блокировкой счёта) |

**Регистрация в `signoff`** — `bpp.invoice`, один этап ФД:
- **«Оплатить».** Решение идёт через доменную ручку `invoices/<id>/decision`. В одной транзакции она делает `lock_line` → проверку бюджета «на текущий момент» (§26.2) → записывает `planned_pay_date` → вызывает решение `signoff`.
- **Страховка для общего инбокса.** Этапу ставится `requirement_key="bpp:budget"`. Тогда «согласовать» из общего инбокса пройдёт через ту же проверку (`check_requirement`) и не обойдёт бюджет. Плановая дата в этом случае — срок оплаты.
- **Колбэки:**
  - `on_approved` → «К оплате», уведомление БУХ;
  - `on_rejected` → «Не к оплате», позиции и сверхплановая сумма освобождены;
  - `on_rework` → «Возвращён на доработку»;
  - `on_cancelled` → «Отменён» или черновик.

**Сервисы** (`apps/bpp/services/invoices/`):

  - `create_from_plan(item_ids)` и `create_from_agreement(agreement_id, item_ids)`;

- **AC-005.** 4 325 000,00 можно, 4 325 000,01 — E-INV-01. Черновик с датой прошлого года — по МРП прошлого года. Валютный счёт сравнивается в KZT по курсу на дату.

- **AC-013.** Двойное «Оплатить» с тем же ключом — одно решение, одна запись аудита, одно уведомление.
- **Дубль.** Дубль счёта → E-INV-03 со ссылкой на существующий.
- **Статусы оплаты.** Частичная отметка → «Оплачено частично», вторая до полной суммы → «Оплачено». Отметка сверх суммы → 422 BR-052.
- **Отмена отметки.** Проходит при `paid_bank_amount == 0` и даёт 409, когда он больше 0.
- **Закрывающие документы.** До «Оплачено» запросить их нельзя. После запроса — «Ждёт закрывающих», вложение → «Документы предоставлены», приём → «Закрыт», возврат — обратно.
- **Массовое решение ФД.** Один счёт с превышением бюджета отказан с причиной, остальные прошли.
- **Обход домена.** «Согласовать» из общего инбокса при превышении бюджета отказывает (`bpp:budget`).
- **Дробление.** Значок стоит на третьем счёте без договора одному контрагенту за 30 дней сверх порога.
- **Сводка.** `closing_docs_pending_for_user` отдаёт только счета автора в «Ждёт закрывающих».

## Task B3.3: «Задействовано» полностью

`committed.py` (B2.4) получает недостающие слагаемые — одна строка в списке каждое:
- позиции договоров «На согласовании» / «Действует» — только у закрытых договоров (D-09);
- строки счетов со статусов от «На рассмотрении ФД», кроме «Отменён» и «Не к оплате».

Позиции расторгнутого договора после расторжения считаются только его счетами (Q-D02).

Проверки остатка под `lock_line` — все четыре места мастер-плана §2.5:
- отправка заявки — уже есть с B2.2;
- «Отправить ФД» — сверхплановая часть строк (BR-043); сумма удерживается с момента отправки и снимается при «Не к оплате»;
- «Оплатить» — повторная проверка «на текущий момент»;
- сохранение и отправка договора — BR-034.

План закупок (B2.3) и остатки позиций (CALC-005, CALC-006) берут договоры и счета. Метка «В договоре на согласовании» заполняется. Блок «Исполнение» заявки показывает договоры и счета.

**Тесты** (`apps/bpp/tests/budget/test_committed.py`, дополнение):
- превышение строки счёта над планом покрывается остатком, иначе текст BR-043;
- «Не к оплате» освобождает сверхплановую сумму;
- счета по открытому договору уменьшают остаток статьи, сам договор — нет;
- расторжение освобождает только неосвоенное;
- агрегат совпадает с эталоном на случайном наборе из заявок, договоров и счетов;
- ночная сверка по-прежнему находит подложенное расхождение.
