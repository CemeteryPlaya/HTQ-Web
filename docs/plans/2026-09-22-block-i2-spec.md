# Блок I.2 — хвосты блока I и переход на поддомены компаний (спека)

**Дата:** 22.09.2026. **Предшественник:** блок I «Единая модель прав»
(`docs/plans/2026-09-17-block-i-single-rbac.md`, коммиты `1f69716..9600982`).
**Следом:** блок J (документы, финальная сверка) — конец рефакторинга
структуры группы (`docs/plans/2026-09-14-group-structure-roadmap.md` §5.J, §7).

## 1. Зачем этот блок

Блок I закрыт, но оставил две вещи, без которых рефакторинг нельзя назвать
законченным:

1. **Блок I нельзя выкатить.** Гейты `api_view(module=, level=)` требуют
   контекста компании; на голом домене `htq.group`, через который сегодня
   ходят на бою, `permission_level` отвечает `none` всем, кроме
   суперпользователя. Nginx и фронт поддомены уже поддерживают
   (`infra/nginx/default.conf::server_name`, `frontend/src/lib/auth/companySwitch.ts`),
   не хватает: коротких адресов, приземления с голого домена, ссылок на
   конкретную компанию и инфраструктурного чеклиста.
2. **Хвосты финального ревью блока I** — одно незаписанное сужение доступа,
   утечка названий должностей через общий каталог ролей, экран, который
   показывает неправду, остатки `hr_level` в интерфейсе, слепые пятна сторожей.

## 4. Часть 1 — поддомены

### S1. Псевдоним компании `Company.subdomain`

- Поле `subdomain`: `SlugField`, `null=True`, `unique=True`, до 32 символов,
  нижний регистр, `[a-z][a-z0-9-]*` — та же форма, что понимает регулярка
  nginx (`(?<company>[a-z][a-z0-9-]*)`).
- Валидация (в сервисе, не только в форме):
  - зарезервированные метки запрещены: `www`, `api`, `admin`, `mail`,
    `static`, `cdn`, `grafana`, `media`, `sfu`, `ws`, `localhost`;
  - псевдоним не совпадает со `slug` ДРУГОЙ компании; новый `slug` не
    совпадает с чужим `subdomain` — иначе один хост резолвился бы в две
    компании.
- Миграция данных `companies/0006` (схема поля — `0005`): для существующих строк с пустым
  `subdomain` проставить `hi-tech-qazaqstan → htq`, `hi-tech-systems → hts`,
  `kazakhstan-engineering-group → keg`, `hi-tech-group → group`; строки, которой
  нет, — пропустить; обратная операция — обнулить ровно эти.
- Задаётся: `company_create --subdomain <метка>`; `PATCH companies/v1/<slug>`
  (платформенный администратор — та же проверка, что у остальных
  платформенных полей); поле в `CompanyFormDialog`.
- Отдаётся: `companies.interface.get_company(...)` (сериализатор реестра),
  `GET companies/v1/me` (список своих компаний) — для фронта.

Рассмотренные альтернативы: `map` в nginx (отклонено — каждая новая компания
потребовала бы правки инфраструктуры); переименование слагов (отклонено —
слаг есть имя схемы `co_<slug>` и значение в `RoleAssignment`, `PositionRole`,
токенах и сводках холдинга).

### S2. Разбор хоста в `CompanyContextMiddleware`

Nginx не меняется: он уже кладёт первую метку хоста в `X-HTQ-Company`.

- `htqweb/middleware/company_context.py` получает метку и спрашивает
  `companies.interface.resolve_host_label(label) -> dict | None`
  (кэш — как у `get_company`, ключ `company:label:<label>`):
  1. компания с `subdomain == label` → она;
  2. иначе компания с `slug == label` **и пустым `subdomain`** → она;
  3. иначе `None` → 404 «Компания не найдена» (как сегодня).
- Итог: у каждой компании ОДИН канонический хост. Адрес по слагу у компании с
  псевдонимом отвечает 404 — не два origin'а с раздельным `localStorage`.
  Компании без псевдонима (стенд, `*.localhost` в разработке) работают по
  слагу, как раньше.
- Дальше всё по-прежнему по СЛАГУ: `set_company(slug)`,
  `apply_search_path(slug)`, claim `company` в токене, сверка claim с
  контекстом в `api_view`.
- Кэш реестра (`companies/interface.py::_cached`) живёт 5 секунд и явно не
  сбрасывается — смена псевдонима вступает в силу не позже чем через 5 с.
  Так же сегодня ведёт себя `company:slug:*`; отдельной инвалидации не
  заводим.

### S3. Ссылки на страницы компании

- `companies.interface.public_url(slug) -> str`: `https://<subdomain или
  slug>.<корень>`, корень — хост из `PUBLIC_BASE_URL`
  (`https://htq.group` → `htq.group`); пустой `PUBLIC_BASE_URL` → поведение
  вызывающего как сегодня (фолбэк по заголовкам запроса).
- Переходят на неё: кадровые share-ссылки (`apps/hr/views.py` — построитель
  публичного URL `_public_url`/`_share_link_public_path`; публичные ручки
  `public_org_view`/`public_employee_view` читают таблицы компании и на голом
  домене ничего не найдут).
- НЕ переходят (общие сервисы, живут на голом домене): приглашения в
  конференцию (`apps/cms/services/conference_invite_service.py`,
  `apps/cms/views.py::_origin`), ссылка в письме записи конференции
  (`apps/conference/tasks.py`), утренняя сводка (`apps/core/tasks.py`).
- `htqweb/settings/base.py::_trusted_origins()` дополнительно выводит
  `https://*.<корень>` из `PUBLIC_BASE_URL` (Django ≥ 4 понимает подстановку
  поддомена в `CSRF_TRUSTED_ORIGINS`).

### S4. Фронт

- `GET companies/v1/me` отдаёт `subdomain`; тип `CompanyBrief` во фронте — тоже.
- `companySwitch.ts`: `switchCompany(company)` строит хост из `subdomain ??
  slug`; `companyFromHost()` возвращает МЕТКУ, а `CompanySwitcher`
  сопоставляет её с `subdomain ?? slug` из списка.
- Приземление на голом домене (`companyFromHost(host) === null`) после
  входа — новая страница `CompanyPicker` (маршрут `/companies/choose`):
  - 0 компаний → сообщение «нет доступа ни к одной компании группы»,
    кнопка выхода;
  - 1 компания → немедленный редирект на её хост (с сохранением пути, если
    пришли по глубокой ссылке);
  - ≥2 → список карточек компаний, клик — редирект.
- Любой авторизованный маршрут на голом домене ведёт на `/companies/choose`.
  Исключения (работают на голом домене как сегодня): вход, регистрация,
  `/join/<token>` (конференции), django-admin. Публичные share-страницы
  кадров живут на поддомене компании (S3) и там доступны без входа.
- Сессия переезжает через refresh-cookie на `.htq.group` — механизм уже есть
  (`REFRESH_COOKIE_DOMAIN`), не меняется.

### S5. Чеклист выкатки поддоменов (документ, не код)

Отдельный файл `docs/deploy/subdomains-runbook.md` + ссылка из roadmap §7.
Шаги 1–4 — подготовка без кода, её можно сделать заранее (голый домен при
этом продолжает работать как сегодня); шаги 5–7 — внутри окна выкатки
блоков I + I.2 (§8):

1. Cloudflare DNS: запись `*` (A на `77.243.80.208` или CNAME на `htq.group`),
   **проксирование включено**. Universal SSL покрывает `*.htq.group` одного
   уровня — псевдонимы `htq`, `hts`, `keg`, `group` одного уровня.
2. Origin-сертификат на сервере (`/etc/htq-certs/origin.pem`): проверить SAN
   (`openssl x509 -in origin.pem -noout -ext subjectAltName`) — нужны
   `htq.group` и `*.htq.group`; если нет — перевыпустить в панели Cloudflare
   (Origin Server → Create Certificate) и заменить файлы.
3. Режим SSL/TLS в Cloudflare — «Full (strict)».
4. `.env`: `SFU_ALLOWED_ORIGINS=https://htq.group,https://*.htq.group`;
   `PUBLIC_BASE_URL=https://htq.group` не менять.
5. Код блоков I + I.2 при закрытом трафике; `migrate_shared` (поле,
   псевдонимы, миграции `access`) выполняется при старте контейнера.
6. Проверка: `curl -sI https://htq.htq.group/` → 200;
   `curl -s https://htq.htq.group/api/companies/v1/me` без токена → 401 (не
   404); вход на `htq.group` → экран выбора/редирект; переключение компаний;
   конференция на `htq.htq.group` (сигналинг проходит проверку Origin).
7. Шаги переноса прав блока I (§7) — и только затем открыть трафик.

## 5. Часть 2 — хвосты RBAC

### R1. Незаписанное сужение (финальное ревью I, n10)

`apps/hr/views.py::_set_identity_approver` стоит под `level="admin"`;
держатель именной роли с `hr.identity.manage` без единого delete-признака

засеянные роли это не меняет. Тест: именная роль с одним ключом
`hr.identity.manage` → 200; `staff_without_roles` → 403.

### R2. Роль компании `Role.company_slug`

- Миграции `access/0009` (поле) и `access/0010` (данные).
- Поле `company_slug`: `CharField`, `null=True`, индекс. Пусто — роль общая
  для группы (все системные и созданные в редакторе). Заполнено — роль одной
  компании.
- `access_backfill_positions` заполняет его у `hr-custom-<slug>-<id>`;
  миграция данных дописывает уже созданные (слаг — между префиксом
  `hr-custom-` и хвостом `-<digits>`).
- Каталог (`GET access/v1/roles` и соседние чтения): общие роли + роли
  текущей компании запроса; суперпользователь — все, с меткой компании.
- Выдача: `PositionRole` и `RoleAssignment` с ролью другой компании
  отвергаются в сервисе (422 с понятным текстом) и `CheckConstraint`-ом не
  выражаются (слаги в разных таблицах) — только сервисная проверка + тест.
- `Role.title` у именной роли обрезается до 255 символов (n7).
- Резолвер прав не меняется: назначение чужой роли не может возникнуть.

### R3. Членство из django-admin (n1)

`apps/companies/admin.py::CompanyMembershipAdmin` создаёт членство мимо
`membership_service.grant_membership` — человек остаётся без
`employee-basic`. → `save_model` новой строки через `grant_membership`.
Докстринги, называющие `grant_membership` «единственной точкой», — поправить
на правду (единственная точка ЛОГИКИ, admin идёт через неё).

### R4. Остатки `hr_level` (n8)

- `frontend/src/components/hr/EmployeeFormDialog.tsx` (~1427, инлайн-создание
  должности): убрать селект «Уровень HR-доступа».
- `frontend/src/pages/hr/HRPositions.tsx` (~1006, список должностей): убрать

- Бэкенд: входная схема должности (`apps/hr/schemas.py::PositionPermissions`)

### R5. Удалить экран «Уровни доступа»

`/admin/access-levels`: маршрут (`routeDefinitions.ts`), пункт меню,

`hr.accessLevels.*` (сторож `translationKeys` — зелёный, осиротевших ключей
нет). Кто какие права имеет — редактор ролей и диалог ролей должности.

### R6. Кнопки удаления = гейт сервера

Четыре DELETE, поставленные под `hr:admin` финальной волной I (рулинг O):
закрытие вакансии (`HRVacancies`), удаление отклика (`HRApplications`),
удаление записи учёта времени (`HRTimeTracking`), удаление документа
(`HRDocuments`). Кнопка удаления — `permissions.atLeast('hr', 'admin')`;
остальные действия экранов (`companyWide`) — без изменений. Тест на экран:
`write` + компания → кнопки нет; `admin` → есть.

### R7. Сторожа и тесты

- `apps/access/tests/test_gate.py`:
  - метод CBV (`get/post/put/patch/delete` в классе, унаследованном от
    `ApiView`) без декоратора — нарушение;
  - вызовы фабрик-декораторов с умолчанием уровня (`access/views.py::write`)
    засчитываются как «уровень есть» только если умолчание объявлено явно в
    сигнатуре фабрики — сторож читает его, а не пропускает вызов.
- Тест «явный список == пресет → роль уровня» различает ветку (сейчас
  зелёный и с отключённой веткой).
- `access_backfill_basic`: тест «компания без участников».
- `access_backfill_positions`: тест «первый держатель без уровня — должность
  пропущена, расхождение напечатано».
- `apps/companies/tests/test_api_modules_memberships.py::test_memberships_grant_list_revoke`
  — порядкозависим (id созданного пользователя совпадает с 9 из
  `superuser_token()`): развести идентификаторы.

### R8. Один расчёт ролей на запрос (m3)

Гейт `htqweb/http.py` считает роли (`access.resolution(...)`) и кладёт
результат в `request.access_resolution`; `apps/hr/rbac.py::resolve(request)`
переиспользует его, если он есть и компания совпадает. Явный атрибут
запроса, не `contextvar` (довод докстринга `Resolution` сохраняется). Тест:
кадровая ручка с узловой проверкой делает ровно один расчёт ролей
(`django_assert_num_queries` или счётчик вызова).

## 8. Порядок выкатки (итог для roadmap §7)

1. **Заранее, без кода** (S5, шаги 1–4): DNS `*`, SAN origin-сертификата,
   режим SSL, `SFU_ALLOWED_ORIGINS`. Голый домен продолжает работать.
2. **Одно окно выкатки, трафик закрыт**:
   1. новый образ (блоки I + I.2); `migrate_shared` при старте контейнера —
      роли `access/0005`–`0008`, поле роли компании, `subdomain` и
      псевдонимы;
   2. `migrate_companies`;
   3. `access_backfill_positions --dry-run` → прочитать сводку →
      `access_backfill_positions` → `access_backfill_basic`;
   4. проверка поддоменов (S5, шаг 6);
   5. открыть трафик. Пользователи приходят на `htq.group`, входят и
      попадают на свою компанию (S4).
3. Гейты и поддомены неразделимы: выкатить одно без другого нельзя — без
   поддоменов гейты закрывают всё, без гейтов поддомены ничего не
   защищают.
