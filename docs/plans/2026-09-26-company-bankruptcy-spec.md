# Банкротство компании с преемником (спека)

**Дата:** 2026-09-26
**Ветка:** `sanzhar`
**Основание:** [дизайн мультикомпанейности](../multi-company-tenancy-design.md) — таблица решений
(«Закрытие компании: архив (только чтение) + перенос активов на компанию-преемника»), §4 подпроект 4
(«банкротство с преемником, перенос людей / техники / договоров»), §5 поле `Company.successor`.
**Предшественник:** [архив — только чтение](2026-09-25-archive-read-only-spec.md) — банкротство
заканчивается архивом в этом режиме.

## 1. Цель и критерий успеха

Компанию группы можно закрыть с преемником одной операцией: указать компанию, которая
принимает дела, — её сотрудники получают доступ к преемнику, сама компания уходит в архив
(только чтение), а связь «кто чей преемник» сохраняется в реестре.

Критерий успеха:
1. `manage.py company_bankrupt --company X --successor Y` и кнопка «Банкротство…» в реестре
   компаний (только суперпользователь) делают одно и то же через один сервис.
2. Каждый участник X с **действующей** учёткой после операции состоит в Y (членство + базовая
   роль `employee-basic`, как у любого нового членства). Уже состоявшие в Y ничего не теряют.
3. `X.successor = Y`, X — в архиве (режим «только чтение»), сводки холдинга пересобраны.
4. Сухой прогон (`--dry-run` / предпросмотр в реестре) показывает, сколько людей получат
   доступ к Y, и ничего не меняет.
5. Повтор операции безопасен: та же пара (X, Y) — довыдать недостающие членства и ничего не
   сломать; другой преемник у уже закрытой X — отказ.

## 3. Решения заказчика (26.09.2026)

| Вопрос | Решение |
|---|---|
| Что значит «перенос людей» | **Только членство** в преемнике. Карточки `hr`, история, документы, отпуска остаются в архиве банкрота; карточки у преемника кадровик заводит сам. |
| Техника (`tasks.Equipment`) | **Не переносится** — остаётся в архиве, преемник заводит свою. |
| Договоры (`contracts`) | **Вне спеки** — остаются в архиве банкрота; перенос, если понадобится, — задача второго разработчика без общего механизма. |
| Запуск | **Команда + кнопка в реестре** (только суперпользователь, с предпросмотром). |

Решения, принятые при проектировании (цена ошибки — §9):
- Флаг «компания по умолчанию»: если у человека X была компанией по умолчанию, членство в Y
  создаётся с `is_default=True` — иначе после входа его вело бы по алфавиту.
- Восстановление банкрота (`restore_company`) снимает `successor`: компания снова живёт сама по
  себе. Выданные в Y членства не отзываются.
- Уже заархивированную X без преемника закрыть с преемником можно (архив мог случиться раньше
  решения о преемнике); X с другим преемником — 409.

## 4. Сервис

`backend/apps/companies/services/lifecycle.py`:

```python
class SuccessorInvalid(LifecycleError):   # 422, code "successor_invalid"
class SuccessorConflict(LifecycleError):  # 409, code "successor_conflict"

@dataclass(frozen=True)
class BankruptcyResult:
    company: Company
    successor: Company
    members_total: int      # участники X с действующей учёткой
    members_granted: int    # из них получили членство в Y сейчас (или получили бы — dry_run)
    members_already: int    # уже состояли в Y
    archived: bool          # X переведена в архив этим вызовом (False — уже была)
    dry_run: bool

def bankrupt_company(slug: str, successor_slug: str, *, dry_run: bool = False) -> BankruptcyResult:
```

Порядок:
1. `company = get_company_or_raise(slug)`, `successor = get_company_or_raise(successor_slug)`
   (404 `not_found`).
2. Проверки: `successor_slug == slug` → `SuccessorInvalid` («компания не может быть собственным
   преемником»); `successor` не действующая → `SuccessorInvalid` («преемник должен быть
   действующей компанией»); у `company` уже есть другой преемник → `SuccessorConflict`.
3. `member_ids = interface.active_member_ids(slug)`; уже в Y — `set(CompanyMembership... company=successor)`.
4. `dry_run` — вернуть подсчёт, ничего не менять.
5. Иначе одной транзакцией: для каждого id — `membership_service.grant_membership(successor, id,
   is_default=<было ли членство в X по умолчанию>)`; `company.successor = successor`;
   сохранить. Затем архив — `archive_company(slug)` (его гейт `LastActiveCompany` не сработает:
   Y действующая; он же пересобирает сводки; уже архивная X — `archived=False`).
6. Строка лога `company_bankrupt slug=… successor=… granted=… already=…`.

`restore_company` дополнительно обнуляет `successor` (в том же `save`).

## 5. Команда и HTTP

- `manage.py company_bankrupt --company X --successor Y [--dry-run]` — печать сводки
  («участников с действующей учёткой: N, получат доступ к Y: M, уже состоят: K; компания X
  переведена в архив»); `LifecycleError` → `CommandError`.
- `POST companies/<slug>/bankrupt` (и со слэшем) — фабрика `@platform`, первой строкой
  `deny_unless_platform_admin`; тело `{"successor": "<slug>", "dry_run": false}`; ответ
  `{"company": CompanyRead, "successor": CompanyRead, "members_total", "members_granted",
  "members_already", "archived", "dry_run"}`; ошибки — конверт `{"detail", "code"}`.
  Реестр самообслуживания менять не нужно: `@platform` в нём одной записью `scoped`.
- `CompanyRead` получает `successor_slug: str | None` (свойство модели, как `parent_slug`).

## 9. Риски

1. **Перенос только членств** — у преемника у людей нет карточек и должностей: без кадровика
   они видят только то, что даёт `employee-basic`. Это решение заказчика; сводка операции
   называет число людей, чтобы кадровик знал объём.
2. **`is_default` переезжает** — человек, у которого X была по умолчанию, а Y — нет, после входа
   попадёт в Y. Если ошибка — убрать передачу флага (одна строка). Людям, которые **уже**
   состоят в Y, флаг «по умолчанию» не переносится — действует правило «уже состоящих не
   трогать» (§1 п. 2, §3): их членство в Y не меняется, и после входа их ведёт прежним порядком (по
   тому членству, что у них по умолчанию, иначе — по алфавиту). Это сознательно: операция
   банкротства не переписывает уже существующие членства преемника.
3. **Членства в Y не отзываются при восстановлении X** — если восстановление было ошибкой
   банкротства, лишние членства снимаются экраном участников руками. Флаг «по умолчанию» при
   восстановлении тоже не возвращается: у перенесённых людей, у которых X была по умолчанию,
   теперь две компании «по умолчанию» (X и Y), и после входа их ведёт по алфавиту между ними.
   Поправить флаг — в django-admin (`CompanyMembershipAdmin`): экран участников флаг только
   показывает.
4. **Договоры и техника остаются в архиве** — работа по ним у преемника начинается с нуля;
   контроль — не наша зона (договоры) или решение заказчика (техника).
