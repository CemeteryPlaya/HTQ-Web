# БЗО, B6.1 — перенос данных из `contracts` в `bpp` (план исполнителя B)

**Цель.** Команда `bpp_migrate_contracts` переносит живые данные старого раздела «Договоры» в модуль БЗО так, чтобы:
- люди продолжили работу с открытыми документами в новом модуле;
- остатки статей бюджета после переноса совпали с остатками до него в пределах отчёта о расхождениях.

Задача мастер-плана — B6.1. Приёмка:
- повторный прогон ничего не дублирует;
- остатки статей после переноса равны остаткам до переноса;
- конфликт кодов статей останавливает перенос без карты.

**Стартовая точка:** `new-module-BPP-ruslan` после PR #41.

**Спека:**
- мастер-план: B6.1, D-06, D-09, D-35, §2.7;
- ответы Q-A05, Q-B36, Q-D01, Q-D03, Q-D05, Q-D06, Q-E15;
- ТЗ §21 (файлы) и CALC-002.

## Решения

| # | Решение | Источник |
|---|---|---|
| D-B61-1 | **Закрытые документы остаются в `contracts`.** Потраченное ими переносится одной скрытой технической «заявкой переноса» на статью проекта — «сальдо до перехода»: статус «Утверждена», `is_migrated`, одна позиция на сумму. CALC-002 учитывает её как обычную утверждённую позицию, поэтому остаток статьи совпадает со старым | Руслан 30.09 (вопрос о закрытых) |
| D-B61-2 | **Документы «На согласовании» переносятся черновиком.** Старый процесс signoff отзывается, автор отправляет документ заново по маршруту БЗО. Команда печатает, кому переотправить | Руслан 30.09 |
| D-B61-3 | **Программы → статьи только по карте на существующие статьи.** Недостающие статьи УК заводит в «Справочниках» заранее. Статья, которой нет в справочнике, останавливает перенос с перечнем. `refdata` (зона A) не меняется | Руслан 30.09 |
| D-B61-4 | **Администратор → «Проект» по карте проектов.** Код «Проекта» неизменяем, поэтому его задаёт человек. Команда строит черновик карты: если администратор связан с доской задач, а доска — с «Проектом», в карте сразу стоит этот «Проект». Руководитель — `Administrator.user_id` | умолчание |
| D-B61-5 | **Бюджет — один на проект, годы суммируются** по статье (D-06). В новый бюджет входят только годы в KZT. Бюджет в другой валюте не переносится и попадает в отчёт. Утверждённые годы складываются в действующую версию. Проект, у которого есть только неутверждённые годы, получает бюджет-черновик | D-06, мастер-план |
| D-B61-6 | **Каждый платёжный документ старого договора становится счётом по договору.** Сюда входят оплата по договору, предоплата, АВР и накладная. Статусы: черновик и «На согласовании» → «Черновик»; «Ожидает оформления бухгалтерией» → «К оплате»; «Закрыт» → «Оплачено» с отметкой оплаты. Файл АВР или накладной прикладывается к счёту как закрывающий документ соответствующего типа | B6.1 («АВР и накладные открытого договора без счёта → отдельный счёт … „Оплачено“ с файлом») |
| D-B61-7 | **Файлы платёжных поручений не переносятся** — в ТЗ у отметки оплаты есть только номер ПП, а типа файла «ПП» нет. Они читаются в `contracts`. «Номер проводки» уходит в комментарий отметки оплаты | ТЗ §10, §21 |
| D-B61-8 | **Перенесённые договоры, счета и подотчёт видны в реестрах** и работают как обычные, с пометкой «перенесён». Скрыты только технические заявки переноса: их нет в Плане закупок, реестрах и статистике. Сейчас реестры прячут всё с `is_migrated` — это исправляется | B6.1 («открытые договоры» — для работы) |
| D-B61-9 | **Идемпотентность** — таблица связей `MigrationLink` (источник → цель), уникальная по источнику. Повтор пропускает уже перенесённое. Компания переносится одной транзакцией; `--dry-run` — тот же прогон с откатом и отчётом | мастер-план |
| D-B61-10 | **Номера `ДГ-`/`СЧ-`** выдаются `next_number` в порядке создания старых документов (`created_at`). Номер по документу контрагента уходит в `ext_number` | мастер-план |

**Ожидаемые расхождения (не ошибка, строки отчёта).** Черновики и «На согласовании» старый модуль расходом не считал. В новом их сумму держит техническая заявка переноса: без утверждённой позиции договор и счёт не отправить (Q-D06). Остаток статьи в новом меньше ровно на эти документы. Отчёт показывает их перечнем.

## Что с чем сопоставляется

| `contracts` | `bpp` / платформа | Правило |
|---|---|---|
| `Country` | `refdata` страна по `iso_code` | нет в справочнике — стоп с перечнем |
| `Program` | `refdata.Article` по карте статей (CSV) | пара «код + название» → код статьи; одна статья может принять несколько программ |
| `Administrator` | «Проект» (`project.interface`) по карте проектов (CSV) | код из карты; страна — `country.iso_code`; руководитель — `user_id` |
| `Budget` + `BudgetLine` | `Budget` проекта, версия 1, строки по статьям | Σ по годам и программам статьи; только KZT |
| `Counterparty` (все) | `bpp.Counterparty` | пара «страна + рег. номер»; уже заведённый переиспользуется; `vat` → плательщик НДС; `active`/`inactive`/`blocked` → Активен/Архив/Заблокирован; контакты — в свои поля |
| `Agreement` открытый (`draft`, `on_review`, `approved`, `signed`) | `Agreement` + техническая заявка с позициями | `approved`/`signed` → «Действует»; `draft`/`on_review` → «Черновик» (D-B61-2); `framework` → открытый договор; `kind` товары → ТМЦ, остальное → работы и услуги; НДС — ставка документа (`vat_source` «Вручную»); `end_date` → «Срок действия по»; позиции — из `AgreementItem`, без позиций — одна позиция «Предмет договора» на всю сумму (Q-D06) |
| `Invoice` без договора, открытый (`draft`, `on_review`, `approved`) | `Invoice` без договора + техническая заявка | `approved` → «К оплате»; остальное → «Черновик»; `paid`/`cancelled` — закрытые |
| `ContractPayment`, `AdvancePayment`, `CompletionAct`, `GoodsInvoice` открытого договора | `Invoice` по договору (D-B61-6) | строки счёта — по позициям договора пропорционально суммам, остаток округления — на последнюю строку; оплата — `PaymentMark` (дата `paid_at`, сумма, комментарий — номер проводки) |
| `AccountableFundsRequest` открытая + `AdvanceReport` | `AccountableFundsRequest` + `AdvanceReport` | `on_review` → «Черновик»; `awaiting_accounting` → «Ждёт выдачи»; `awaiting_advance_report` → «Ждёт отчёта»; согласованный авансовый отчёт → одобренный, прочие → черновик |
| файлы `*_file_id` (media) | `apps.files.interface.adopt_media_file` | тип по документу: `agreement`, `invoice`, `act`, `waybill`, `advance_report` |
| закрытые документы | сальдо на статью (D-B61-1) | вклад по правилам `contracts/services/budget_calc.py` |

Автор документа — `created_by` старого. Если он пуст — `--actor <user_id>`: тот, кто выполняет перенос (обычно АДМ). Он же пишется в журнал изменений исполнителем переноса.

Роль инициатора технической заявки берётся по группе статьи: «Снабжение» → СН, «Проектное управление» → ПМ.

Единица позиции — по названию из справочника `refdata`. Не нашлась — «шт.», и позиция попадает в отчёт.

## Команда

```text
manage.py bpp_migrate_contracts --company <slug> --draft-maps <dir>
    # черновики карт: projects.csv, articles.csv + отчёт конфликтов кодов; ничего не пишет
manage.py bpp_migrate_contracts --company <slug> --projects-map <csv> --articles-map <csv>
    --actor <user_id> [--dry-run] [--report <xlsx>]
```

**Порядок одной транзакции:**
1. Проверки:
   - обе карты полные;
   - все статьи и страны есть в справочниках;
   - маршруты БЗО и роли не нужны — документы переносятся без запуска согласования.

   Любой отказ — стоп и перечень, ничего не записано.
2. Справочники: контрагенты → «Проекты» → бюджеты.
3. Документы в порядке `created_at`:
   - договоры с техническими заявками;
   - счета без договора;
   - платёжные документы договоров → счета;
   - подотчёт.
4. Отзыв старых процессов «На согласовании» (`signoff.interface`).
5. Сальдо закрытых документов по статьям.
6. Сверка: для каждой пары «проект × статья» — старые лимит, «Задействовано» и остаток против новых. Расхождение сверх ожидаемых (черновики) → стоп.

**Отчёт** (`--report`, xlsx):
- проекты;
- бюджеты по годам и валютам;
- перенесённые документы («старый id → новый номер»);
- «Переотправить на согласование»;
- «Не перенесено» — другая валюта, закрытые, файлы ПП;
- сверка остатков.

## Интерфейсы

- **`apps.contracts.interface` (зона B для B6.1, §2.7):** `migration_snapshot()`. Возвращает плоские словари всех нужных моделей и вклад каждого документа в «Задействовано» строки по старым правилам (`budget_calc`). Плюс `revoke_for_migration(subject_type, ids)` — отзыв процессов.
- **`apps.bpp.interface`:** `migrated_targets(source_type, source_ids)` — для заморозки `contracts` (A6.2): карточка старого документа показывает «перенесён в ДГ-…».
- **`project.interface.create_project`, `refdata.interface.*`, `files.interface.adopt_media_file`** — уже есть. Статья по коду ищется через `article_groups` + `active_articles`. Зону A не меняем.

## Задачи

1. **`MigrationLink`** — модель, миграция `bpp/00NN`, `bpp.interface.migrated_targets`. Тесты: уникальность источника, выдача целей.
2. **`contracts.interface.migration_snapshot` / `revoke_for_migration`**. Тесты: снимок на заведённых данных совпадает с `budget_calc` по каждой строке.
3. **Черновики карт и их проверка** (`--draft-maps`, разбор CSV). Тесты: конфликт кодов программ → стоп; доска задач со связанным «Проектом» → он в черновике.
4. **Справочники и бюджеты.** Тесты: годы суммируются; USD не переносится и есть в отчёте; неутверждённые годы → бюджет-черновик; контрагент переиспользуется.
5. **Документы.**
   - Договоры с техническими заявками, счета, платёжные документы → счета, подотчёт, файлы.
   - «На согласовании» → черновик с отзывом старого процесса.

   Тесты:
   - по статусу каждого типа;
   - открытый (рамочный) договор;
   - договор без позиций;
   - оплата с отметкой;
   - АВР с файлом;
   - повтор ничего не дублирует.
6. **Сальдо и сверка.** Тесты:
   - исполненный договор и оплаченный счёт уходят в сальдо, остатки равны;
   - черновик — ожидаемое расхождение;
   - подменённая сумма → стоп.
7. **Реестры (D-B61-8).** Перенесённые видны, в реестрах и карточках — пометка «перенесён». Технические заявки скрыты везде, включая «Задействовано по заявкам» в карточке бюджета: там строка «Сальдо до перехода». Фронт: пометка, тесты.
8. **Сквозная проверка и ранбук.** Тест «весь набор contracts → перенос → работа». В ранбуке: дамп прода → копия → `migrate_shared`/`migrate_companies` → карты → `--dry-run` → разбор отчёта → перенос → проверки. Плюс инструкция по маршрутам `contracts.*` (Q-D03). Правки `CLAUDE.md`, `STRUCTURE.md`, сверки B.

## Вопросы на сверку (с умолчаниями)

- Код «Проекта» для администраторов без доски задач задаёт карта. В черновике стоит `П-<id администратора>`, ФД правит его до переноса.
- АВР и накладная переносятся самостоятельными счетами (D-B61-6), а не файлами к другому счёту. Связи «АВР ↔ оплата» в старой модели нет, поэтому сопоставить их нечем.
- Расторгнутый стандартный договор в старом модуле бюджет не занимал, даже если по нему платили. Сальдо повторяет это правило как есть, но отчёт показывает такие договоры отдельно — для решения ФД.
