### 0.2 Проверка ответов

**Работают как есть:** большинство ответов групп A, C и D, а также ответы по уведомлениям, аудиту, форматам ошибок, нумерации, файлам, экспорту, фронту и тестам. Отдельно проверено по коду, что работают:
- рубильники подмодулей (Q-C03);
- ленивое разрешение исполнителей и «Нет исполнителя» — через флаг маршрута (Q-C10, Q-B22);
- блокировка строки бюджета против гонок (В-07) — приём уже есть (`agreement_service.py:145`).

**Работают с оговоркой** — 24 ответа, у каждого в документе вопросов строка «Проверка». Существенные:
- новая аппка — переносим **всё**;
- новый Проект — один источник правды;
- справочники — через `public`;
- календарь — вне критического пути;
- центр уведомлений — раньше документов;
- НДС вручную и закрывающие документы после оплаты меняют правила [П] ТЗ (BR-031, BR-051) и критерии приёмки (AC-006, AC-009) — это надо зафиксировать как изменение ТЗ;
- «номер счёта по заявке» против сквозного `СЧ-` (Q-E14);
- «счёт занимает бюджет после согласования» оставляет окно гонки для суммы сверх плана позиции (Q-D02 → Q-B06 (г));
- самосогласование без источника «заместителя» (Q-E25);
- руководитель проекта не входит в участники автоматически (Q-E26);
- «главный бухгалтер» вне ролей ТЗ (Q-E27);
- перенос только открытых документов против удаления `contracts` (Q-E15).

**Не заработают без доработки:**
1. **UUID-ключи ↔ signoff** (Q-C23 → Q-E04). Объект с UUID нельзя отправить на согласование, пока `subject_id` целый.
2. **Директора управляющей компании согласуют документы дочерних компаний** (Q-B15 → Q-E02). Signoff разворачивает должности только в схеме своей компании (`engine.py:468-484`), единого инбокса по компаниям нет, членства у директоров в дочерних нет. Для пилота не мешает.
3. **Заявка шаблоном без модели** (Q-A04 → Q-E01): резерв под блокировкой (BR-011), позиции с FK, статусы позиций и План закупок на JSON формы не строятся. Q-C05 это уже решил в пользу модели.

## 1. Резюме

### 1.1 Что уже есть

Около половины объектной модели ТЗ уже реализовано в `apps.contracts`. Тот же заказчик уже присылал требования: в коде есть ссылки на «ТЗ 9.2», BR-032/033/036/042 (коммит `0631434`, Rake887). Есть бюджет со строками, контрагенты, договор с позициями из заявки, счёт без договора, оплата по договору, АВР, накладная, предоплата, подотчётные средства, импорт реестра CashFlow, фронт на всё это (`frontend/src/pages/contracts/*`). Согласование всех документов идёт через единый движок `apps.signoff`. Заявка на закуп — шаблон конструктора форм `apps.approvals`.

Но модель данных построена **на других осях**, чем ТЗ:

- **Бюджет.** В коде бюджет = «администратор (проект × страна) × год × валюта» (`backend/apps/contracts/models.py:395`). В ТЗ — один бюджет на проект с версиями (BR-001, §24).
- **Статья.** В коде «Программа» = «программа + статья расходов» одной строкой, коды у каждого проекта свои (`models.py:208-258`). В ТЗ — глобальный справочник статей с **группой доступа**, которой в коде нет.
- **Счёт.** В коде три разных документа: счёт без договора `Invoice` (без номера — `models.py:903`), оплата по договору `ContractPayment` и предоплата `AdvancePayment`. В ТЗ один «Счёт на оплату» с основанием и сквозным номером `СЧ-ГГГГ-NNNNNN`, по которому идёт сверка с банком.
- **АВР и накладная.** В коде это самостоятельные согласуемые документы, которые сами запускают оплату (`models.py:1048`, `:1087`). В ТЗ — закрывающие файлы на счёте, которые запрашивает бухгалтер.
- **Заявка.** В коде — форма конструктора: позиции в JSON, без цены, без резерва бюджета, маршрут «закупщик ×2 → CFO». В ТЗ — типизированная заявка с ценами, резервом бюджета, маршрутом ТД → ОД и Планом закупок.

### 1.3 Рекомендуемая стратегия (исходная, до ответов)

> **→ изменено ответами 25.09:**
> - п.1 — вместо развития `apps.contracts` делаем **новую аппку**, в которую переезжает вся цепочка (Q-C01; довод про FK внутри одной аппки остаётся в силе и относится теперь к новой аппке);
> - п.3 — модель заявки подтверждена (Q-C05);
> - п.5 — справочники ведёт управляющая компания (Q-C17 → Q-E05).
>
> Актуальная картина — в §0.

1. **Развивать `apps.contracts` как единый домен БЗО, а не заводить новую аппку.** Цепочка «строка бюджета → позиция заявки → позиция договора / строка счёта → строка выписки» держится на внешних ключах и считается в одной транзакции: CALC-002, CALC-005, BR-011 с блокировкой строки бюджета. Межаппочный FK платформа запрещает (`apps/core/tests/test_app_isolation.py`). Поэтому все транзакционные объекты цепочки должны жить в одной аппке, и это `contracts`: тенантная аппка с живыми данными, импортом и фронтом. Перед параллельной работой двух исполнителей `contracts/models.py` (1270 строк) и `views.py` (1539 строк) стоит разнести на пакеты по поддоменам, иначе конфликты мерджа и нумерации миграций будут каждый день.
2. **`apps.signoff` остаётся единственным движком.** Недостающее из §16 добавляется в движок как общие возможности, не под БЗО: запрет самосогласования, замещение, сроки и эскалация, обязательный комментарий при отказе, «сейчас у», предсогласованные этапы, голосование за вариант. Отдельная таблица `approval_step` из §24 не нужна: её роль играют `ApprovalProcessStage`/`ApprovalTask`.
3. **«Заявку на закупку» сделать типизированной моделью в `contracts`,** а не шаблоном конструктора форм. Позиции в JSON формы не дают FK, резерва под блокировкой, `CALC-005` и статусов позиций. `apps.approvals` остаётся конструктором прочих заявок. Судьбу текущего шаблона «Заявка на закуп» и уже поданных по нему заявок решить отдельно (Q-A04).
4. **Права — только через `apps.access`.** Восемь ролей ТЗ = системные роли плюс узлы реестра `contracts.*`. Ручки contracts переводятся на `api_view(module="contracts", level=…)`, contracts/signoff убираются из `_OUT_OF_SCOPE_APPS`. Согласующие в маршрутах — HR-должности (ФД/ТД/ОД/ГД/БУХ как должности), права — роли. Это две разные оси, как уже устроено в платформе.
5. **Мультикомпанейность уже отвечает на вопрос ТЗ В-01.** Каждая компания группы — своя схема. Бюджеты, документы, нумерация, банковские счета и выписки живут в схеме компании. Сводки по группе строятся через `holding`-представления (`backend/apps/contracts/holding.py:9`).

### 6.1 Принципы деления

1. **По подсистемам с чёткими interface-стыками, а не по слоям.** Каждый исполнитель ведёт свои подсистемы от модели до экрана — так меньше ожиданий друг друга.

3. **Нулевой этап — совместный и короткий** *(→ изменено ответами Q-C01/Q-C03/Q-A07)*:
   - каркас **новой аппки** пакетами по подмодулям с рубильниками;

   - дисциплина миграций для двух веток (`new-module-BPP-sanzhar`, `new-module-BPP-ruslan`): перед `makemigrations` — `git merge` ветки соседа, конфликт номеров снимает merge-миграция у того, кто мерджит вторым (мастер-план §0, правило 4);
   - совместная спека.
   
   Разносить `apps.contracts` на пакеты не нужно — он замораживается (только чтение); удаление — только отдельным решением (мастер-план D-35).
4. **Владение signoff** — у B. Каждое изменение движка B присылает A на подтверждение (Q-A02).
5. **Один pytest-прогон за раз** на общей тестовой БД (см. память проекта). Интеграционные прогоны — по расписанию, а не одновременно.

**Баланс нагрузки** (грубо): у B больше предметной логики и миграций данных (бюджет, заявка, договор, счёт, signoff), у A — инфраструктура и новые подсистемы (права, справочники, выписка, альтернативы). Пересмотрим после оценки задач в плане. Если у B окажется перегруз, первым кандидатом на передачу A будет «доработки signoff без голосования» (сроки, замещение, «нет исполнителя») — это инфраструктурная часть движка.

### 6.3 Точки стыковки (контракты между A и B)

- Нумерация: `next_number(prefix, year) -> str` в схеме компании (A → B).
- Справочники: `vat_rate(country_id, date)`, `mrp(date)`, `threshold_1000_mrp(date)`, `uom_*` (A → B).
- Проект: `project_brief`, `is_member(user, project)`, `projects_visible_to(user)` (A → B).
- Права: узлы, `allowed_actions(user, obj)` и группы статей пользователя (A → B).
- Счёт для сверки: номер, БИН контрагента, сумма, статус; запись `paid_bank_amount`/`recon_status` в той же транзакции (B → A).
- Документы для альтернатив: «создать черновик договора/счёта из АП», «заменить альтернативой» (B → A).
- Уведомления: `notify(event, recipients, obj)` (A → B).
- Аудит: `audit.log(obj, action, changes)` (A → B).
