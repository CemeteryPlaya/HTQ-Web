# Стадия 2 «Доступ и роли» — спецификация и разделение работ

Реализует [multi-company-tenancy-stage2-design.md](../multi-company-tenancy-stage2-design.md).
Опирается на подпроект 1 (ядро тенантности, выполнен, ветка `structure-refactoring`).

Документ определяет **что строится**, **кто из двух исполнителей что делает**,
**в какой ветке** и **по какому контракту они стыкуются**.

---

## 1. Главное ограничение стадии

Заказчик **параллельно перерабатывает модель ролей и должностей**: на этапе
проектирования вскрылись проблемы, и `hr.Position`, `LevelThreshold` и связанные
с ними понятия будут переделаны, пока идёт стадия 2.

Из этого следует одно проектное решение, и оно важнее всех остальных в документе:

> **`apps.access` не обращается к моделям HR ни одной строкой.**
> Назначение роли ключуется на `user_id` платформы, а не на `employee_id`.

Почему именно так. Изначальный дизайн (§5.2) предполагал `RoleAssignment.employee_id`
— мягкую ссылку на кадровую карточку. Если модель должностей переделывается
одновременно, эта ссылка становится движущейся мишенью: любая правка кадрового
учёта потребует согласованной правки прав, и две параллельные работы упрутся
друг в друга. `user_id` живёт в `public`, принадлежит платформе и от переработки
HR не зависит вовсе.

Побочная выгода: разрешение прав перестаёт требовать кадровую карточку. Директор
холдинга, у которого в сервисной компании нет и не будет `Employee`, разрешается
тем же кодом, что и обычный сотрудник, — ветка «не-сотрудник» из §8 дизайна
исчезает как отдельный случай.

**Область видимости хранится значением, а не вычисляется из кадров.**
`RoleAssignment` несёт `scope_kind` и `scope_id` явно. Фильтрация по этой области
живёт в потребляющих аппках (`hr`, `tasks`), а не в `apps.access`. Так граница
между нашей стадией и вашей переработкой проходит по файлам, а не по договорённости.

### Что из дизайна стадии 2 переносится в вашу переработку

- §10 «Перевод существующего HR» целиком: сопоставление `junior/middle/senior/lead`
  новым ролям, судьба `LevelThreshold`, удаление адаптера `hr-level`;
- внутренние проверки возможностей на страницах HR (`can_create_employee` и прочие);
- связь «должность → роль», если она вам понадобится.

Оба исполнителя эти места **не трогают**. `useHRLevel` остаётся жить.

## 2. Разделение на исполнителей и ветки

| | Исполнитель A | Исполнитель B |
|---|---|---|
| Ветка | `structure-refactoring` | `structure-refactoring-1` |
| Зона | `backend/**` | `frontend/**` |
| Предмет | Модель доступа, разрешение прав, API | Потребление прав, редактор ролей |
| Документы | правит `docs/**` | **не трогает `docs/**`** |

**Файловые множества не пересекаются.** Это не пожелание, а условие: два
исполнителя в разных ветках сливаются без конфликтов ровно до тех пор, пока ни
один файл не редактируется обоими. Единственный общий ресурс — документация,
поэтому она закреплена за A.

`structure-refactoring-1` ответвляется **от `structure-refactoring`** на текущей
голове (`d83e1ef`), иначе B не получит ядро тенантности.

⚠️ Ветку `structure-refactoring-1` заводите вы — по правилу проекта исполнители
веток не создают.

### Порядок слияния

1. A доводит §4 (контракт) до рабочего состояния и сообщает B.
2. B до этого момента работает против фикстуры из §4, после — против живого API.
3. A вливается в `structure-refactoring` по мере готовности задач.
4. B перебазируется на `structure-refactoring` перед своим слиянием.

B не ждёт A, чтобы начать: контракт заморожен настоящим документом.

## 3. Реестр модулей и уровней

Уровни, строго по возрастанию:

```
none  <  read  <  write  <  admin
```

Модули — значения существующего `KNOWN_SERVICES` (`apps/core/services.py`).
Отдельного справочника не заводим: два разъезжающихся списка модулей — вопрос
времени, а не вероятности.

Правило сравнения одно и то же на обеих сторонах: доступ разрешён, если
эффективный уровень **не ниже** требуемого.

## 4. Замороженный контракт API

Это стык между исполнителями. Менять — только согласованной правкой документа,
не в коде.

Префикс: `/api/access/v1/`. Конверт ошибок общий для платформы: `{"detail": ...}`.

### 4.1 Роль

```json
{
  "id": 12,
  "code": "region-director",
  "title": "Директор региона",
  "weight": 90,
  "parent_id": 3,
  "is_system": false
}
```

| Метод | Путь | Смысл |
|---|---|---|
| `GET` | `roles/` | Плоский список всех ролей компании; иерархия читается по `parent_id` |
| `POST` | `roles/` | Создать. Тело: `code`, `title`, `weight`, `parent_id` |
| `PATCH` | `roles/<id>` | Изменить `title`, `weight`, `parent_id` |
| `DELETE` | `roles/<id>?on_subordinates=reparent\|refuse` | Удалить |
| `POST` | `roles/swap` | Тело `{"a": <id>, "b": <id>}` — атомарный обмен местами |

Коды ответов, обязательные к соблюдению:

- `409` — переподчинение образует цикл. Тело: `{"detail": "cycle", "path": [id, …]}`
- `409` — `DELETE` с `on_subordinates=refuse` при наличии подчинённых
- `409` — попытка удалить `is_system`
- `422` — `code` не уникален в компании

`roles/swap` меняет местами `parent_id` и `weight` двух ролей **одной
транзакцией**. Два последовательных `PATCH` для этого непригодны: между ними
дерево проходит через состояние с циклом либо с общим родителем, и обрыв
оставляет иерархию сломанной.

### 4.2 Права роли

```json
[{"module": "hr", "level": "write"}, {"module": "tasks", "level": "read"}]
```

| Метод | Путь |
|---|---|
| `GET` | `roles/<id>/permissions` |
| `PUT` | `roles/<id>/permissions` — список заменяется целиком |

Замена целиком, а не частичная правка: набор прав роли — единый смысловой объект,
и «забыли прислать модуль» не должно молча означать «оставить как было».
Отсутствующий в списке модуль равен `none`.

### 4.3 Назначения

```json
[{"role_id": 12, "scope_kind": "company", "scope_id": null}]
```

| Метод | Путь |
|---|---|
| `GET` | `assignments/<user_id>` |
| `PUT` | `assignments/<user_id>` — список заменяется целиком |

`scope_kind` ∈ `company` \| `department` \| `site`.
`scope_id` обязателен и не равен `null` при `department` и `site`; при `company`
обязан быть `null` — `422` иначе.

### 4.4 Права текущего пользователя

`GET access/v1/me`

```json
{
  "company": "hi-tech-qazaqstan",
  "permissions": {
    "hr":        {"level": "admin", "scope": {"kind": "company",    "id": null}},
    "tasks":     {"level": "write", "scope": {"kind": "department", "id": 3}},
    "contracts": {"level": "read",  "scope": {"kind": "company",    "id": null}}
  }
}
```

Модули со `none` **не включаются** в ответ. Отсутствие ключа и есть «нет
доступа»: явный `none` заставил бы обе стороны различать «модуля нет в списке» и
«модуль есть со значением none», не давая ничего взамен.

При нескольких ролях: по каждому модулю берётся **максимальный** уровень, а
область — **самая широкая** из тех назначений, что дали этот уровень.

Без контекста компании ручка отвечает `{"company": null, "permissions": {}}` —
и это не ошибка, а переходный режим подпроекта 1.

## 5. Исполнитель A — бэкенд

Ветка `structure-refactoring`. Каждая задача заканчивается зелёными тестами и
коммитом.

### A1. Скелет `apps.access`

`apps.py` c `API_PREFIX = "api/access/v1/"`, `interface.py`, `metrics.py`,
`holding.py` с `HOLDING_MODELS`, регистрация в `INSTALLED_APPS` и
`settings.TENANT_APPS`.

`holding.py` обязателен даже пустым кортежем: без него сборка падает
`ImproperlyConfigured`, и это намеренно — аппка не должна выпасть из сводок
холдинга молча.

### A2. Модели и миграции

```
Role                  code, title, weight, parent (self-FK, null), is_system
RoleModulePermission  role FK, module, level        уникальность (role, module)
RoleAssignment        user_id int, role FK, scope_kind, scope_id (null)
```

Тенантные модели: **столбца компании нет**, изоляция на `search_path`.
`code` уникален в пределах схемы. `RoleAssignment.user_id` — обычный `int` без
внешнего ключа: `auth_user` живёт в `public`, FK поперёк схем невозможен.

### A3. Операции над иерархией

Переподчинение с отказом на цикле, атомарный `swap`, удаление с переносом
подчинённых на родителя либо отказом.

Проверка цикла — **в сервисе и ограничением в БД**, не в интерфейсе: диаграмма
не единственный вход, есть API и django-admin.

### A4. Разрешение прав

`apps.access.interface.permission_level(user, module, company)` и
`permissions_for(user, company)` — вторая для `/me` и профиля.

Порядок:

1. `is_superuser` → `admin` на всё;
2. нет контекста компании → пусто (подстановка «по умолчанию» запрещена —
   ровно тот молчаливый откат, против которого написан `htqweb/fallback.py`);
3. назначения пользователя в этой компании → максимум по каждому модулю;
4. иначе пусто.

Ветка «не-сотрудник» из §8 дизайна отсутствует намеренно: ключевание на `user_id`
(§1) делает её тем же случаем.

### A5. Грант в членстве

`CompanyMembership` (`public`) получает `role_code`, `scope_kind`, `scope_id` —
все необязательные. **Expand-миграция**: только добавление, ничего не сужается.
Разные компании стоят на разных версиях схемы, поэтому иначе нельзя.

Грант — запасной источник назначения для пользователя, у которого в схеме
компании нет ни одного `RoleAssignment`.

### A6. API по контракту §4

Ручки, `urls.py` со слэшевым и бесслэшевым написанием (`APPEND_SLASH = False`),
схемы Pydantic. **Сообщить B по готовности — это точка синхронизации.**

### A7. `/me` и карта прав в профиле

`GET access/v1/me` по §4.4; та же карта добавляется в ответ профиля
`users/v1/profile/me`, чтобы фронт не делал второй запрос на каждой загрузке.

`roles_for()` в `apps/users/services/profile_service.py` **остаётся как есть**:
её тремя значениями пользуется действующий фронт, и снимать их до задачи B4
значит уронить вход в систему.

### A8. Гейт в `api_view`

`api_view(module="hr", level="write")`. Резолвинг — через
`apps.access.interface` **ленивым импортом внутри функции**: вьюхи самой
`apps.access` декорированы `api_view`, и импорт на уровне модуля даст цикл при
старте.

Гейт **объявляется, но не навешивается** на существующие ручки в этой стадии —
это отдельная работа поверх переработанного HR.

### A9. Тесты

- изоляция аппок: `apps.access` доступна только через `interface`;
- наличие `holding.py` с `HOLDING_MODELS`;
- отказ на цикле, в том числе через API в обход интерфейса;
- атомарность `swap`: прерывание в середине не оставляет сломанного дерева;
- матрица `permission_level` по всем четырём веткам A4, включая «нет компании»;
- `PUT` прав заменяет набор целиком, отсутствующий модуль становится `none`;
- `422` на `scope_id` при `company` и на его отсутствие при `department`/`site`;
- миграция A5 применяется на схеме компании, отставшей на версию.

## 6. Исполнитель B — фронтенд

Ветка `structure-refactoring-1`, ответвлённая от `structure-refactoring`.

### B1. Клиент доступа

`src/api/access.ts` и типы по §4. Плюс фикстура ответа `/me` из §4.4 —
до готовности A6 всё разрабатывается против неё.

### B2. `usePermissions`

Хук поверх `/me`: `level(module)`, `atLeast(module, level)`, `scope(module)`.
Кеширование как у `useHRLevel` — `staleTime` 5 минут.

**`useHRLevel` не удаляется и не переписывается** — он в зоне переработки
заказчика (§1).

### B3. Удаление мёртвого словаря

Из `src/lib/auth/roles.ts` удаляются `ELEVATED_ROLES`, `HR_ROLES`,
`EDITOR_ROLES`, `EMPLOYEE_ROLES` и построенные на них функции. Бэкенд не выдаёт
ни одной из этих строк никогда (`roles_for` возвращает только `admin`, `staff`,
`user`), поэтому все ветки на них недостижимы.

Добавить **тест-сторож**: ни один маршрут и ни один компонент не сравнивается со
строкой роли, которой нет среди выдаваемых бэкендом. Отсутствие такой проверки и
позволило словарю выглядеть работающим.

### B4. `RequireAuth` на модуль и уровень

`requiredRole: string` → `requires: { module, level }`. Совместимость со старой
формой не нужна — все её потребители перекладываются в B5 той же веткой.

### B5. Перекладка маршрутов

45 маршрутов в `routeDefinitions.ts`:

| Было | Стало |
|---|---|
| `'hr'` | `{ module: 'hr', level: 'read' }` |
| `'editor'` | `{ module: 'cms', level: 'write' }` |
| `'admin'` | `{ module: <по принадлежности маршрута>, level: 'admin' }` |

`'admin'` разворачивается по смыслу пути, а не одним значением: `/tasks/equipment`
→ `tasks:admin`, `/signoff/routes` → `signoff:admin`, `/requests/templates` →
`approvals:admin`, `/admin/users` → `users:admin`.

### B6. Навигация

Пункты меню скрываются при уровне `none`. Скрытие — удобство, **не защита**:
рубеж остаётся на бэкенде.

### B7. Редактор ролей

Новая страница на компонентах `src/components/hr/OrgChart/`: они уже построены на
`@xyflow/react` + `@dagrejs/dagre` и умеют перетаскивание связей через `Handle` с
диалогом подтверждения, панель редактирования, перенос подчинённых и раскладку.
Строится второй экземпляр семейства с другим источником данных.

Обязательно в интерфейсе: **подпись у дерева о том, что связь означает
подчинение, а не передачу прав** (§6 дизайна). Это самое вероятное расхождение
ожиданий, и закрывать его надо в интерфейсе, а не в документации.

Операции: переподчинение перетаскиванием, обмен местами, удаление с выбором
судьбы подчинённых, панель уровней по модулям.

### B8. Тесты

- `usePermissions` на фикстуре §4.4, включая пустой ответ без компании;
- `RequireAuth` пускает при уровне не ниже требуемого и отвергает ниже;
- тест-сторож из B3;
- редактор: отказ на цикле показывается пользователем читаемо, а не молча
  откатывает узел;
- обмен местами уходит одним запросом `roles/swap`, а не двумя `PATCH`.

---

## 7. Чего стадия не делает

- навешивание гейта на существующие ручки — после переработки HR;
- перевод `junior/middle/senior/lead` на роли — ваша переработка (§1);
- `CompanyModule` и гейты модулей на компанию — подпроект 3;
- жизненный цикл компании, архив только для чтения — подпроект 4;
- третий режим для `media_files` и `mail` — конец стадии, первым под нож при
  нехватке объёма;
- объектная область (`scope_kind=site`) хранится и отдаётся, но **фильтрация по
  ней в домене задач не делается** — это отдельный шаг, самый дорогой в стадии.

## 8. Риски

1. **Контракт §4 разъедется между ветками.** Закрывается тем, что он заморожен
   здесь и меняется правкой документа, а не кодом. Первое же расхождение,
   обнаруженное в коде, — повод остановиться и согласовать, а не подстроиться.
2. **Переработка HR затронет `user_id`.** Маловероятно, но если платформенные
   учётки будут пересозданы, назначения ролей осиротеют. Проверить до начала.
3. **`is_staff` меняет смысл** — после B3 он перестаёт давать прикладной доступ.
   Действующие учётки, полагающиеся на него, надо перебрать до выкатки.
4. **B опережает A.** Фикстура §4.4 позволяет уйти далеко вперёд и накопить
   код, не проверенный против живого API. Точка синхронизации A6 — не
   формальность.
5. **Ожидание наследования прав по иерархии** — закрывается подписью в B7 и
   явной проверкой на демонстрации.
