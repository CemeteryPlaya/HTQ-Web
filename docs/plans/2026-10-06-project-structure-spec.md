# Проектная структура сотрудников — спек (подпроект 1)

Дата: 06.10.2026. Источник требования — схема финансового директора (Алгазы, 05.10): у компании две структуры — **управленческая** («ТОП / специалисты», это кадровая схема `hr`) и **проектная** (своя на каждом проекте, части «Офис» и «Объект»), уровни L1 «ГД» → L2 «Зам. дир., Тех. дир.» → L3 «специалисты» → L4 «рабочие», подчинение по стрелкам между уровнями.

**Главное ограничение:** кадровую схему (`apps.hr`: должности, уровни N-1…N-4, подчинение, права) не трогать. Проектная структура — отдельная, своя у каждого проекта; человек на проекте может занимать роль, не совпадающую с его кадровой должностью.

## 0. Разбиение и порядок

Проектная структура нужна для трёх вещей сразу (ответ 05.10: «всё перечисленное — нужно не только ФД, но и вышестоящим»). Это три подпроекта, каждый со своим спеком, планом и выкаткой; второй и третий стоят на первом:

| № | Подпроект | Суть | Статус |
|---|---|---|---|
| 1 | **Проектная структура** | Справочник ролей, места с подчинением, назначения сотрудников, экран-оргсхема | этот спек |
| 2 | Решения по проектной структуре | Этап маршрута `signoff` на «роли этого проекта» (новый тип исполнителя этапа рядом с HR-должностью), права внутри проекта | отдельный спек после 1 |
| 3 | Учёт | Численность и затраты по уровням/ролям проекта, план/факт, стыковка с `tasks.ResourceRequirement`/`ProjectStaffReport`, сводка группы | отдельный спек после 1 |

Подпроект 1 проектируется так, чтобы 2 и 3 легли на него без переделки: роли — общий справочник компании (маршрут «Тех. дир. проекта» одинаков на всех проектах), места несут план (план/факт для учёта), назначения датированы (исполнитель и численность «на дату»).

## 2. Модель данных (`apps.project`, схема компании)

Уровни проекта L1–L4 — собственная шкала, с кадровыми N-1…N-4 (`hr.LevelThreshold`) не связана.

### 2.1. `ProjectRole` — справочник «Проектные роли»

| Поле | Тип | Правило |
|---|---|---|
| `name` | `CharField(100)` | уникально в компании |
| `level` | `SmallIntegerField` | 1…4, `CheckConstraint` |
| `default_part` | `CharField`, `office`/`site` | подставляется в новое место |
| `sort_order` | `IntegerField` | порядок в списке |
| `is_active` | `BooleanField` | выключенная роль не выбирается для новых мест |
| `created_at`, `updated_at` | | |

- Роль, на которую ссылается хоть одно место (включая закрытые), **не удаляется** (`on_delete=PROTECT`, 409 `E-PRJ-07`), а выключается.
- Смена `level` у роли с местами — 409: она сломала бы правило уровней уже построенных деревьев.
- Начальное наполнение (data-миграция, см. §6): «Руководитель проекта (ГД)» L1 офис; «Заместитель директора» L2 офис; «Технический директор» L2 офис; «Специалист» L3 офис; «Рабочий» L4 объект.

### 2.2. `ProjectSlot` — место в структуре проекта

| Поле | Тип | Правило |
|---|---|---|
| `id` | UUID | как у `Project` (D-05) |
| `project` | FK `Project`, `CASCADE` | |
| `role` | FK `ProjectRole`, `PROTECT` | при заведении — только действующая роль |
| `part` | `office`/`site` | по умолчанию — `role.default_part` |
| `title` | `CharField(255)`, может быть пустым | уточнение: «сметчик», «бригада 2» |
| `parent` | FK `self`, `PROTECT`, null | руководитель на проекте |
| `planned_headcount` | `PositiveSmallIntegerField` | ≥ 1, по умолчанию 1 |
| `closed_on` | `DateField`, null | место закрыто с даты; строка не удаляется |
| `created_by`, `created_at`, `updated_at` | | |

Правила (сервис, под блокировкой строки проекта `select_for_update` — параллельные правки одного дерева идут по очереди):
- `parent` — место **того же проекта**, не закрытое, с уровнем роли **строго меньше** (выше) уровня своей роли.
- `parent = null` допустим только у места уровня L1. Корней L1 может быть несколько (например, ГД проекта и его первый заместитель на L1 — решает руководство; запрета нет).
- Циклов нет (проверка обходом вверх при смене `parent`).
- Подчинение через части разрешено («Объект» → «Офис»).
- Закрыть место нельзя, если на дату закрытия у него есть действующие назначения или незакрытые подчинённые места — 409. Закрытое место не открывается обратно (заводится новое).
- `planned_headcount` нельзя опустить ниже числа действующих сегодня назначений — 409.

### 2.3. `ProjectAssignment` — сотрудник на месте

| Поле | Тип | Правило |
|---|---|---|
| `id` | UUID | |
| `slot` | FK `ProjectSlot`, `CASCADE` | |
| `employee_id` | `IntegerField` | `hr.Employee.id` своей компании |
| `date_from` | `DateField` | |
| `date_to` | `DateField`, null | включительно; пусто — бессрочно |
| `created_by`, `created_at`, `updated_at` | | |

Правила:
- Сотрудник при назначении — **действующий** сотрудник компании (через `hr.interface`); иначе 422.
- `date_to ≥ date_from`; назначение не выходит за `closed_on` места.
- Один сотрудник не может иметь двух пересекающихся по датам назначений на **одно и то же место** — 409.
- **Лимит плана:** на любую дату в периоде назначения число действующих назначений места ≤ `planned_headcount` — 409 (чтобы взять больше людей, сначала поднимают план).
- Совмещение разрешено: один сотрудник одновременно на нескольких местах проекта и на нескольких проектах.
- Увольнение назначения не закрывает (в `hr` не встраиваемся): экран показывает «уволен», подпроект 2 такого человека исполнителем не возьмёт.
- `DELETE` — только у назначения, которое ещё не началось (`date_from > сегодня`, ошибочный ввод); начавшееся только закрывается `date_to` — его история нужна учёту.
- **Участники проекта:** назначение сотрудника с учётной записью добавляет его в `ProjectMember` (если его там нет) — чтобы он видел проект и доску задач. Закрытие или удаление назначения участника **не убирает** (его могли добавить вручную).

## 3. Права

| Действие | Кто |
|---|---|
| Видеть структуру проекта | тот, кто видит карточку проекта (действующие правила: участник проекта или держатель `project.all`) |
| Править структуру своего проекта | руководитель проекта (`Project.manager_user_id`) — по факту руководства, без узла |
| Править структуру любого проекта | держатели `project.structure` (`edit`) |
| Видеть справочник ролей | все с `project:read` (нужен для выбора роли и подписей на схеме) |
| Править справочник ролей | держатели `project.roles` (`edit`); руководитель проекта — нет |

- Узлы `project.structure` и `project.roles` — в `apps/project/access_functions.py`, оба в `EXPLICIT_ONLY`: глубину у предка резолвер не берёт, поэтому широкая роль модуля `project` правки не получает без явной строки.
- Миграция `access/0024` (по образцу `0015`/`0020`) — явная строка у **каждой** системной роли: `edit` у `bpp-fd`, `bpp-td`, `bpp-od`, `bpp-gd`, `bpp-adm`, `hr-lead`; пустая — у остальных.
- Невидимый проект — 404 (как у карточки), видимый без права правки — 403 `E-ACC-01`.
- Связь «руководитель проекта (учётка) ↔ место L1 (сотрудник)» не синхронизируется: права даёт `manager_user_id`, схема показывает места. Расхождение — дело руководства, не ошибка.

## 4. API (`/api/project/v1/`)

Все ручки — `api_view(module="project", level=…)` с явным `level=`; диспетчеры `urls.py` — голые цепочки по `request.method` (сторож `test_gate.py`). Обе записи пути — со слэшем и без (`APPEND_SLASH = False`). Ошибки — конверт `{detail, code, fields, details}` (D-28). Коды: `E-PRJ-05` (409) — нарушение правил дерева, плана или дат места/назначения; `E-PRJ-06` (422) — сотрудник не действующий или не своей компании; `E-PRJ-07` (409) — справочник ролей: удаление или смена уровня используемой роли. Занятые коды `E-PRJ-01…04` не меняются.

| Метод и путь | Что | Уровень |
|---|---|---|
| `GET project-roles` | справочник (`?active=1` — только действующие) | read |
| `POST project-roles`, `PATCH project-roles/<id>` | правка справочника + узел `project.roles` | write |
| `GET projects/<id>/structure?on=YYYY-MM-DD` | всё дерево на дату (по умолчанию сегодня) одним ответом | read |
| `POST projects/<id>/slots` | завести место | write |
| `PATCH slots/<id>` | подчинение, уточнение, часть, план, закрытие (`closed_on`) | write |
| `POST slots/<id>/assignments` | назначить сотрудника | write |
| `PATCH assignments/<id>` | закрыть датой (`date_to`), поправить даты | write |
| `DELETE assignments/<id>` | удалить не начавшееся | write |
| `GET employees?q=` | поиск действующих сотрудников компании для выбора (ФИО, должность по кадрам); кадровых прав не требует, только право правки структуры хоть одного проекта | read |

Ответ `structure`: `{project_id, on, can_edit, slots: [{id, role: {id, name, level}, part, title, parent_id, planned_headcount, actual_headcount, closed_on, assignments: [{id, employee_id, full_name, position_title, date_from, date_to, dismissed}]}]}` — плоским списком с `parent_id`, дерево строит фронт. Закрытые к дате места не отдаются. ФИО и должность — одним запросом к `hr.interface` на всё дерево (без N+1).

`hr.interface`: используются существующие функции; если пакетной выборки сотрудников по списку `id` нет — добавляется **только чтение** (`employees_brief_by_ids`), модели и логика `hr` не меняются.

**Не входит в подпроект 1:** функции `project.interface` для согласований (`holders…`) — появятся в подпроекте 2 вместе с потребителем; `HOLDING_MODELS` новых моделей и сводка группы — подпроект 3; журнал изменений структуры — по запросу (сейчас `created_by`/`updated_at`).

## 5. Экран

Вкладка **«Структура»** на карточке «Проекта» (`frontend/src/features/bpp/projects`).

- Оргсхема **ярусами L1 → L4** (как на схеме ФД): место — карточка (роль и уточнение, метка «Офис»/«Объект», люди, «план N / факт M»), линии к руководителю.
- Переключатель **«Все / Офис / Объект»**, выбор **«на дату»** (по умолчанию сегодня).
- Место с планом > 3 показывается свёрнуто («Рабочий × 10»), имена раскрываются по клику.
- Пустое место — «вакансия»; уволенный сотрудник — «уволен».
- При `can_edit`: на месте — «Добавить подчинённое место», «Назначить сотрудника» (поиск по ФИО), «Изменить», «Закрыть»; на человеке — «Снять с даты», у не начавшегося — «Удалить». Пустой проект — кнопка «Добавить место L1».
- Страница **«Проектные роли»** в меню «Проектов» — видна держателям `project.roles`: список, добавление, правка, выключение.
- Тексты ошибок 409/422 — из `detail` ответа (`lib/apiError`).

## 7. Проверки

Бэкенд (pytest, Python 3.14, `:55432`):
- дерево: уровень руководителя строго выше; корень только L1; цикл; руководитель из другого проекта или закрытый — отказ;
- закрытие места с действующими людьми или подчинёнными — 409; `planned_headcount` ниже факта — 409;
- назначения: лимит плана на пересечении дат; повтор того же сотрудника на месте с пересечением — 409; совмещение на разных местах — можно; уволенный/чужой сотрудник — 422; выход за `closed_on` — отказ;
- `DELETE` только не начавшегося;
- автодобавление в `ProjectMember` для сотрудника с учёткой, без учётки — нет; закрытие участника не убирает;
- справочник: удаление используемой роли и смена уровня у используемой — 409;
- права: руководитель — свой проект да, чужой нет; держатель `project.structure` — любой; участник — только чтение (403 на запись); невидимый проект — 404; `project.roles` — правка справочника, руководитель проекта — 403;
- миграция `access`: точные строки у каждой системной роли; узлы в `EXPLICIT_ONLY`;
- `structure` на дату: закрытые к дате места и назначения вне периода не попадают; ФИО одним запросом к `hr.interface`;
- сторожа зелёные: `test_gate`, `test_app_isolation`, `test_invariants`.

Фронт (vitest): вкладка — ярусы, фильтр «Офис/Объект», «вакансия»/«уволен», свёрнутое место, кнопки только при `can_edit`; страница справочника — видимость по узлу. Типы — `npx tsc --noEmit -p tsconfig.app.json` (сверить число старых ошибок до и после).
