# Тендерный модуль закупок (аппка `tender`) — мастер-план разработки

06.10.2026 · ветка `tender` (от `sanzhar` @ `0d5eebd3`)

**Исходное ТЗ** — [docs/tz/TZ-tender-procurement-v1.0.md](../tz/TZ-tender-procurement-v1.0.md) (далее «ТЗ», ссылки — «ТЗ TND-020», «ТЗ, решение 8»). Мастер-план его не заменяет: он фиксирует, **как** ТЗ ложится на код, исправляет места, где ТЗ расходится с кодом, и делит работу на этапы. При расхождении действует реестр решений §1 этого плана, затем ТЗ.

**Как получен.** ТЗ проверено против кода `sanzhar` @ `0d5eebd3` пятью независимыми проверками (`harness-plan`, `team_validation_mode: subagent`): архитектура, безопасность портала, предметные правила БЗО, тестируемость, критик. Их находки — §2; решения пользователя по четырём развилкам (06.10) — §1, строки «Ответ 06.10».

**Порядок работы — как у БЗО.** Пошаговый план с кодом пишется к старту каждого этапа в `docs/plans/`, задачи этапа — в корневой `Plans.md` (`/harness-work <N>`), ревью — `harness-review`. `STRUCTURE.md`, `CLAUDE.md`, `API.md` обновляются в той же задаче, что и код.

## 1. Реестр решений

«ТЗ» — решение из таблицы «Решения 06.10» ТЗ; «Ответ 06.10» — ответ пользователя на развилки после проверки; «умолчание» — нет прямого ответа, план идёт по рекомендованному варианту до ответа на вопрос из §6.

| № | Решение | Источник |
|---|---|---|
| T-01 | `apps.tender` — отдельная **тенантная** аппка, сервис `tender` в `KNOWN_SERVICES` (не в `CORE_MODULES` — рубильник по компании), API `/api/tender/v1/`, раздел `/tender`. В пилоте без подмодулей `tender_*`. С БЗО — только через `bpp.interface`, в одну сторону | ТЗ |
| T-02 | **Вариант A**: заявка ведётся в tender; «Отправить на согласование» создаёт под ней заявки ЗЗ в БЗО и запускает их штатный маршрут ТД → ОД (BR-011, CALC-002). Вариант C («тендер над позициями утверждённой ЗЗ из Плана») рассмотрен и **отклонён** | ТЗ, решение 1; Ответ 06.10 |
| T-03 | ЗЗ дробятся по паре **(статья × вид закупки)**: у ЗЗ одна статья (`PurchaseRequest.article_id`) и один `purchase_type` (`goods`/`works`). Доставка и СМР — всегда отдельные ЗЗ на свои статьи; СМР — `works`; доставка — `works` (услуга) | ТЗ TND-004; вид доставки — умолчание (Q-T06) |
| T-04 | У заявки tender **обязательны плановые суммы доставки и СМР** (`delivery_plan_amount`, `works_plan_amount`), если признак включён: позиция ЗЗ без цены > 0 не создаётся (`ck_bpp_request_item_price`) | проверка 06.10 |
| T-05 | У заявки tender поле **«Обоснование»** (≥ 10 символов, как у ЗЗ) — уходит во все её ЗЗ | проверка 06.10 |
| T-06 | Закупщику предлагаются только статьи **групп его роли** (BR-010, `services/core/permissions.article_groups_for`); статья чужой группы — 422 `E-REQ-04` ещё в tender, а не на отправке | проверка 06.10; СМР в группе ПМ — Q-T07 |
| T-07 | ЗЗ с `source="tender"` в интерфейсе и API БЗО **не правятся, не отменяются и не закрываются вручную** (замок сервера), их позиции **скрыты из Плана закупок**, а ручные договоры и счета на них запрещены сервером — документы создаёт только `create_documents_from_tender`. Доработка — в tender: повторная отправка пересобирает позиции ЗЗ той же статьи | проверка 06.10 (два места правки — главный риск варианта A) |
| T-08 | Статус заявки tender — **агрегат её ЗЗ** с приоритетом `rejected > rework > in_approval > approved`. Тендер объявляется, только когда утверждены **все** ЗЗ заявки. Отклонённую часть закупщик может «исключить» (позиции этой статьи удаляются из заявки, ЗЗ остаётся «Отклонена») — тогда остальное становится «Утверждена» | умолчание (Q-T08) |
| T-09 | Статусы ЗЗ приходят в tender **слушателем** `bpp.interface.register_request_listener(fn)` в транзакции смены статуса (приём `project.interface.register_change_listener`), без опроса. БЗО не знает про tender — только про реестр слушателей | ТЗ (вариант «слушатель»); проверка 06.10 |
| T-10 | **Нумерация и журнал — копия в tender** (`tender.NumberSequence`, `tender.AuditLog` с триггером append-only, как `bpp/0001`). Вынос в `apps.core` невозможен: `core` живёт в `public`, а номера и журнал тенантные | проверка 06.10 (закрывает вопрос этапа 0 ТЗ) |
| T-11 | Маршрут `tender.award`: этап «Проверка качества» — `ApproverKind.SUBJECT`, ключ `quality_reviewer`: `approvers()` tender возвращает выбранного закупщиком пользователя с ролью `tender-quality` либо держателей должности ТД (`hr.interface.resolve_position_users`); этап «ФД» — по должности. **Правок signoff не требуется.** Этапа ГД в пилоте нет, **роль `tender-gd` в пилоте не заводится** (противоречие ТЗ снято) | ТЗ TND-023, решения 2, 5; проверка 06.10 |
| T-12 | Сравнение — в KZT с НДС по курсу НБРК **последнего дня не позже даты вскрытия** (`refdata.interface.exchange_rate` ищет строго на дату — в выходной вернёт `None`; добавить `exchange_rate_on_or_before`). Документы БЗО считают курс на свою дату (D-15) — расхождение показывается в карточке, BR-034/BR-043 проверяются штатно при отправке документа | ТЗ TND-020; проверка 06.10 |
| T-13 | **Остаток бюджета проверяется при `award/submit`**: если победитель дороже плана сверх свободного остатка статьи, выбор не уходит на утверждение (422), дефицит виден в сравнении. Иначе ФД утвердит выбор, а передача в БЗО упадёт на BR-043/BR-034 | умолчание (Q-T02) |
| T-14 | Порог договора — **BR-040 / CALC-011** (счёт без договора дороже 1000 МРП не отправить; KZT с НДС, МРП на дату счёта), а не BR-094 (тот — про АП). Порог считается **на поставщика по тендеру** (товар + доставка + СМР): выше — договоры по каждой ЗЗ, чтобы передача не дробила закупку (D-17) | проверка 06.10; уровень подсчёта — умолчание (Q-T03) |
| T-15 | **Схемы оплаты 1–3 — в пилоте** (Ответ 06.10). Схема 1 — один счёт `is_advance`. Схема 2 — **один счёт с частичными отметками БУХ** (D-11): два счёта «аванс + остаток» код не примет (BR-042, `qty_left_for_invoice`). Схема 3 — правка зоны B: признак счёта «оплата после приёмки» и срок оплаты = дата приёмки + N дней (ставит приёмка из tender). Модель `PaymentScheme`/`PaymentStage` закладывается сразу, схема 4 (EPC) — этап 6 | ТЗ «Оплата и доставка»; Ответ 06.10; проверка 06.10 |
| T-16 | **Закрывающие — по D-13 без изменений**: в «Ждёт закрывающих» счёт переводит БУХ запросом (`request_docs`), вкладывать можно только запрошенные типы. Tender хранит сканы у себя и прикладывает их функцией `bpp.interface.attach_closing_docs(...)`, которая **сама держит правило D-13** (статус `awaiting_docs` + запрошенный тип); `attach_bytes` напрямую не зовётся. Отметка «Товар принят <дата>, оригиналы переданы <дата, кому>» — поле счёта через `bpp.interface.set_acceptance(...)`, видна БУХ | ТЗ, вопрос 6; проверка 06.10 (в ТЗ переход «Оплачено → Ждёт закрывающих» описан как автоматический — это не так) |
| T-17 | Сканы накладных, СФ и актов в tender видит **тот же круг, что в БЗО**: автор (закупщик), ФД, БУХ, ГД. `tender-viewer` (ОД) и проверяющий качество — нет (ТЗ §21) | умолчание (проверка 06.10) |
| T-18 | **Альтернативы БЗО к документам из тендера разрешены**. Tender показывает у поставщика «Заменён альтернативой АП-…» и новый документ (поле `alternative` карточки БЗО через `documents_status`). KPI БЗО — только для АП; экономия тендера — только в отчёте tender | ТЗ, решения 7, 8; Ответ 06.10 |
| T-19 | Договоры и счета из тендера согласуются **штатными маршрутами БЗО** без предсогласования (`preapproved`) | умолчание (Q-T04) |
| T-20 | Документы БЗО создаются **от имени закупщика** — автора ЗЗ и исполнителя её позиций (`PurchaseRequestItem.executor_id`) — обёрткой над `new_agreement`/`new_invoice` (F-03), а не системным актором: права, видимость и журнал БЗО остаются честными | проверка 06.10 |
| T-21 | **Привязка устройства**: cookie `__Secure-tender_device` (`HttpOnly; Secure; SameSite=Strict; Path=/api/tender/v1/supplier/`, срок тендера + 30 дней); в ТЗ `Path=/supplier/` — ошибка: браузер не пошлёт такую cookie в API. В БД — только хэши токена и секрета устройства. Привязка — `select_for_update` приглашения, лимит устройств проверяется в транзакции | ТЗ §«Персональная ссылка»; проверка 06.10 |
| T-22 | **OTP-перепривязка — в этапе писем**; до него сбросить привязку или перевыпустить ссылку может закупщик | Ответ 06.10 |
| T-23 | Портал: IP — только из `X-Real-IP` (не `X-Forwarded-For`); общий лимитер `htqweb/ratelimit.hit(bucket, key, limit, window)` (OTP — fail-closed); своя `location` nginx с `limit_req`, маскировкой токена в логе, `client_max_body_size 21M`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`; POST — только `application/json` (кроме загрузки файлов) и `Origin` = хост компании | проверка 06.10 |
| T-24 | **Файлы портала принимаются только при включённом антивирусе**: без `ANTIVIRUS_CLAMD_HOST` загрузка КП — 503 «загрузка временно недоступна», внутренние загрузки не меняются. Автор файла поставщика — технический неактивный пользователь «Поставщик (портал)» (`FileObject.uploaded_by_id` NOT NULL), id приглашения — в журнале tender | ТЗ «ClamAV обязательно»; автор — умолчание (Q-T10) |
| T-25 | **Почта поставщикам — свой outbox tender** (`OutboundEmail` + Celery-повтор, `django.core.mail`, From `TENDER_FROM_EMAIL=tender@htq.group`), не `apps.mail.services.sender` (тот шлёт из личных ящиков, а прямой импорт нарушает изоляцию аппок). Внутренним пользователям — `notifications.interface.notify`. Асинхронные bounce (DSN в ящик `tender@`) — [Л] | проверка 06.10 |
| T-26 | Плановые цены, другие участники, их число и цены в портал не попадают: ответ портала собирается **белым списком полей** + сторож-тест на рекурсивное отсутствие ключей | ТЗ «Безопасность» |
| T-27 | Экспорт xlsx — общий санитайзер формул (префикс `'` для `= + - @ \t \r`); заодно чинится `bpp/services/core/export.py` (сейчас экранирует только `=`) | проверка 06.10 |
| T-28 | Журнал портала и `AuditLog` — append-only триггером БД, хранение 5 лет (решение 11); удаление по сроку — после пилота (раньше удалять нечего) | ТЗ, решение 11 |

### 3.1 Раскладка `apps/tender`

```
apps/tender/
  apps.py            # API_PREFIX = "api/tender/v1/"; ready(): signoff-субъект, file owners, слушатель bpp, источник сводки
  interface.py       # пока пусто (соседям tender ничего не отдаёт); каждая будущая функция — require_service("tender")
  access_functions.py# узлы tender.*, EXPLICIT_ONLY
  holding.py         # HOLDING_MODELS = () в пилоте

  admin.py           # ServiceGatedAdminMixin
  approval_hooks.py  # register_subject("tender.award", ...)
  file_owners.py     # tender.request (ТЗ, чертежи), tender.offer (КП), tender.receipt (накладные, акты, фото)
  models/            # request.py, tender.py, supplier.py, portal.py, offer.py, award.py, receipt.py, core.py
  services/
    core/            # numbering.py, audit.py, errors.py (копия bpp, T-10), money.py (KZT, НДС, курс)
    requests/        # заявка, отправка в БЗО, свёртка статусов
    tenders/         # жизненный цикл, участники, приглашения
    portal/          # токены, привязка, OTP, лимиты, предложение
    comparison/      # вскрытие, сравнение, экспорт

    delivery/        # стадии поставки, приёмка, закрывающие
    mail/            # outbox, шаблоны писем
  tasks.py           # Celery: outbox, закрытие приёма, напоминания, чистка OTP (@company_task / dispatch)
  urls.py, views.py, urls_supplier.py, views_supplier.py, schemas.py
```

Фронт: `features/tender/<подраздел>/module.tsx` по образцу `features/bpp/modules.ts`; портал — `pages/public/SupplierTender.tsx` в `publicRoutes` (`routeDefinitions.ts`) без общего layout; строка `^/api/tender/` в `vite.config.ts`.

### 3.2 Модель данных (поправки к таблице ТЗ)

Все модели тенантные, UUID-ключ, `version` (409 `E-CON-01`), деньги `Decimal(18,2)`, ссылки на `bpp`/`project`/`refdata` — голые `UUIDField` без FK.

| Модель | Поправка к ТЗ |
|---|---|
| `TenderRequest` | + `justification`, `delivery_plan_amount`, `works_plan_amount` (T-04, T-05); `bpp_request_ids` — не массив, а `TenderRequestPart` |
| `TenderRequestPart` (новая) | одна ЗЗ: `article_id`, `purchase_type`, `kind` (`goods`/`delivery`/`works`), `bpp_request_id`, `bpp_status` (зеркало, пишет слушатель), `excluded_at` (T-08) |
| `TenderRequestItem` | + `part` (FK `TenderRequestPart`), `bpp_request_item_id` |
| `Tender` | `quality_reviewer_user_id` (null → ТД по должности, T-11); `opened_at`, `rate_date`; без `is_open` в пилоте (этап 6) |
| `Offer` | `currency_code` — у предложения; у `Tender` — лишь желаемая валюта (снято противоречие ТЗ) |
| `OfferExtra` (новая) | доставка и СМР предложения как выбираемые строки: `kind`, `amount`, `included_in_price`, `note`, `amount_kzt` (ТЗ, находка 15) |
| `Award` | ссылается на `OfferLine` **или** `OfferExtra` (XOR); `part_id` (какая ЗЗ), `bpp_document_type/id`, `replaced_by` (АП, T-18) |
| `PaymentScheme`, `PaymentStage` | шаблоны 1–3 + модель для 4 (`trigger`: `before_shipment`/`on_receipt`/`after_works`/`after_warranty`, `pct`, `days`) |
| `DeviceBinding` | `secret_hash`, `ua`, `ip`, `bound_at`, `revoked_at`; `Otp` — этап 4 |
| `OutboundEmail` (новая) | outbox писем поставщикам: `to`, `kind`, `invitation`, `status`, `attempts`, `last_error`, `sent_at` (T-25) |
| `NumberSequence`, `AuditLog`, `PortalEvent` | копия `bpp` (T-10), триггер append-only на `AuditLog` и `PortalEvent` (T-28) |

### 3.3 Статусы (поправки)

- **Заявка tender**: Черновик → На согласовании → Утверждена / На доработке / Отклонена → В тендере → Передана в БЗО → Закрыта; Отменена. Свёртка частей — T-08. «Отклонена» в тендер не переходит.
- **Тендер**: Черновик → Приём предложений → Вскрыт → На утверждении (signoff `tender.award`: «Проверка качества» → «ФД») → Выбор утверждён → Документы в БЗО → Поставка → Закрыт; Отменён, Не состоялся, Возвращён на доработку. Этапа «ГД» нет (T-11).
- Приглашение, предложение, поставка — как в ТЗ.

### 3.5 Передача и обратные пути

- Тендер «Не состоялся» / «Отменён» → заявка обратно «Утверждена»; закупщик объявляет новый тендер **или** «Вернуть в План» (`release_to_plan`) — позиции становятся обычными позициями ЗЗ у исполнителя-закупщика.
- Невыбранный остаток позиций после выбора → «Новый тендер на остаток» (этап 6) или «Вернуть остаток в План»; при передаче неиспользованные ЗЗ доставки/СМР (поставщик включил доставку в цену) закрываются `close_remainder` — резерв освобождается.
- `valid_until` предложения истёк до решения ФД — предупреждение в сравнении и на утверждении, решение не блокируется (умолчание, Q-T12).
