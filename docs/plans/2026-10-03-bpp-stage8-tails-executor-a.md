## Решения

- **D-S8-1 (8.1). Срок — на всю проверку.** `scan()` считает крайний срок `time.monotonic() + ANTIVIRUS_TIMEOUT`; перед каждой операцией сокета остаток считается ОДИН раз, проверяется (≤ 0 → `ScanUnavailable`) и только потом ставится (`settimeout` с отрицательным значением поднял бы `ValueError` — это не `OSError`, был бы 500 без метрики). Ответ clamd на `z`-команду всегда заканчивается `\0`: ответ без него (соединение закрыто раньше, срок вышел) — `ScanUnavailable`, неполный буфер не разбирается. Fail-closed не ослабляется: любое «не успели» → 503 `E-SYS-01`, вердикт метрики `unavailable`. Известное ограничение — разрешение имени (`getaddrinfo` внутри `create_connection`) таймаутом сокета не ограничено (в compose имя `clamav` — внутренний DNS Docker); записать в докстринг. Значение по умолчанию (30 с) не меняется — меняется смысл: на всю проверку (ранбук, `.env.example`).
- **D-S8-2 (8.2). Счётчики остаются раздельными — решение пользователя 03.10.** Один счётчик на учётку дал бы честный порог 5, но позволил бы, зная только e-mail, закрыть вход в учётку целиком (включая администраторов) и выдал бы связь «имя ↔ e-mail» через общую блокировку. Принято: блокировка — по форме логина, порог 5 на каждую форму; успешный вход и `auth_unlock` снимают обе формы (как сделано в этапе 7). Кода нет; в ранбук включения блокировки и в объявление — точная формулировка «5 неверных паролей подряд под одним логином (именем или e-mail)».
- **D-S8-3 (8.3). Видимость поиска — по правилу `can_view`, без запроса на строку.** Правило карточки договора: автор, «все» (`sees_all`), проект + группа статей (`_sees_by_scope`), участник согласования. Внешний гейт `sees_all or can("bpp.agreements", "view")` остаётся (автор или участник без роли — пусто, как сейчас). Реализация: `sees_all` — один фильтр без проверок по строкам; иначе кандидаты контрагента берутся одной выборкой, статьи — одним `refdata.article_brief` по уникальным статьям, участие — новой `signoff.interface.participant_subject_ids(user_id, subject_type, subject_ids)` только для кандидатов, не видимых как автору или по проекту и статьям (выключенный `signoff` не роняет поиск ФД). `is_participant` выражается через неё — правило участия одно. Порядок — `-created_at, pk`. `visible_brief` — тем же путём. Реестр (`read._visible`, правило «ждут решения») не трогаем: менять его — отдельное решение. Отступление от формулировки находки («как в реестре») осознанное: кто что видит в поиске, не меняется. `signoff` и `bpp/services/agreements` — зона B: отдельный коммит, правка только на чтение, работу не блокирует — в список сверки Руслану.
- **D-S8-4 (8.4). Верхний регистр не попадает в БД — `CheckConstraint`.** Уникальность прежняя (`uq_bpp_counterparty_ext_1c`, `uq_project_ext_1c`); добавляется `CheckConstraint(condition=Q(ext_1c_ref=Lower("ext_1c_ref")))` (`ck_bpp_counterparty_ext_1c_lower`, `ck_project_ext_1c_lower`). Так разбор ошибок в сервисах не меняется (поиск конфликта точным значением у контрагента остаётся верным), точные выборки используют индекс, а django-admin получает ошибку формы (проверка ограничений модели), а не 500. Миграции `bpp/0020`, `project/0003` (тенантные, expand, `migrate_companies`): дубли БЕЗ учёта регистра — стоп `RuntimeError` с перечнем (как в 0018/0002), затем `UPDATE … SET ext_1c_ref = lower(ext_1c_ref) WHERE ext_1c_ref <> lower(ext_1c_ref)` с выводом числа строк по схеме (мимо журнала `bpp` и `version` — записать в докстринг), затем ограничение; `RunPython` с `reverse_code=noop` (тест `test_onec_migration` откатывает через 0020). Поиск 1С (`__iexact` с этапа 7) возвращается к точному сравнению. Номер `bpp/0020` может совпасть с веткой Руслана — при сведении merge-миграция, как `0017_merge_stage5_a_b`.
