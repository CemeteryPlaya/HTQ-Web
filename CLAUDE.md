## Migration history (done)

The FastAPI→Django reverse migration — built by **two parallel executors** (Поток A = `hr`/`mail`/`messenger`, Поток B = `tasks`/`approvals`; see **[PLAN.md](PLAN.md)** for the full phase-by-phase journal) — is **complete and cut over**: all 9 FastAPI microservices and `libs/` (`htqweb_auth`, `htqweb_metrics`) were deleted from the repo, and the platform now runs as **one Django backend** (`backend/`). If you see "Поток A"/"Поток B" or "PLAN.md §..." in code comments, that's just where a piece of code came from — the zone split no longer restricts anything; work across any `backend/apps/**` as directed.

- **Cross-app access is still ONLY via `apps.<x>.interface`** (enforced by `apps/core/tests/test_app_isolation.py`) — no direct imports of another app's models/services, no cross-domain FK. That invariant survived the migration unchanged.
- **NEVER create git branches yourself.** The user creates and hands off every branch. Do not run `git branch`, `git checkout -b`, `git switch -c`, or `git worktree add`, and do **not** "branch first" before committing — even on the default branch. This overrides the default Claude Code behavior. Work only on the branch you are given; if the expected branch seems missing or wrong, stop and ask.

## What this is

HTQWeb — Hi-Tech Group's internal enterprise platform. A React + Vite SPA in front of **one Django backend** (Python 3.14, Django 5.2.7). Postgres (direct connection, app-level pooling), Redis (cache + Celery broker), MinIO/S3 object storage, Mediasoup SFU for video.

For context, the platform's history is a full circle: it started as a Django monolith, was migrated (Strangler Fig) out to ~9 FastAPI microservices behind an nginx gateway, and has now been merged back into a single Django backend (the reverse migration above). MongoDB (previously HR docs + the old admin panel) is gone along with the FastAPI generation.

## Commands

Каждый compose-файл объявляет своё имя проекта, поэтому контейнеры называются по нему:
прод — `htq-web-<service>-1` (имя берётся из каталога репозитория), тестовые стеки —
`htqweb-local-<service>-1` и `htqweb-env-<service>-1`. Тома у стеков тоже раздельные.

**БД:** прод и `test-env` берут её из `.env` — адрес задаётся `DB_HOST` и
умолчания НЕ имеет: пустая или опечатанная переменная должна ронять запуск, а
не молча уводить стек куда-то ещё. `test-local` поднимает свой Postgres в контейнере и
**жёстко** прописывает `DB_HOST: db` — подстановки из `.env` там нет намеренно,
иначе «локальный» стек ушёл бы на прод.

**Run the stack** (файлы самостоятельные — никаких `-f a -f b`):
```bash
# ТЕСТ, локальная БД в контейнере (обычная разработка; Vite HMR :3000)
docker compose -f docker-compose.test-local.yml up -d --build
docker compose -f docker-compose.test-local.yml up -d --build --no-deps backend-web  # один процесс

# ТЕСТ, БД из .env (миграции по умолчанию OFF)
docker compose -f docker-compose.test-env.yml up -d --build

# ПРОД
docker compose up -d --build                       # + nginx/certbot под профилем production
```
⚠️ Три стека публикуют одни и те же host-порты — одновременно поднимается только один.

Прод-стек требует флага профиля — `docker compose --profile production up -d`. Без него nginx, certbot и nginx-exporter **не стартуют** (они в профиле `production`), то есть шлюза нет: SPA не отдаётся, а `/api` доступен только через порты, которые `backend-web`/`backend-asgi` публикуют напрямую. Обычный `docker compose up -d` поднимает всё остальное.

**Конференция (SFU) поднята и в dev, и в проде.** `sfu` (mediasoup, сигналинг `:4443`, медиа `:44444/udp+tcp`) и `webtransport` (QUIC-мост `:4433/udp`) больше не под профилем `production` — стартуют вместе со стеком. Что важно знать:
- **Сигналинг требует платформенный JWT.** SFU валидирует токен на WS-upgrade тем же `JWT_SECRET`/HS256, что и Django (`sfu/src/auth.ts`); браузер передаёт его подпротоколом `['htqweb.jwt', <token>]`, WebTransport-мост — параметром `?token=`. Без токена — 401 на upgrade. Отключается только для локальной отладки: `SFU_REQUIRE_AUTH=false`.
- **`WEBRTC_ANNOUNCED_IP` обязателен.** С wildcard listenIp и пустым announced SFU падает на старте намеренно (иначе — чёрное видео). В dev подставляется `127.0.0.1` (браузер на той же машине); для проверки с другого устройства поставьте LAN-IP хоста в корневом `.env`, в проде — публичный IP.
- **Транспорт сигналинга:** фронт сначала пробует WebTransport (QUIC), при неудаче сам откатывается на WebSocket (`WebRTCManager.buildSignalingAttempts`). Адрес моста и отпечаток его самоподписанного сертификата приезжают в `GET /api/cms/v1/conference/config` (`wt_signaling_url` / `wt_certificate_hashes`).
- **Тестовым фронтам обязателен `VITE_SFU_WS_TARGET: ws://sfu:4443`.** Без него Vite шлёт `/ws/sfu` на дефолтный `127.0.0.1:4443` — то есть в САМ контейнер фронта, — и сигналинг молча не находит SFU. В обоих `docker-compose.test-*.yml` переменная задана; при заведении нового стека её легко забыть, а симптом (страница открывается, связь не устанавливается) на причину не указывает.
- Флаг сервиса в реестре включён миграцией `core/0003_enable_conference`; на боевой БД с `RUN_MIGRATIONS=0` её нужно применить руками (`manage.py migrate core`) либо флипнуть `manage.py service conference --on`.
- **Приглашения по ссылке и внешние участники.** `ConferenceInvite` (`apps.cms`, миграция `cms/0005_conference_invites`) + `/api/cms/v1/conference/invites*`. Ссылка вида `/join/<token>` ведёт на публичную страницу: сотрудника она сразу отправляет в комнату, гостю предлагает назваться и выдаёт **гостевой JWT** (`htqweb/authn/jwt.py::issue_guest_token`). Тот подписан общим `JWT_SECRET` — иначе SFU его не примет, — но `token_type="guest"` закрывает ему всё API платформы (`htqweb.http._authenticate_jwt` пускает только `access`), а claim `room_id` привязывает к ОДНОЙ комнате: `sfu/src/auth.ts::guestMayJoin` + `mayEnterRoom` в `server.ts` проверяют это на обоих входах (`join_room`, `joinRoom`). Гостевой токен намеренно не несёт `user_id` — вторая линия обороны: `TokenPayload` без него не собирается. Отправка ссылки — `POST invites/<id>/send` (почта через `django.core.mail`, уведомление через `apps.messenger.interface`, каналы независимы), встреча в календаре создаётся фронтом обычным `event_type="conference"` + `conference_room_id`.
- **Запись, история и протокол.** Аппка **`apps.conference`** (`/api/conference/v1/*`) — имя `conference` в `KNOWN_SERVICES` перестало быть «зарезервированным без аппки». Запись **автоматическая на каждой встрече** и ведётся **поучастниково**: `sfu/src/recording.ts` вешает `PlainTransport` на каждый producer, ffmpeg ремуксит поток в `.mkv` (`-c copy`, без перекодирования — CPU почти не тратится) на общий том `conference_raw`. `.mkv`, а не `.webm`: комната поддерживает и H264, который webm при `-c copy` не принимает. Из подорожечной записи **бесплатно следует протокол** — аудио каждого лежит отдельным файлом, поэтому «кто говорит» известно из имени файла и диаризация не нужна вовсе. Сведение в одно mp4 и распознавание (faster-whisper, `WHISPER_MODEL=medium`, аудио не покидает периметр) делает **отдельный контейнер `backend-media-worker`** (`backend/Dockerfile.media`, очередь `conference_media` через `CELERY_TASK_ROUTES`) — общий `backend-worker` запущен без `-Q` и этих задач не видит, а ffmpeg с ctranslate2 не утяжеляют остальные пять backend-образов. **Ретенция 25 дней** (`CONFERENCE_RETENTION_DAYS`): `purge_expired` стирает медиа из S3 и ставит `recording_state="purged"`, но история встречи, участники, события и текстовый протокол остаются НАВСЕГДА. Отдельное состояние вместо удаления строки — чтобы интерфейс отличал «не писали» от «записали и вычистили по сроку».
- **Канал SFU → Django обязателен к настройке.** `CONFERENCE_INTERNAL_TOKEN` (заголовок `X-HTQ-Internal-Token`, не JWT — у SFU нет пользователя). **Пустой секрет ЗАКРЫВАЕТ приём, а не открывает всем**, поэтому без него не будет ни истории, ни записей. Связь односторонняя и необязательная: недоступный Django не ломает звонок (всё через `sfu/src/fallback.ts`, `expected=false`). Все `internal/*`-ручки идемпотентны — сеть между контейнерами теряет ответы, и повтор не должен ни раздваивать встречу, ни запускать вторую сборку.
- **Плеер записи ходит по подписи, а не по JWT.** `<video src>` не отправляет `Authorization`, поэтому `GET /sessions/<id>/recording` объявлен `auth=None` и проверяет `?sig=&exp=` (`apps/conference/services/signing.py`, общая схема с `htqweb/storage/signed_url.py`); ссылку выдаёт карточка встречи, где права уже проверены. Отдаётся **302 на presigned-адрес**, а не байты через Django: иначе теряется `Range`, то есть перемотка по часовому видео. ⚠️ При правке этих вьюх помните, что `api_view(auth=None)` НЕ разбирает токен — `request.token` заполняется вручную в `_authorize_media`, иначе «вторая дверь» по JWT только нарисована.

Mail-server credentials live in **two layers**: `MailServerConfig` (one DB row, edited at `/admin/mailboxes` → «Подключение») **over** the env vars, merged by `apps/mail/services/mail_config.py` with the rule *empty field in the DB = take it from env*. Never read `settings.IMAP_HOST` (or any other `MAILCOW_*`/`IMAP_*`/`SMTP_*`) directly from `apps/mail` — go through `mail_config.get_config()`, or UI-set values will be silently ignored.

`mail_check` is the first thing to run when corporate mail misbehaves: it prints the resolved config (provisioner mode, domain, IMAP/SMTP targets), then checks each link **in dependency order** — port reachable → IMAP connect → login → folders (including whether `MAIL_SYNC_FOLDERS` actually exist on that server, the usual `Sent` vs `Sent Items` trap) → SMTP connect → SMTP login. The first failure stops the chain so you get the one real cause instead of derived errors, and every failure carries the concrete fix. Without `--mailbox` it needs no secrets at all (config + tunnel only); `--password` is optional for an already-provisioned mailbox (the stored one is decrypted from the DB). Passwords never appear in the output. Exits non-zero on any failure, so it works in scripts.

`seed_purchase_request_template` — одноразовая, идемпотентная и безопасная на проде: заводит шаблон формы «Заявка на закуп» из записки CFO (виджет «строка бюджета» + повторяемая группа ТРУ/кол-во/ед./дата) и публикует версию. С `--buyer`/`--cfo` (id **должностей** HR) заводится и маршрут: **два шага закупщика подряд, затем CFO** — «Подбор поставщика» → «Счёт на оплату» → «Утверждение финансовым директором» (`BUYER_STAGES`, `STAGE_CFO` в команде). Два шага, а не один «закупщик проверил», потому что закуп — работа на дни, и один этап прятал бы её целиком: заявка неделю висела бы в очереди без признаков движения. Шаги — чек-лист закупщика: «Ждёт меня» показывает «этап 2 из 3» (`stage_order`/`stage_count` в `InboxItem`), «Ход согласования» — весь путь. Каждый шаг закрывается результатом, который движок проверяет до записи решения. На первом это **сравнительная таблица поставщиков**: блок `quotes` (виджет **`supplier_quotes`**, `filled_by: approver`), строки — позиции заявки, колонки закупщик добавляет сам, в клетках цена ЗА ЕДИНИЦУ, выбранное предложение отмечено. На втором — блок «Счёт на оплату» (номер, дата, сумма), **файл PDF** и **совпадение сумм**: у «Суммы по счёту» стоит `must_equal: quotes.total`, и пока счёт выставлен не на сумму выбранного предложения, шаг не закрывается (иначе CFO утверждает одно, а платят другое). Рядом — свободный блок «Условия поставки и оплаты» (`terms`). Сервер выводит `totals`/`total`/`supplier_name` таблицы при каждом сохранении (`services/quotes.py`), `quotes.total` — сумма заявки (`contributes_to_total`), и `<ключ>.total` дальше работает как обычное денежное поле. Присланный клиентом `total` затирается: по этому числу утверждают деньги, и считать его вправе только сервер. ⚠️ Шаблон будет заменён типизированной заявкой модуля БЗО (см. «Модуль БЗО» ниже) — новых возможностей в него не вкладывать. `must_equal` — общее правило схемы, не про закуп: любое числовое поле может требовать равенства другому (путь `key` или `группа.key`), сломанное правило отвергается при публикации формы, а проверка идёт там же, где обязательность — при подаче для полей инициатора и на шаге для полей согласующего. `requirement_key` этапа = `field:<ключ блока>`; панель «Ваш шаг» на карточке согласования показывает ровно блок текущего шага (+ PDF, если этап его требует) и закрывает шаг кнопкой «Сохранить и закрыть шаг» (`instances/<id>/stage-values/` → `tasks/<id>/attachment` → `/decision`). Инициатор эти блоки не видит и при подаче они не требуются. Поставщик — **не контрагент** из «Договоров»: разовая закупка не должна тянуть карточку с БИН и согласованием. CFO утверждает по этому счёту — в самой заявке ни поставщика, ни цены нет, её заполнял инициатор, и на время согласования форма для него закрыта; счёт CFO видит ссылкой в «Ходе согласования». Должности, а не люди: сменился сотрудник — маршрут не правят, движок находит текущего на запуске; команда предупреждает, если на должности нет активного сотрудника с учётной записью (сам движок это проверяет только на отправке, что для разовой настройки поздно). `--buyer-user`/`--cfo-user` — те же этапы поимённо, для теста без HR-данных. Без этих аргументов маршрут **не создаётся**: пустой маршрут хуже отсутствующего (отправка отвечала бы «в маршруте нет этапов» вместо «маршрут не настроен»). Подача заявки — «Запросы» → «Создать запрос» → шаблон; отдельной кнопки «закуп» нет по замыслу: закуп — это шаблон формы, а не свой раздел.

**Статистика по заявкам разведена по доступу.** Личная — `GET /api/requests/v1/stats/mine` (`apps/approvals/services/personal_stats.py`, страница `/requests/my-stats`): сколько человек подал, на какую сумму и **что заказывал** — позиции сворачиваются из ПОВТОРЯЕМЫХ групп формы по правилу «что = первая текстовая колонка, сколько = `summarize_keys` группы (или первая числовая), в чём = первый выпадающий список», единицы входят в ключ группировки. У ручки **нет параметра «чья статистика»** — пользователь берётся из токена, и это вся защита. Общие разрезы (`stats/{overview,by-project,by-template,by-actor,heatmap}`) под уровнем `admin` модуля `approvals` (роль `services-admin`; в pre-production это был `admin=True`, при слиянии со `sanzhar` переведено на гейт блока L): раньше гейта не было вовсе — страница пряталась ролью на фронте, а эндпоинты отвечали любому, включая `by-actor`. `total_amount` считается из полей с `contributes_to_total` **включая поля блоков** и пересчитывается, когда согласующий заполняет свой блок, — иначе сумма закупа (она приезжает уже на согласовании) всегда оставалась бы нулём.

Так приходят договор `bpp.agreement` и счёт `bpp.invoice` (B) и выписка `bpp.bank_import` (A): скан договора и файл счёта обязательны для отправки (422 `E-FIL-04` через `services/core/files.py::require_files`), закрывающие АВР/накладную/счёт-фактуру видят только автор, ФД и БУХ (`can_view_type`) и вкладывают по запросу БУХ, а «Документы предоставлены» без файла запрошенного типа — `E-INV-04`; общие куски колбэков — `file_owners.actor_from_token`/`history_on_event`. Их типы в справочнике — миграции `files/0003_bpp_file_types` (заявка, подотчёт) и `files/0004_bpp_stage3_file_types` (`agreement`, `agreement_annex`, `invoice`, `act`, `waybill`, `vat_invoice`, `bank_statement` — TXT/XLSX/CSV; под выписку scope `file_object` принимает `text/plain`/`text/csv`, `EXT_MIME` — `.txt`/`.csv`, отдаются вложением; `alternative_offer` — с A5.1), а не `bpp`: справочник живёт в `public`, а миграции тенантной `bpp` идут по схемам компаний. Своих ручек файлов у документов модуля нет (B-2): люди работают с файлами на панели `/api/files/v1`, а сервисы модуля прикладывают их через обёртку `apps/bpp/services/core/files.py` (`attach/replace/list_files/download_url/require_files/count_files`), а та — через **загрузку из кода**: `apps.files.interface.attach_bytes`/`replace_bytes`/`download_link`/`find_version` — тот же путь, что HTTP-загрузка (справочник, квоты под блокировкой владельца, антивирус, версии, журнал `FileEvent` с IP и user-agent), но `can_modify` не спрашивается — права проверил владелец своими правилами (добавлять и удалять документы заявки панель пускает только в черновике и на доработке, а новую версию — и после отправки: необязательный колбэк владельца `can_version` проверяется на пути версии вместо `can_modify`, и папка отдаёт у документа `can_version`/`can_delete`). Откат сохранённых байтов у загрузки из кода — сразу `media.discard_upload`, а не пометкой через грейс: она идёт в транзакции владельца, и пометка откатилась бы вместе с ней, оставив «сироту» в S3. **Журнал `FileEvent` — только вставка, триггером БД** (`files/0002`, как `bpp_auditlog`): пропускается лишь однократная простановка компании `tenancy_bootstrap` (пустая `company_slug` → непустая, прочие столбцы без изменений). Владелец регистрируется из своего `ready()` через `apps.files.interface.register_owner` и отвечает колбэками: видно ли объект, можно ли менять его файлы (`FilesForbidden` → 403 `E-ACC-01`, `FilesLocked` → 409 `E-FIL-06`), отправлялся ли он, как заблокировать его строку; необязательные уточнения по типу файла (ТЗ §21: АВР видят не все, кто видит счёт) — `can_view_type(owner_id, token, file_type) -> bool` (невидимый тип пропадает из папки, а ссылка, новая версия и удаление его документа — 404, как у несуществующего) и `can_modify_type(...) -> bool` (проверяется после `can_modify`; `False` — 403, свой текст — `FilesForbidden`/`FilesLocked`), без них тип на доступ не влияет, загрузка из кода их не спрашивает; типы своих файлов он сеет в справочник миграцией (`public`, см. выше про `files/0003`). ⚠️ transaction=True-тест чистит `public` целиком, и справочник вместе с ним: такому тесту строки типов надо засеять заново (`seed` миграции или фикстурой, как `apps/bpp/tests/test_files.py::probe`), иначе папка владельца падает `ImproperlyConfigured`. **Ключ владельца — строка** (`FileObject.owner_id`/`FileEvent.owner_id`, `CharField(64)`): документы БЗО адресуются UUID (D-05); владелец с нецелым ключом передаёт `register_owner(model=…)`, колбэки получают ключ в типе своей модели (`OwnerEntry.native_id`), в таблице — каноническая строка, неподходящий ключ в URL — 404 `E-FIL-05`. Тесты подсистемы идут на пробных владельцах `apps/files/tests/testapp` (целый ключ и UUID), подключённых только в `settings/test.py`. **Версии — по ТЗ:** номер присваивается один раз под блокировкой владельца и не меняется; новая версия грузится поверх конкретной действующей (`base_file_id`), устаревшая база — 409 `E-CON-01`; повтор с тем же `Idempotency-Key` отдаёт первую запись. **Ошибки — в конверте модуля БЗО (D-28)** `{detail, code, fields, details}`: это конверт ТЗ, где `message` назван `detail`, поэтому текст понимает любой клиент общего `{"detail"}`; код фронт читает через `lib/apiError` (`errorCode`). Тексты формата и размера — дословно ТЗ §13.2, одна фраза на оба случая («Файл X не загружен: допустимы PDF, JPG, PNG до 10 МБ»), и так же на фронте (`components/files/fileChecks.ts`). **Гейт:** правка справочника типов — `api_view(module="files", level="write")` (узел `files.types`), остальные ручки — в `access/self_service.py` (`scoped`: права на документы решает владелец; список типов — `open`); диспетчеры `urls.py` — голые цепочки по `request.method`, иначе их не примет сторож `test_gate.py`. Ключ в хранилище — `file_object/<компания или public>/<папка владельца>/<id>/…`; у тенантного владельца `company_slug` — часть ключа и обязательный фильтр каждого запроса (id строк повторяются по компаниям), у общего — только факт. Scope `file_object` в media — `owner_gated`: по JWT media такие файлы не отдаёт и не подписывает никому, только по ссылке подсистемы. **Скачивание журналируется (ТЗ §25.2), поэтому готовых ссылок в ответах папки и загрузки нет** — ссылку выдаёт `…/versions/<id>/link` на каждое скачивание, и каждая выдача пишет `file_downloaded` (IP, user-agent) в журнал `FileEvent` и владельцу (`on_event`); не возвращайте `url` в `version_out` «для удобства» — это скачивание мимо журнала. Компания тенантного владельца обязательна: при заведённых компаниях запрос без контекста — `NoCompanyContext`, а не молчаливое `""`. Физически удаляется лишь документ ни разу не отправленного владельца, иначе `deleted_at`; удаляя объект, владелец зовёт `files.owner_deleted`. Для будущего переноса данных (B6.1) есть `adopt_media_file` (уже лежащий в media файл — версией 1 в папку владельца) и `current_files`. Потолок размера `FILES_UPLOAD_CEILING_MB = 20` совпадает с `client_max_body_size 21M` локации `/api/files/v1/` в nginx — меняйте вместе. `tenancy_bootstrap` проставляет `company_slug` файлам тенантных владельцев в той же транзакции, что переносит таблицы. **Антивирус** (ТЗ §21 [Л]) — ClamAV: сервис `clamav` (`clamav/clamav:1.4`, clamd :3310 только внутри сети, базы в томе `clamav_db`, ~1,5 ГБ памяти) и клиент `htqweb/antivirus.py` (протокол INSTREAM, без пакета). **По умолчанию выключен** (мастер-план БЗО, D-31: «задел под ClamAV, по умолчанию без проверки», ответ Q-B25; включение — задача A7.4): во всех трёх стеках `${ANTIVIRUS_CLAMD_HOST:-}`, сервис `clamav` под профилем `antivirus` и без него не стартует. Включить — `ANTIVIRUS_CLAMD_HOST=clamav` в `.env` и `--profile antivirus` при `up`; `settings/test.py` держит хост пустым явно. Что проверять при включённом сканере, решает флаг scope `ScopePolicy.antivirus` в `apps.media_files`: документы — `file_object`, `generic` (сканы договорного контура и любой неизвестный scope) и `signoff_doc` (PDF шагов согласования); аватарки, чат, новости, HR-документы и вложения задач — нет. Отказы пайплайна media — наследники `htqweb.http.ApiError`, поэтому и вьюха, которая их не разбирает (договорный контур), отдаёт их своим статусом и текстом, а не 500. Угроза — 422 `E-FIL-08` + `FileEvent` `file_rejected`; **настроенный, но молчащий сканер ЗАКРЫВАЕТ приём** (503 `E-SYS-01`), а не пропускает файл непроверенным — это отказ, а не подмена, поэтому через `htqweb.fallback` не идёт. `CLAMD_CONF_StreamMaxLength: 100M` в compose — предел потока clamd поднят до потолка шлюза для `/api/media/`. ⚠️ Первый запуск после включения: пока freshclam качает базы (минуты), clamd не отвечает и загрузка документов получает 503 — так задумано; `database.clamav.net` отдаёт базы не во все страны — при 403 в логах freshclam нужен `DatabaseMirror`. Поле конструктора `file` по-прежнему хранит только имена файлов и к подсистеме отношения не имеет.

**Варианты голоса в `signoff`** (задача B1.3 мастер-плана БЗО, сделана заранее; имена — по контракту §2.6). Предмет регистрирует `options` (варианты `[{key, label}]`: исходный документ и его альтернативы, ТЗ §12.4), `check_option` (можно ли голосовать за вариант — строка-причина) и `on_option(subject_id, stage_order, user_id, option_key)` — доменная запись голоса (D-26), в транзакции решения. Карточка процесса отдаёт `options`; `approve` без `option_key` при двух и более вариантах, с неизвестным или отвергнутым предметом вариантом — **422** (`OptionError`); голос хранится на задаче (`ApprovalTask.option_key`/`option_label`, миграция `signoff/0011_task_option`), решающий — голос **последнего этапа** (`signoff.interface.final_option`); массовое решение вариант не угадывает. Потребителей пока нет: альтернативы §12 строятся в `bpp` (A5.1/B5.1), черновая реализация в `contracts` снята по D-01. Кто выбирает — признак этапа `votes_option` (миграция `signoff/0015`, галочка «Выбирает вариант» в редакторе маршрута; D-25: ФД и ГД): если он есть хоть у одного этапа снимка, выбирают только такие этапы, карточка процесса отдаёт `options` лишь пока идёт выбирающая группа, а решающий голос — у последнего выбирающего этапа; нет признака ни у одного этапа — вариант называет каждый этап, как в ТЗ §12.4 (`engine.stage_votes`). Ключ объекта у вариантов — как у остальных колбэков: в типе ключа модели (`registry.native_id`), так что у документов с UUID они работают так же (B0.1, `signoff/0012`: `ApprovalProcess.subject_id` — строка).

**Флаги маршрута `signoff`** (мастер-план БЗО, B1.2 / D-21, D-22; миграция `signoff/0013`). Столбцы `ApprovalRoute`, все выключены по умолчанию — без них движок ведёт себя по-старому; на запуске снимком копируются в `ApprovalProcess.route_flags` (правка маршрута идущий процесс не меняет, ТЗ §16.1 п.2). `forbid_self_approval` (BR-061): автор исключается из своей группы должности — остаются другие держатели и временные исполнители (`hr.ActingAssignment`), иначе группа уходит держателям `escalation_position_id` (ГД) с тем же `position_id` для кворума; автор и есть ГД — группа пропускается (событие `self_approval_skipped`, уведомление `self_skip_notify_position_ids` — ФД), этап без задач согласуется сразу (`stage_auto_approved`); решение автора — 403 `SelfApprovalForbidden`. `reject_comment_min` (BR-060): `reject`/`rework` с комментарием короче — 422 `CommentTooShort` (оба — наследники `InvalidDecision`, как и ошибки вариантов голоса). `lazy_resolution` (ТЗ §16.1 п.2, п.5): исполнители этапа — при его активации (`services/resolution.py`, по снимку этапа, на сегодня); группа без исполнителя — этап `no_executor` «Нет исполнителя», документ ждёт, уведомлены `no_executor_notify_position_ids` (АДМ, ГД); повторная попытка — `engine.retry_no_executor`, ручка `POST processes/<id>/retry-executors` и периодика `signoff.retry_no_executor` (15 мин, диспетчер + веер, до первой компании — в `public`; миграция `0014` в `SHARED_EFFECT_MIGRATIONS`). «Роли» в signoff — HR-должности, поэтому получатели и эскалация заданы должностями. Без `lazy_resolution` пустая должность — по-прежнему `RouteUnusable` на запуске. `skip_unmatched_groups` (D-18, миграция `signoff/0016`): группа, где не сошлось ни одно условие и нет «иначе», пропускается, а не роняет запуск `RouteUnusable`; не осталось ни одного этапа — процесс заводится и сразу закрывается «согласовано» (`engine._approve_without_stages`: события `started` + `no_applicable_stages`, предмет получает обычные `on_started` и `on_approved`) — так допсоглашение без изменения суммы вступает в силу без решений. Редактор — `RouteFlagsCard` на странице маршрута; в карточке процесса — плашка «Нет исполнителя».

**API `signoff` для модуля БЗО** (B1.3, `signoff.interface`). `decide_many(actor_id=, items=[{task_id, decision, comment?, option_key?}])` — поштучно, каждый элемент в своей транзакции (`services/batch.py`); на нём же ручка `tasks/batch-decision`, принимающая и старое тело `{task_ids, decision, comment}`, и новое `{items}`. `current_holders(subject_type, subject_ids)` — «Сейчас у» для колонки реестров (`services/holders.py`: этап текущей группы, держатели открытых задач с ФИО, должность первой группы, `since` = `ApprovalProcessStage.activated_at`, признак `no_executor`); объекты без идущего процесса и невозможные ключи в ответ не попадают. `pending_for_user(user_id)` — очередь для ежедневной сводки (та же выборка, что «Ждёт меня»). **Уведомления движка идут через центр уведомлений** (`engine._notify_center`: колокольчик, e-mail, Telegram по выбору получателя; заголовок — описание документа + событие, `_CENTER_TITLES`), запись в транзакции решения под своей точкой сохранения; центр не установлен или выключен — по-старому, мессенджером после коммита. Источник сводки центра уведомлений — `holders.digest_items` (заголовок с этапом, ссылка на документ или карточку процесса), регистрируется из `SignoffConfig.ready()`, если `apps.notifications` установлена. `configure_route(..., flags=)` заводит маршрут сразу с флагами (так делает `bpp_configure_routes`). `start_process(..., preapproved=[{position_id, actor_id, label}])` (D-26) — группы этих должностей без задач (хранятся в `ApprovalProcess.preapproved`, их обходит и ленивое разрешение), этап только из них закрывается сразу (`stage_preapproved`), должность не из маршрута — `PreapprovalMismatch` (409).

`migrate_workflows_to_signoff` — команда перехода на единый движок: переводит `workflow_json` шаблонов в маршруты signoff (область `template:<id>`) и **перезапускает с первого этапа** заявки, застигнутые «на согласовании» старым движком. Непереносимый граф попадает в отчёт с причиной, а его заявки возвращаются инициатору. `--dry-run` печатает план, ничего не записывая.

## Architecture invariants (the load-bearing ones)

- **One Django backend, domains are apps.** `backend/apps/{users,cms,media_files,files,hr,mail,messenger,tasks,approvals,contracts,signoff,conference,companies,access,core}`, plus the BZO module's apps (since 26.09.2026): `project`, `refdata`, `notifications`, `bpp` — see «Модуль БЗО» above. Six of those post-date the migration and have no FastAPI ancestor: `files` (the ТЗ §21 file subsystem, `/api/files/v1` — see the paragraph under Commands), `conference` (history, recordings and minutes of video meetings, `/api/conference/v1`), `companies` (the group's company registry, `/api/companies/v1`) and `access` (roles and permissions, `/api/access/v1`) — the last two are described in the sections below — plus **`contracts`** (`/api/contracts/v1`, budgets/counterparties/agreements) and **`signoff`** (`/api/signoff/v1`, the platform's **single approval engine** — multi-stage approval over *other apps'* rows, contracts' documents and `apps.approvals`' requests alike; `apps.approvals` is the form **designer** and register that feeds it, not a second engine; see STRUCTURE.md §3.6). `apps.core` is the only shared foundation (JWT/service-registry primitives live in `htqweb/`, not in an app); every other app talks to a neighbour ONLY through that neighbour's `apps.<x>.interface` module — never its `models`/`services` directly (enforced by the isolation test above).
- **API layer is hand-rolled Django, not DRF.** `htqweb.http.api_view` (`methods=`, `auth="jwt"|"admin_session"|None`, optional Pydantic `body=`, `admin=True` gate) decorates views; the error envelope is always `{"detail": ...}` (401/403/404/422/500/503), matching the old FastAPI contract. Pydantic schemas (`apps/<domain>/schemas.py`) carried over from the FastAPI services essentially as-is and still do request/response validation.
- **URLs auto-mount by convention.** An app declares `API_PREFIX = "api/<domain>/v1/"` on its `AppConfig` (`apps/<domain>/apps.py`) and defines `apps/<domain>/urls.py`; `htqweb/urls.py` discovers every installed app with that attribute and mounts it — adding a domain never touches `htqweb/urls.py`. `APPEND_SLASH = False`, so `urls.py` registers both the slashed and bare spelling of a path wherever the frontend might send either.
- **Business logic lives in `apps/<domain>/services/<file>.py`.** `views.py` are thin dispatchers (parse → call service → shape response). Look in `services/`, not in views, for behavior.
- **JWT issuer is still `htqweb-auth`.** There's no separate user-service anymore — `apps.users` both issues (`htqweb/authn/jwt.py`, called from `apps.users.views`) and every app validates tokens locally via the same shared `JWT_SECRET`/HS256, in-process, no network call. Claims: `sub, user_id, username, email, is_staff, is_superuser, is_admin, company, token_type, iat, exp, iss` — the FastAPI-era set plus `company` (slug компании, для которой выпущен токен; см. «Мультикомпанейность» ниже).
- **Apps are disableable at runtime**, same mechanism as before the merge, just in-process now: `apps.core.models.ServiceStatus` (one DB row per domain, 5s-cached) + `htqweb.middleware.service_gate.ServiceGateMiddleware` (gates `/api/<prefix>/` and `/ws/.../` by URL prefix) + `apps.core.services.require_service("<name>")` (the in-process gate — first line of every `interface.py` function and every Celery task) + `htqweb.admin_gate.ServiceGatedAdminMixin` (gates that app's models in `/django-admin/`). Flip one with `manage.py service <name> --on/--off`. A disabled dependency surfaces as 503 `{"detail", "code": "service_disabled", "service"}` everywhere — HTTP edge, an in-process `interface` call turned into `ServiceDisabled`, or `django-admin` (which fails the Django-native way: `PermissionDenied`, not a JSON body). A part of an app can carry its own switch: `apps.core.models.KNOWN_SUBMODULES` (submodule → parent service, one level; today the seven `bpp_*`) — `apps.core.services.disabled_layer()` checks the parent first, and the 503 names whichever layer is off. Submodule prefixes must sit ABOVE the module prefix in `PREFIX_TO_SERVICE` (the gate takes the first match; guard `apps/core/tests/test_bpp_scaffold.py`).
- **Processes** (`docker-compose.yml`, all built from the same `backend/Dockerfile` image, differing only in `command`): `backend-web` (gunicorn/WSGI — all of `/api/*`, `/django-admin/`, static; the **only** process that runs migrations — `manage.py migrate_shared`, not bare `migrate`, see «Мультикомпанейность» — gated by `RUN_MIGRATIONS=1`, and the only one that seeds the `admin`/`admin12345` account (plus collectstatic and storage buckets), gated separately by `RUN_BOOTSTRAP`: it is `1` by default in `docker-compose.yml`/`test-env` and hard-coded in `test-local`, so a stack started with `RUN_MIGRATIONS=0` still seeds the admin), `backend-asgi` (uvicorn/ASGI — SSE `/api/requests/v1/stream` + WebSocket `/ws/`; messenger's Socket.IO mounts at `ws/messenger/socket.io`), `backend-worker` (Celery), `backend-beat` (Celery beat, `django-celery-beat` DB-backed scheduler), `flower` (Celery monitoring UI). Broker/result backend is Redis. Every Celery task's first line is `require_service("<app>")`.
- **nginx (`infra/nginx/default.conf`) is the gateway**: two upstreams, `backend` (WSGI, everything else) and `backend_asgi` (the SSE route + `/ws/`). In dev, Vite's proxy (`frontend/vite.config.ts`) mirrors that split — every `*ServiceTarget` variable it defines now resolves to the same `VITE_BACKEND_TARGET` (the per-service names only survive because the proxy rule table still keys off them).

## Postgres — direct connection now; PgBouncer is legacy-shaped history

- **Django talks straight to Postgres**: `DB_HOST=db`, `DB_PORT=5432` (psycopg, sync), `CONN_MAX_AGE=0` — pooling is app-level, not a shared external pooler. PgBouncer (`:6432`) is still in the compose file for host-side tooling/manual `psql`, but it is **not** in the live request path anymore.
- **History (no longer applies — here so old scars make sense if you trip over them):** the FastAPI generation put every service behind PgBouncer in transaction-pooling mode, which silently drops `search_path`, so all 8 Python services (except `user`→schema `auth`) actually lived in schema `public` with a table-name-prefix convention (`hr_*`, `task_*`, `request_*`, `cms_*`, `email_*`), and Alembic needed a fresh-thread-per-migration dance to survive the pooler. None of that applies to Django: one schema (`public`), natural table names (`<app>_<model>`), `managed=True`, plain `makemigrations`/`migrate`.
- **Tests need a real, unpooled Postgres** — `CREATE DATABASE`/`DROP DATABASE test_htqweb` cannot pass through PgBouncer's transaction pool. That's what host port `:55432` (the `db` service of `docker-compose.test-local.yml`) is for; see [backend/README-tests.md](backend/README-tests.md).

## Мультикомпанейность — схема на компанию

Компании группы изолированы **схемами Postgres**, а не столбцом `company_id`: `settings.TENANT_APPS = ("hr", "tasks", "contracts", "signoff", "bpp", "project")` живут в `co_<slug>` (дефис в slug заменяется на `_` — идентификатор Postgres дефис не допускает, `htqweb/tenancy/context.py::schema_for`), всё остальное — в `public`. Разводит их `search_path`, который на каждый запрос ставит `CompanyContextMiddleware` (`htqweb/middleware/company_context.py`) по заголовку `X-HTQ-Company` (его кладёт nginx, вытащив поддомен регуляркой — комментарий над `server_name` в `infra/nginx/default.conf` объясняет, почему она нарочно отсекает `www`, IP и голый домен второго уровня). **Модели tenant-аппок поэтому НЕ содержат поля компании — не добавляйте его**: изоляция обеспечивается СУБД, а не дисциплиной разработчика, и это ключевое, намеренное следствие выбора схем.

- **Контекст компании обязателен, а не подставляется.** `htqweb.tenancy.current_company()` поднимает `NoCompanyContext`, если контекст не установлен, — молчаливый откат на `public` дал бы «успешно отработавший» код, не нашедший ни одной строки. Сам `CompanyContextMiddleware` при этом оставляет `search_path=public`, если заголовка `X-HTQ-Company` вообще нет (общие домены вроде `users`/`cms` и страницы голого домена — вход, регистрация, выбор компании, `/join/<token>`) — падает только код, который реально спросил компанию. Архивную компанию middleware не отбивает целиком: чтение идёт в её схему, запись отклоняется (см. «Архив — только чтение» ниже).
- **Токен несёт claim `company`**, и `api_view` отвергает запрос кодом 403, если он не совпадает с компанией, резолвленной из поддомена, — вторая линия обороны: поддомен подделать тривиально, подпись токена — нет.
- **Поддомен — это метка, а не обязательно слаг** (блок I.2). `Company.subdomain` — короткий адрес компании (`htq`, `hts`, `keg`, `group` — миграции `companies/0005`–`0006`; `company_create --subdomain`, `PATCH companies/v1/companies/<slug>` платформенным администратором, поле в `CompanyFormDialog`); `Company.clean()` не пускает зарезервированные метки (`RESERVED_SUBDOMAINS`) и столкновение псевдонима с чужим слагом в обе стороны. Метку из `X-HTQ-Company` middleware переводит в компанию через `companies.interface.resolve_host_label`: сначала псевдоним, затем слаг — но только у компании БЕЗ псевдонима. У компании поэтому ОДИН канонический хост: адрес по слагу у компании с псевдонимом отвечает 404 (два origin'а дали бы два раздельных `localStorage` и два токена); компании без псевдонима (стенд, `*.localhost`) живут по слагу. Дальше всё по-прежнему по СЛАГУ — схема `co_<slug>`, claim токена, `company_slug` в ролях. Ссылки наружу на страницы, читающие таблицы компании (кадровые share-ссылки), строит `companies.interface.public_url(slug)` — `https://<псевдоним или слаг>.<корень>`, корень — хост `PUBLIC_BASE_URL`; общие сервисы (приглашения в конференцию, сводка) остаются на голом домене. Поэтому `PUBLIC_BASE_URL` — голый домен со схемой и без `www` (`https://htq.group`), и из него же `_trusted_origins()` выводит `https://*.<корень>` в `CSRF_TRUSTED_ORIGINS`. На голом домене SPA после входа уводит любой защищённый маршрут на `/companies/choose` (`pages/CompanyPicker.tsx`): одна компания — сразу редирект на её хост, несколько — выбор. Выкатка — чеклистом [docs/deploy/subdomains-runbook.md](docs/deploy/subdomains-runbook.md), одним окном с гейтами блока I.
- **Права в компании могут прийти не из неё самой, а от должности в компании ВЫШЕ по дереву владения.** Должность холдинга, помеченная `hr.Position.serves_subsidiaries` (признак, отдельный от `is_manager`/`external_hierarchy` — «работает на всю группу» и «начальник людей» разные вопросы), несёт свои роли во все компании ниже по дереву — `apps/access/services/inheritance.py`, обход вверх по `Company.parent`; действующий предок отдаёт роли, архивный — нет, но обход идёт дальше; `/me` называет источник в `inherited_from`. **Это не заменяет членство, а складывается с ним**: наследование даёт РОЛИ, но `CompanyMembership` в компании ниже по дереву остаётся отдельным, явно заводимым фактом (`company_grant` или экран участников) — без него токен на поддомен этой компании не выдаётся вовсе, и признак на должности сам по себе не даёт держателю ничего. Разрыв «признак есть, членства нет» виден в метрике `htqweb_access_serving_holders_without_membership` и печатается `company_create` при заведении новой компании.
- **Замещение ключевых должностей** — `hr.Substitution` (HR-FRM-006, миграция `hr/0025`): кто замещает должность, каким приказом это оформлено и в какой период действует правило. Замещающий — **должность**, а не человек: так правило переживает смену держателя. Наружу отдаётся одной функцией `hr.interface.substitutes_for(position_id, on_date)` (ровно три ключа — `position_id`, `kind`, `basis`), которую зовут маршруты согласования. Это ПРАВИЛО, а не отсутствие: домен `hr` отпуска и болезни не моделирует, и решение «пора ли звать замещающего» принимает вызывающий. Неактивные замещающие должности из ответа исключаются — маршрут не должен упираться в тупик.
- **Временный исполнитель должности** — `hr.ActingAssignment` (мастер-план БЗО, B1.1 / D-22, миграция `hr/0038`): сотрудник исполняет должность с/по (обе границы включительно), основание — приказ; назначают АДМ и HR (`/api/hr/v1/acting-assignments`, правка — `hr:admin`, чтение — `hr:read`). В отличие от `Substitution` это СОБЫТИЕ, а не правило: оно закрывает и пустую должность, и отсутствие держателя (отпуск оформляется временным исполнителем его должности на те же даты). `hr.interface.resolve_position_users(position_ids, *, on_date=None)` добавляет временных исполнителей к держателям на дату (по умолчанию — сегодня), `acting_holders(position_id, on_date)` отдаёт только их; исполнять может лишь действующий сотрудник с учётной записью. Движок согласования видит их там, где разрешает должности, поэтому уже созданные задачи назначение не переписывает.
- **ОСУ — системная должность, не порог уровней.** `hr.Position` «Участник (ОСУ)» (`is_system`, вес 0, своё подразделение `osu`) над генеральным директором холдинга; заводится только `participant_service.ensure_participant()` — через `manage.py hr_participant` на бою и `seed_hr_demo` на стенде. Маршруты согласования берут её через `hr.interface.participant_position()` (ровно `id`, `title`, `is_active`; `None` в компании без органа владельцев). Отдельного уровня N-0 нет намеренно: `LevelThreshold` не допускает 0, а дерево раскладывается по связям подчинения. Связь «ГД → ОСУ» на бою ставит кадровик — команда не угадывает ГД по названию.
- **Кадровые решения согласуются движком signoff.** Десять предметов `hr.*` (матрица HR-FRM-004, строки 1–10: заявка на изменение оргструктуры, штатная единица, локальный нормативный акт, должностная инструкция, кадровый приказ, премия, взыскание, график отпусков, заявление на отпуск, командировка) объявлены в `apps/hr/approval_hooks.py` одной таблицей `SUBJECT_MODELS`/`SUBJECT_SPECS` и регистрируются из `HrConfig.ready()` — тем же приёмом, что в `apps.contracts`. Каждый несёт ФАКТЫ, по которым ветвится маршрут: сумма премии, срок отпуска (включительные границы, считается, а не хранится), категория должности (`position_level`, `is_manager`), `target_company_slug` для кросс-компанейского этапа. **Набор ключей фактов — контракт со вторым разработчиком** (roadmap §6.4), закреплён тестом `test_every_matrix_row_has_its_subject_and_facts`: переименование ключа ломает УЖЕ настроенный маршрут в чужих данных, поэтому правится только с обеих сторон сразу. Единственный автоматический эффект утверждения во всём блоке — кадровый приказ пишет запись в `PersonnelHistory` (сторож `test_only_the_personnel_order_has_an_automatic_effect`); остальные девять просто становятся утверждёнными, а отсутствие в календаре и правку оргструктуры вносит кадровик руками. Отправка — `POST /api/hr/v1/approvals/{subject_type}/{id}/submit`, маршруты настраивает второй разработчик; пока маршрута нет, ручка честно отвечает 409.
- ⚠️ **Согласуемая модель обязана звать `assert_editable()` первой строкой каждой операции правки и удаления** (`apps/hr/services/staffing_service.py`, `apps/contracts/services/*.py`). Движок не имеет доступа к чужим таблицам: колонку `approval_state` он ведёт, а сторожить её обязан владелец таблицы — без этого вызова строку, отправленную на согласование, можно изменить посреди маршрута, и согласующие подпишут факты, которых уже нет. Из десяти кадровых предметов сервис записи сегодня есть только у штатной единицы; у остальных девяти замок появится вместе с их ручками, и забыть его тем легче, чем позже они заводятся.
- **Два независимых рубильника.** `apps.core.models.ServiceStatus` гасит домен на всей платформе; `apps.companies.models.CompanyModule` — у одной компании. `CORE_MODULES` (`apps/core/services.py`: `users, companies, core, hr, messenger, media, cms, access`, плюс платформенные аппки БЗО `project, refdata, notifications`) — обязательное ядро, у каждой компании оно есть всегда и `CompanyModule` на него не действует. Оба слоя объединяет `apps.core.services.service_status()`, а не только `require_service()`: HTTP-гейт (`ServiceGateMiddleware`) спрашивает именно `service_status()`, и будь компанейский рубильник только внутри `require_service()`, запрос к аппке с выключенным у компании модулем прошёл бы этот гейт насквозь — вьюхи вызывают свои сервисы напрямую, а не через `interface.py`.
- **В Celery компания передаётся явно.** `@company_task` (`htqweb/tenancy/celery.py`) разворачивает именованный kwarg `company_slug` в контекст; без него — `MissingCompanyArgument`, а не молчаливый откат на `public`. Обёртка объявляет `company_slug` в своей `__signature__`: на Python 3.14 (бой, CI) Celery проверяет аргументы `.delay()` через `inspect.signature`, и без этого `.delay(company_slug=…)` падает `TypeError`, а на 3.13 — нет; сторож — `test_invariants.py::test_company_tasks_accept_company_slug_by_signature`.
- **Миграции тенантных аппок НЕ идут при старте контейнера.** `RUN_MIGRATIONS=1` в `docker-entrypoint.sh` вызывает `manage.py migrate_shared`, а не голый `migrate`: список общих аппок вычисляется из графа миграций минус `TENANT_APPS`, потому что после `tenancy_bootstrap` голый `migrate` при `search_path=public` счёл бы тенантные аппки (`settings.TENANT_APPS`) непромигрированными и создал бы их таблицы заново — пустыми, поверх боевых данных, уже переехавших в схемы компаний. Схемы компаний доводит `manage.py migrate_companies`, отдельно, во время выкатки. Расписания Celery-beat тенантных аппок (data-миграции из `SHARED_EFFECT_MIGRATIONS` — на живом стеке они не выполняются нигде) заводит `apps/core/periodic_tasks.py::ensure_periodic_tasks` в конце `migrate_shared` (вручную — `manage.py ensure_periodic_tasks`): только недостающие строки, операторские `enabled`/расписание не трогаются; новая такая миграция обязана попасть и в реестр `PERIODIC_TASKS`, сторож — `apps/core/tests/test_periodic_tasks.py`. Разные компании штатно стоят на разных версиях, поэтому **любое изменение схемы тенантной аппки — по expand/contract**: обратно-совместимый шаг отдельной миграцией от разрушающего.
- **Сводное чтение холдинга** — схема `holding`, `UNION ALL`-представления по всем действующим компаниям (`apps.companies.services.holding_views`). Каждая tenant-аппка **обязана** объявить `apps/<domain>/holding.py` с `HOLDING_MODELS` (пустым кортежем, если сводить нечего) — отсутствие файла или атрибута роняет сборку `ImproperlyConfigured`, чтобы аппка не выпала из сводок молча. Представления физически **блокируют contract-миграции** (Postgres не даёт удалить столбец или сменить тип, пока от него зависит вьюха), поэтому `migrate_companies` сносит их до прогона и собирает после; заведение, архивация и восстановление компании тоже пересобирают их.
- **У сводок появились читатели.** `managed=False`-модели `apps/<домен>/holding_models.py` (`hr`, `tasks`) читают представления `holding.*` через `use_holding()`; экран «Сводка группы» (`/holding`) собирает две ручки — `hr/v1/holding/headcount` и `tasks/v1/holding/projects`. ⚠️ У читателя `db_table` СОВПАДАЕТ с таблицей компании (иначе и быть не может — представление называется по таблице), поэтому вызов вне `use_holding()` прочитал бы одну компанию и выдал её цифры за групповые. Чтобы это не случилось молча, `use_holding()` ставит признак `htqweb.tenancy.db.holding_active()`, а менеджер читателя без него поднимает `HoldingContextRequired`. Сводка отдаётся только на поддомене компании вида «холдинг» (`apps.companies.interface.is_holding`, свой гейт `_deny_unless_holding` в каждой из двух вьюх) — ПОВЕРХ гейта модуля `api_view(module=…)`: гейт модуля → гейт вида компании → сервис. С блока I сторож `apps/access/tests/test_gate.py` гейт модуля на каждой ручке `hr`/`tasks` ТРЕБУЕТ. Кадровая ручка стоит под `module="hr", level="read"` (пускает держателя любой кадровой роли, хоть `hr-junior`), задачная — под `module="tasks", level="admin"` (у `employee-basic` модуль `tasks` агрегируется в `write`, поэтому `read`/`write` пустили бы рядового сотрудника; `is_staff` без роли гейт не пускает — бесплатный обход только у `is_superuser`). Строгость разная НАМЕРЕННО не сведена к одной: это следствие уже сложившихся конвенций доменов `hr`/`tasks`, а не замысел блока H. Во время `migrate_companies` представлений не существует — ручки отвечают 503 «сводки пересобираются», а не нулями.

**Новая схема компании рождается с уровнями N-1…N-4** — `hr/0024_seed_level_thresholds` сеет `LevelThreshold` при `migrate_companies`, только в схеме компании (`search_path` начинается с `co_`) и только в пустую таблицу; в `public` (pytest, dev до `tenancy_bootstrap`, HTQ до переноса) миграция ничего не пишет. `UnitType.DIRECTORATE` — вид подразделения для трёх дирекций холдинга.

⚠️ **Expand по тенантной аппке требует `migrate_companies` отдельным шагом выкатки.** Старт контейнера зовёт `migrate_shared` и схем компаний не трогает, поэтому новый столбец появится в `public`-части и не появится в `co_<slug>` — код, который его читает, упадёт у всех компаний. Образец такого шага — `hr/0021_position_external_hierarchy`.

⚠️ **`RUN_MIGRATIONS` в `docker-compose.yml` по умолчанию `1`** (`${RUN_MIGRATIONS:-1}`), `.env.example` (единственный `.env*`-файл в корне репозитория) его не задаёт, а боевой `.env` в репозиторий не входит — «миграции на проде выключены» не гарантировано репозиторием. Перед `tenancy_bootstrap` на бою флаг надо выставить явно.

⚠️ **Осиротевшая строка реестра после неудачного отката `company_create`.** Откат — три независимых шага (`drop_schema`, удаление строки `Company`, `rebuild_holding_views`), каждый через `_cleanup` (см. докстринг `apps/companies/management/commands/company_create.py`). Если `company.delete()` упадёт ПОСЛЕ того, как `drop_schema` уже успешно снёс схему, в реестре останется активная строка компании без физической схемы под ней — и следующий `rebuild_holding_views` (в том же откате или при следующем `migrate_companies`) упадёт, пытаясь собрать `UNION ALL` по несуществующей `co_<slug>`: сводки холдинга не восстановить, пока эта строка не удалена руками. Лечение — удалить осиротевшую строку `Company` (django-admin или `Company.objects.filter(slug=...).delete()`) и повторить `manage.py migrate_companies` (пересобирает представления по оставшимся действующим компаниям).

Вне гейта: `core` (не модуль прав), WebSocket мессенджера, SSE `approvals/stream`. Уровень считается **только в контексте компании**: без `X-HTQ-Company` — `none` у всех, кроме суперпользователя (`is_staff`/`is_admin` сами по себе не открывают ничего), поэтому тестам ручек нужны и заголовок компании, и роль (`apps/access/tests/helpers.py::assign`, `apps/tasks/tests/helpers.py::auth`). Сторож `test_gate.py` с блока I.2 видит и метод класса-вьюхи (`get/post/…`) вовсе без декоратора — базы классов читаются через `ast` и резолвятся через псевдонимы импорта и по всем модулям аппки (доменная база в соседнем модуле тоже видна); требует явный `level=` рядом с `module=` и разрешает его и в определении фабрики-декоратора (литеральное умолчание в сигнатуре, литерал у вызова — только `read|write|admin`), а уровень, переприсвоенный в теле фабрики или пришедший распаковкой (`**{...}`) на её вызове, — нарушение; текстовый разбор сверяется с `ast` по числу вызовов `api_view`. Функции-ручки из `urls.py` без `api_view` тоже проверяются: засчитывается только строгий диспетчер — ветвления лишь по `request.method`, без вызовов до гейта (в условии — только методы над `request.…`, в аргументах — только имена), все пути закрыты (гейтированная ручка того же файла или 405). Ручка с собственной логикой ветвления — только явной записью в `_DISPATCHERS_WITH_OWN_LOGIC` с причиной; каждый её `return` всё равно проверяется, а запись, которую сторож больше не находит, валит тест как устаревшая.
- **Проверки тоньше уровня — по узлу**: `apps/hr/rbac.py::NodeAccess.has(<старый ключ>)` раскрывает ключ в узел+признаки через `KEY_TO_NODE` и спрашивает `access.interface.flags_for`. Нужно, потому что уровень модуля не отличает senior от lead, а узел `hr.employees` с признаком `delete` — отличает. Область (`department`/`company`) режет выборки, не вход в ручку. Роли считаются **один раз на запрос**: гейт `api_view(module=)` кладёт тройку `(компания, user_id, расчёт)` в `request.access_resolution` (явный атрибут запроса, не `contextvar`), и `NodeAccess` переиспользует её, только если совпали и компания, и `user_id` токена; ручки без гейта считают сами.
- **Ручки самообслуживания намеренно без гейта** — реестр `apps/access/self_service.py` с причиной из закрытого списка `self` (строго свои данные) | `open` (общий справочник, у которого проверок не было и сужать не наше решение) | `scoped` (защищена своей, не ролевой проверкой); сторож `test_gate.py` требует гейт у всего вне реестра и причину у всего в нём. ⚠️ В `companies` фабрика `@platform` стоит в реестре ОДНОЙ записью `"platform": "scoped"` — любая новая ручка на ней попадает в `scoped` автоматически, поэтому обязана первой строкой звать `deny_unless_platform_admin`, как архив/восстановление/отзыв.
- **Роль может принадлежать компании** — `Role.company_slug` (`access/0009` поле, `0010` проставляет его уже заведённым `hr-custom-*`; пусто — роль общая для группы, как все системные и созданные в редакторе). Именная роль переноса несёт название должности своей компании, поэтому каталог `GET access/v1/roles` отдаёт общие роли плюс роли компании запроса, а соседние чтения (`roles/<id>/permissions`, `roles/<id>/holders`) на чужую роль отвечают 404, как на несуществующую (`AccessView.role_or_404`); суперпользователь видит всё. Выдача чужой роли отвергнута на всех путях: сервис (`assignment.assert_role_belongs` → 422), django-admin (`PositionRole.clean()`/`RoleAssignment.clean()`). Копия роли (`roles/<id>/copy`) наследует компанию источника.
- **`apps/hr/access.py` — только эвристика переноса** (`classify_hr_level` для `hr.interface.list_positions_hr_levels` → `manage.py access_backfill_positions`), не модель прав; сторож `apps/hr/tests/test_single_rbac_guards.py`. **`Position.permissions` — мёртвая колонка**: кадровый домен её не читает, сид не пишет; жива ради `hr.interface.user_has_permission` для `apps/contracts` (roadmap §6.6) и записи через API должностей ради него же. Узел именной роли — объединение признаков всех ключей списка, ведущих в него, поэтому ключи одного узла **складываются**: роль отвечает «да» и на соседний старый ключ того же узла, чьи признаки покрыты (как у ролей уровней; сторож `test_backfill_positions.py::test_single_key_custom_role_grants_only_that_key`). **Сознательное исключение №4**: должность, чей список состоит только из ключей `contracts.*`, кадрового доступа не получает — старая модель пускала держателя в кадровые ручки по одному уровню (`HRAccess.has_access` — «уровень есть ИЛИ ключи есть»), хотя ни одного кадрового ключа список не давал; сводка печатает такие должности строкой «явный список без кадровых ключей», `contracts` читает свои ключи из колонки сам. ## Среды и политика fallback'ов

**Fallback** здесь — место, где вместо настоящего значения подставляется запасное и выполнение продолжается. Такие места молчаливы по своей природе: снаружи подмена выглядит как нормальная работа. Поэтому все они проходят через один примитив, а среды разведены так, чтобы у разработчика подмен не было вовсе.

Ось одна на три рантайма — `HTQ_ENV` (для фронта `VITE_HTQ_ENV`, вшивается в бандл на сборке):

| Среда | `HTQ_ENV` | `DJANGO_SETTINGS_MODULE` | Режим | Как запускается |
|---|---|---|---|---|
| Прод | `production` | `htqweb.settings.base` | `log` | `docker compose up -d` |
| Тестовая (как прод) | `staging` | `htqweb.settings.base` | `log` | `docker compose -f docker-compose.yml -f docker-compose.staging.yml up -d` |
| Разработчик | `development` | `htqweb.settings.dev` | **`strict`** | `docker compose -f docker-compose.test-local.yml up -d` |
| pytest | — | `htqweb.settings.test` | **`strict`** | `pytest` |

- `log` — подмена происходит, **пользователю не видно ничего** (ни в теле ответа, ни в UI): строка `FALLBACK site=… reason=…` в лог + `htqweb_fallback_total{site,expected}`.
- `strict` — подмены **нет**: летит `FallbackNotAllowed` (на фронте `FallbackNotAllowedError` в оверлей Vite), `raise … from exc` сохраняет исходный traceback.
- `FALLBACK_MODE=strict|log` перебивает вывод из среды в обе стороны (включить строгий режим на стенде перед выкаткой; разово ослабить локально). `FALLBACK_LOG_LEVEL` крутит уровень отдельного логгера `htqweb.fallback`.

**Новый fallback пишется только так** — `htqweb/fallback.py`, `frontend/src/lib/fallback.ts`, `sfu/src/fallback.ts` (одинаковый API):

```python
try:
    values = module.collect()
except Exception as exc:
    fallback("core.metrics.app_collect_failed", None,
             reason="сбор метрик аппки упал", exc=exc, app=label)
    continue
```

`site` — статический литерал `<аппка>.<модуль>.<что>`: он уходит в метку метрики, данные туда подставлять нельзя. `expected=True` помечает предусмотренную деградацию (камеры нет, плана нет) — strict её не роняет, лог тише, серия в счётчике отдельная; алерт смотрит только на `expected="false"`.

**Что через него НЕ проходит** (иначе механизм утонет в шуме, и на слово FALLBACK перестанут смотреть): дефолты конфигов из env; штатные лестницы разрешения, срабатывающие на каждый вызов (`apps/hr/services/calendar_service.py::_fallback`, `image_service.detect_mime`); визуальные заглушки на фронте (`|| '—'`, `?? []` во время загрузки); `is_fallback` в `apps.signoff` (предметное понятие «запасной этап маршрута»); `AvatarFallback` из shadcn. Отдельный случай — коллектор `BusinessMetricsCollector.collect()` и `htqweb/gunicorn_conf.py`: там нельзя трогать реестр Prometheus и нет настроек Django соответственно, и в обоих файлах написано почему.

⚠️ **Celery-процессы `/metrics` не отдают** (Prometheus снимает их через Flower), поэтому подмены из задач в метрику не попадают — их закрывает Loki-правило `htqweb-fallback-worker-logs` по подстроке `FALLBACK`.

## Observability

Prometheus (`infra/logging/prometheus/prometheus.yml`) scrapes **13 jobs**: `django-backend` (WSGI) and `django-asgi`, `celery` (via Flower), `postgres`, `redis`, `node` + `cadvisor` (host and containers), `nginx` (production profile only), `sfu`, `minio`, `loki`, `grafana`, and itself. The `nginx` job uses `dns_sd_configs`, not a static target, precisely because `nginx-exporter` lives in the `production` profile: outside it the name doesn't resolve, so the job has **zero targets** instead of a permanently-DOWN one (a static target there meant `htqweb-target-down` fired forever). Celery processes (`backend-worker`, `backend-beat`, `backend-media-worker`) deliberately have **no job and no `/metrics`** — they serve no HTTP; their visibility is Flower + `redis_key_size` per queue + Loki. Retention is 30d **or** 10GB, whichever comes first (`infra/logging/prometheus/Dockerfile`). `PROMETHEUS_ENV` lands in `external_labels` on every series.

**Access is closed in prod, open in dev.** Grafana faces the outside two ways: nginx `/grafana/` with the JWT SSO it already had (superuser→Admin, staff→Editor; dashboards in the **HTQWeb** folder), and host port `3001` kept open on purpose as a spare entrance when the gateway is down. Everything else in prod is bound to **`127.0.0.1`** (`prometheus` 9090, `loki` 3100, `flower` 5555, the MinIO console 9001, and `redis` 6379 — that last one used to be on `0.0.0.0` with no password) or publishes no port at all (`postgres-exporter`, `redis-exporter`); reach them with `ssh -L`. The test stacks keep publishing everything on `0.0.0.0`. nginx does not proxy `/prometheus/` (it used to, with no auth whatsoever, and Prometheus has none of its own) — the admin monitoring widget goes through `GET /api/admin/v1/infrastructure/targets` instead, which fetches server-side behind the usual `admin=True` gate. In prod `GRAFANA_ADMIN_PASSWORD`, `GF_TELEGRAM_BOT_TOKEN` and `ALERT_EMAIL_TO` are declared with compose's `:?` syntax and the stack refuses to come up without them — **an empty Telegram token or email address makes Grafana 10.4 exit 1 on contact-point provisioning**, taking the dashboards down with the alerts.

**The backend exposes `/metrics`** (`apps/core/views.py::metrics`, registered in `apps/core/urls.py` next to `/health/`, deliberately outside `/api/` so `ServiceGateMiddleware` can't gate it). `django-prometheus` supplies HTTP/DB/cache metrics; `DATABASES.ENGINE` and `CACHES.BACKEND` are its wrapper subclasses. ⚠️ `backend-web` runs `gunicorn --workers 4`, so metrics use **multiprocess mode**: `PROMETHEUS_MULTIPROC_DIR` (tmpfs) + `htqweb/gunicorn_conf.py` (clears the dir on boot, marks dead workers on `child_exit`). Without that, a scrape hits one random worker of four.

**Business metrics** are per-app: `apps/<domain>/metrics.py` defines `collect()` over its own models, `apps/core/metrics.py` discovers and merges them (same convention as `API_PREFIX` autodiscovery — no cross-app imports, so `test_app_isolation` stays green). **All fourteen domain apps have one** (`tasks, approvals, mail, conference, contracts, signoff, hr, cms, media_files, messenger, users`, plus `access`, `companies` and `bpp` — the BZO module, its own `htqweb-bpp` dashboard: approval queue, nightly «Задействовано» check, failed bank-statement imports, invoice queues of the FD and the accountant, invoices waiting for closing documents longer than 5 days) — the seven from `contracts` to `users` were added together with the `htqweb-domains` dashboard, because `test_metrics_are_observed` refuses a metric that no panel and no rule looks at. **Tenant apps are collected per company.** `_metric_modules()` marks `settings.TENANT_APPS` (today `hr`, `tasks`, `contracts`, `signoff`, `bpp`, `project`; only those that ship a `metrics.py` are collected), and `collect_all()` calls their `collect()` inside `use_company(slug)` for every active company that has a schema, labelling each series `company=<slug>` (a company without a schema is skipped with a `logger.info` — `search_path` into a missing schema falls through to `public` and would duplicate its numbers). Dashboards fold them with `sum/max without (company)` under a «Компания» variable; the nine rules on them keep the company (no aggregation, or `by (company, …)`), and the notification templates print it. Guards: `test_tenant_metrics_on_dashboards_follow_the_company_variable`, `test_alert_rules_keep_the_company_of_tenant_metrics`. A `metrics.py` uses **no** `require_service`: observability must survive a disabled domain. Metric names carry **no digits** — the guard test's regex is `htqweb_[a-z_]+`. They're computed by Celery-beat every 60s into the cache (`apps.core.tasks.collect_business_metrics`), not on scrape, and exported under the `htqweb_*` prefix. An empty cache exports **nothing** rather than zeros — "the collector died" and "zero tasks" must not look alike.

Alerting stays in Grafana (no Alertmanager): **43 rules** in `infra/logging/grafana-provisioning/alerting/` — 30 Prometheus, 7 Loki, and 6 in a separate `htqweb-business` group. **Two Telegram chats, split by the `channel=business` label, not by severity** (severity means urgency, channel means audience): incidents ring, business events arrive silently and are *allowed* to stay lit for weeks. The business route is deliberately **first and without `continue`** in `contact_points.yml` — reordering it silently sends business events to the incident chat too. Message text lives in `templates.yml` (one template per chat); the threshold a rule compares against is **not** in a notification's data, so each rule carries its own `threshold` annotation for the template to print, and `__dashboardUid__`/`__panelId__` (27 rules have them) are what make `{{ .DashboardURL }}` render at all. That file's header records what was deliberately *not* alerted on and why — read it before adding a rule; every noisy rule costs the whole system its credibility. The load-bearing one is `htqweb-business-metrics-stale` (`absent(htqweb_service_enabled)`): when the beat collector dies the `htqweb_*` family stops being exported entirely, and every rule that reads it has `noDataState: OK` — so without this rule the platform reports "all green" precisely because it went blind. Dashboards live in `infra/logging/grafana-dashboards/` (11 files); `backend/apps/core/tests/test_metrics_are_observed.py` fails the build if a metric is collected but appears on no dashboard and in no rule, or if a dashboard references a metric that no longer exists. Delivery is Telegram for everything, plus email as a second independent channel on `severity=critical` — secrets via `GF_TELEGRAM_*` / `GF_SMTP_*` (see `.env.example`). One deliberate exception to "alerting belongs to Grafana": `apps.core.tasks.send_daily_digest` (Celery beat, 09:00 Asia/Almaty Mon–Fri, migration `core/0005`) posts a morning summary to the business chat itself. The bot is the same one Grafana uses, so `TELEGRAM_BOT_TOKEN` **defaults to `GF_TELEGRAM_BOT_TOKEN`** (now also passed into `x-django-env`) and only exists as an override; `TELEGRAM_DIGEST_CHAT_ID` is separate and must be set, because Grafana keeps chat ids as literals in `contact_points.yml` and duplicating one into settings would be a second truth about where things go — empty just disables the digest. It is legitimate precisely because it is *not* incident alerting: a digest is about **comparison** ("31, was 35 yesterday" — it diffs against a second cache key), Grafana OSS has no reporting at all, and it costs zero queries because it reads the cached snapshot. It never raises or retries (a failed send goes through `fallback(expected=True)`, so it surfaces in the incident chat via `htqweb-fallback-worker-logs` instead of re-sending). `scripts/generate-monitoring-traffic.sh` targets the Django backend and works as-is.
